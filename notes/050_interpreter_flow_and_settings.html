The shared interpreter flow

Retry transient transport failures at the same endpoint with finite attempts and backoff. Give a model bounded opportunities to inspect and correct its answer. Escalate to the next configured model when those opportunities are exhausted.

The first chart is the proposed common design. Current provider behavior and supported TOML settings follow for comparison; they do not yet implement every part of this design. Configuration examples contain no live deployment values.

Proposed common flow: choose evidence, then submit

Design revision for review; module refactor pending. See the implementation plan in note 052. The model chooses a permitted action. The provider decides whether scientific input is acceptable. The SDK owns requests, bounded correction, model selection and retirement. A model's final prose or input-problem claim cannot accept preparation or prove invalid input.

Keep one API Attempt and one overall deadline. Choose endpoints in configured order, dividing remaining time among untried endpoints after prior cleanup. Fix each model's deadline once. “Later” means configured later, not automatically smarter.

Which tools does the model actually need?

Tool access should answer a concrete question or perform a permitted action. Reading information is optional unless the provider's scientific contract requires an inspection. Do not force every model through discover → inspect → validate → submit.

Corrections to the earlier chart

  • Separate model claims from provider decisions. An inability report requests handoff; it is not a rejected proposal, accepted preparation or verified bad input. Repeated model agreement does not change that.
  • Repair identifiable call mistakes; escalate unusable carriers. Unknown tools, invalid argument JSON and multiple calls can receive safe correction without running anything. A reply whose call identity cannot be trusted cannot be repaired as an ordinary tool result.
  • Count corrections honestly. The current SDK's three-correction allowance includes protocol repairs and rejected tool arguments, not just scientific proposals. Successful information calls consume turns and time, but no correction allowance. Each model has 12 turns; each turn has at most two HTTP attempts.
  • Do not make a tool a mandatory preflight. The first model can submit directly when the original input and supplied schema suffice. A successor can inspect fresh data without first reading history. Provider-specific scientific prerequisites still apply.
  • Keep acceptance before cleanup. A preparation accepted after its model window expires is retained. Cleanup trouble cannot turn that acceptance into permission to replay preparation. Provider failures propagate promptly; their caller retains resource settlement.
  • Do not promise fresh inventory in successor context. The module reuses captured original messages and adds its catalogue. Only provider operations establish current source membership or validity.

Limits to keep visible before implementing

History pagination is not context management. Earlier pages remain in the transcript. Filling the remaining request allowance with one page can leave no room for another page or useful reasoning. Keep the current bounded reader, but do not promise that a model can read an arbitrarily large record page by page. Targeted provider inspection is preferable when available; record selection or transcript compaction needs a separate demonstrated requirement.

A constraint lookup need not discover anything new. Its static fallback repeats the supplied schema and handles simple property paths; it is not a full JSON Schema resolver. Source-specific allowed values require the provider accessor. Keep this distinction in the tool description.

Refactor boundary: keep one module. Bind each shared tool's schema and execution behavior together; derive advertised definitions and lookup from the same instances. The model visit retains deadlines, retries, correction accounting and cleanup. Provider callbacks retain scientific validation and effects. Use the agreed report_interpretation_problem name and keep scientific report fields provider-owned; no additional handoff tool.

Earlier alternative: compact automatic handoff

Not the selected SDK approach. This alternative would supply selected history directly. Do not require the successor to call a new history tool before it can act. A history lookup adds a model round trip and consumes its turn/time allowance. Original instructions remain primary; prior model guesses do not replace them.

Original input

The original request and provider instructions, with the current authoritative source/upload membership where reconciliation can change it. Never substitute an earlier model's interpretation for the user's input.

Failed proposals

Bounded recent proposal/rejection pairs from prior model visits: what was proposed, which tool or provider rule rejected it, and the safe rejection reason. Mark proposals as unaccepted model output. A formatting error is not evidence that source-supported scientific values are wrong.

Captured observations

Directly useful inspection findings with their tool, source/member references and input identity. These establish what was observed; source-supplied text and scientific claims do not become instructions or proven truth merely because a tool returned them.

Build the handoff from captured records without another model call. Keep relevant records across the model ladder, not only the immediately preceding model. Explicitly mark omitted older records or large payloads; do not silently truncate structured proposals into different ones. Do not forward raw transcripts, model reasoning, network diagnostics or credentials.

Large inspection details: use the provider's existing tools

A ZIP member listing can approach 256 KiB in SECS, so automatically injecting every prior inspection is wasteful. Include a small index of relevant source/member or representation references. The successor can use existing tools such as inspect_source or inspect_upload if it needs further detail. This case does not require adding a generic history tool to every provider.

An existing inspection call is not automatically a cached read. SECS's inspection path acquires sources, invokes the scientific worker and updates representation claims. Source reconciliation can change membership or bytes within an API Attempt. Providers own those operations and determine whether an old observation is still applicable; stale records must be marked accordingly.

A provider may reuse a captured result only when it explicitly establishes replay-safe semantics for the same source/companion identities and exact inspection scope. Do not add blanket SDK memoization or cache failures, preparation or execution. Retrieving a cached 256-KiB result still adds that much data to context; caching alone does not solve prompt-size limits. Targeted retrieval or pagination needs its own demonstrated provider requirement.

History is transient and scoped to this interpretation inside its existing API Attempt and captured input identities. A model visit is not a new API Attempt. There is no cross-Job transcript store, generic history API or new persistence layer. Optional inspection calls use ordinary turns/time, not the correction quota when successful, and retain their provider-owned lifecycle. A history lookup never authorizes replaying an accepted preparation or generation.

Selected approach: the model fetches the context it needs

Implemented in the shared SDK; provider adoption remains separate. The Interpreter module implements the tools-first flow with the existing conversation and transport owners. Its API and integration example are in the package README. This does not change the current provider wiring described below.

Give the successor the original request, provider instructions, captured source inventory when supplied and a small catalogue of earlier work. Do not automatically inject prior proposals or large inspection payloads. The model chooses which records to retrieve, which sources to inspect now, or whether it can act directly.

Original task + catalogue → model chooses needed evidence → read captured record(s) → reason / inspect / submit
Reading history is optional. Each read uses the ordinary model-turn and time budget, but not the correction quota when successful. It never restarts a deadline.

One shared record-reading tool

The SDK-owned read_interpretation_records tool reads one or several catalogue references in one invocation:

{"records": [{"ref": "record-3"}, {"ref": "record-2"}]}

Batching fits the existing one-tool-call-per-model-turn pattern without serial round trips for every small record. The tool returns captured data only: it does not download, inspect, prepare or execute scientific work. Its authority is closed over this interpretation inside its existing API Attempt; the model supplies no cross-Job selector.

Each returned page identifies its kind, model visit, tool, historical status, retained record size and whether the response is complete. Source identities are part of the captured provider payload, when supplied. A batch explicitly identifies every returned, unavailable or deferred record; missing output is not evidence that no record existed. Malformed carrier or argument text is not retained as a history record; the unavailable count covers records dropped by retention limits, not every failed model turn. Raw model text and private transport diagnostics are not reconstructed.

Large records: bound responses without forcing tiny pages

Return selected records together when they fit the existing response and the entire next model request, including its prior messages and tool framing. Byte size alone does not establish token fit; respect known model context limits without claiming an unknown token limit has been proved. A 256-KiB record does not inherently require four 64-KiB model round trips. When a selected record cannot fit, return an explicit incomplete result with a cursor bound to that immutable captured record. The same reader can request the next part:

{"records": [{"ref": "record-2", "cursor": 4096}]}

Chunks are explicitly fragments, not silently truncated complete JSON records. Reading a page does not prove that the whole observation or source has been examined. Pagination helps the model select less data; if it ultimately reads every page, those bytes still consume context and additional model turns. No generic search language, cross-Job archive, new service or extra TOML controls are proposed.

Queryable capabilities and allowed values

Model-directed access can also expose the active input contract. The describe_input_constraints tool answers a targeted query such as:

{"tool": "submit_interpretation", "field": "verbosity"}

The static response returns the declared field schema, required status and parent schema; dependencies remain as declared, not resolved. A provider accessor can supply dynamic restrictions. Other useful queries include accepted formats, units and source-dependent representation choices. Return provider-owned capability/validator metadata from the same authority that admits inputs; do not maintain a second handwritten list in the SDK or TOML. The provider owns scientific constraints, while the SDK supplies a common query interface.

Keep essential tool names and argument shapes visible so the model knows what it can ask. Small static enums may remain in the tool schema; larger or dynamic sets can be fetched when needed. These metadata reads consume normal turns/time, without spending the correction quota when successful or performing a scientific preparation. Knowing a value is allowed does not establish that it matches the user's request or source data.

A useful trace

  1. An earlier model proposed source-supported scientific values but placed a verbosity field at the wrong location. Its candidate and provider rejection are retained as record-3.
  2. The successor sees that catalogue entry and chooses to read it, rather than receiving every previous conversation.
  3. It sees the formatting rejection, preserves the useful scientific values as proposals to check against the original input, and submits the corrected shape.

For SECS, it could instead retrieve a relevant captured ZIP inspection. If that observation is stale or current source identity matters, it explicitly requests a fresh inspection; the historical reader neither updates representation claims nor makes an old representation valid again.

The real tradeoff

Strength: the model chooses evidence instead of inheriting an automatically selected narrative. It can avoid irrelevant proposals and large old observations, and historical reads have an honest read-only contract separate from live inspection.

Cost: optional reads still add model latency and consume time/turns. The model can overlook relevant records, spend its entire window retrieving pages, or miss a contradiction in an unread part. Unread history does not justify claiming that no prior rejection or observation exists. A claim about the completeness or absence of original-source content requires the relevant source evidence; access markers alone do not prove comprehension. Ordinary provider validation does not generally guarantee that a partial reading found every scientifically relevant fact.

The SDK uses catalogue-plus-pull access instead of automatic history-payload injection. It reuses bounded per-interpretation memory; it does not require a persistent record store or a configurable handoff-mode matrix. Original input, provenance, source freshness and scientific ownership remain the same requirements under either strategy.

Agreed default: divide remaining time among untried models
After previous endpoint cleanup settles, divide the remaining overall time by the number of endpoints still to try, including the one being selected. Fix that model's deadline once; retries and corrections never restart it. Unused time rolls forward. With 240 seconds and two models, the first receives at most 120 seconds. If its model work ends after 20 seconds, the second receives approximately 220 seconds minus cleanup time; if it uses its full 120 seconds, the second receives approximately 120 seconds minus cleanup time. Cleanup consumes overall time rather than extending the interpretation window. The caller's earlier Job/work deadline still takes precedence.
No arbitrary short response ceiling
A connected model request may use its remaining model window. An 80-second response can fit a 120-second window; it must not be repeatedly aborted by an unrelated 25-second SDK read limit. A short SDK connection-establishment bound, including DNS and TLS setup, can detect unreachable services. Confirm cleanup before retrying; retire safely before escalation.
Retries are a maximum, not a promise
A quick transient failure leaves time for a same-endpoint retry after backoff. A request that consumes the entire model window causes escalation; there is no time left to promise another full-length request. The proposed initial SDK policy allows at most two HTTP attempts per logical turn, including the first, with one bounded jittered backoff and Retry-After handling. These are SDK policy, not endpoint-file settings.
Keep inspection and failed proposals distinct
The SDK centrally bounds total logical turns and corrections per model, including protocol repairs and rejected tool arguments. Successful inspections consume turns and time, but do not consume the repair quota. Corrections remain best-effort within the total-turn and time limits; inspections can exhaust those limits before all repair opportunities are used. The initial policy should accommodate SECS's existing 12-turn conversation while limiting repeated bad proposals separately; the exact constants belong in centrally qualified SDK policy, not per-model TOML.
No duplicated limits in endpoint files
Drop endpoint IDs, endpoint/exchange/retirement timers, per-model turn caps and retry/backoff knobs from this proposal. Endpoint files contain complete URL, model and credential-file reference, with reasoning effort or CA only when the service needs them. Introduce a model-specific time override only if measured behavior demonstrates that the default allocation is insufficient.
One captured configuration per interpretation
Capture the overall policy and ordered endpoint definitions before starting. Do not rescan or reread settings between retries and endpoint switches. Later edits apply to new interpretations.
Scientific ownership stays with the provider
Escalation carries the original request and a provenance-labelled catalogue with optional record retrieval; it never replays accepted scientific work. The provider retains its prompts, tools, acceptance rules and work deadlines. Exhaustion ends this Job, not the provider.

Current implementation: three things to count

Logical turn

One call to an endpoint adapter to obtain and handle a model reply. The counter increments before that call, so a failed exchange also uses a turn.

HTTP attempt

One network request. NMRPeak can make up to two HTTP attempts inside one logical turn for selected operational failures. That retry does not create another conversation turn.

Tool feedback

The provider returns inspection findings or explains a rejection. Sending that feedback does not itself use a turn; the model's next response requires the next turn.

Turn 1 · InspectModel asks to inspect an upload.
Provider returns facts.
Turn 2 · ProposeModel proposes input.
Provider rejects it and explains why.
Turn 3 · RepairModel proposes corrected input.
Provider accepts it and finishes interpretation.

A limit of three means three total turns. It includes the initial turn and useful inspections. If turn 3 is rejected, there is no turn 4 in that conversation. A provider may then try another endpoint under the policy below.

One conversation, at the current endpoint

An endpoint is a configured model service and model name. Deadlines and cancellation can interrupt this flow; cleanup still has to settle.

Before switching: the previous model I/O must retire safely. Unconfirmed cleanup blocks ordinary fallback. Scientific crashes, uncertain scientific outcomes and cancellation are not permission to repeat work with another model.

Provider branches: what happens next

Both amber boxes above enter this chart. A deadline or cancellation can end the operation at any point. “Retired” means the previous model connection's cleanup is confirmed.

What happens after failure or exhaustion?

“Next” means the next configured endpoint. It can be a more capable model if configured that way; the code does not assess intelligence or reorder endpoints.

Endpoint selection and order
The interpreter directory's *.toml files are read in lexicographic filename order, for example 00-fast.toml before 10-strong.toml. The id field does not set priority. base_url, model and optional reasoning_effort select each service/model. At most 4 endpoints.
Binding configuration: [interpreter]
request_timeout_seconds bounds one HTTP exchange; turn_timeout_seconds bounds the adapter turn; interpretation_timeout_seconds bounds the whole endpoint sequence. These live in the selected binding's configuration, such as the tracked e01.toml.example, rather than the top-level provider example.
Turn count
MAX_TURNS_PER_ENDPOINT = 3 is a code constant, not a TOML setting. Raising a time limit does not raise the turn count.

NMRNet · one conversation budget across endpoints

Turn 1 at A → carrier failure → retire A → turn 2 at B → …
Fallback preserves the transcript and consumes the same total allowance; it does not reset the turn counter.

config/provider.toml: [interpreter].max_turns
Total logical turns across the ordered [[interpreter.endpoints]] list. The tracked example uses 6. This is not six turns per endpoint.
[[interpreter.endpoints]]
Endpoints run in their array declaration order, not sorted by configuration_id. url is the complete request URL and is sent verbatim: include /chat/completions when that is the service's route. [preparation].seconds
The input-preparation owner bounds the selection phase, including its interpreter chooser. This is a different setting from endpoint exchange time and from the logical turn count.

SECS · one configured interpreter

One endpoint → inspect / propose / correct → accept, cannot-analyse, or exhaust budget

config/provider.toml: [execution]
interpreter_url, interpreter_model and optional interpreter_reasoning_effort select one model service. There is no ordered endpoint list.
max_turns
Total turns for that endpoint. The tracked configuration example supplies 12; the lower-level session constructor has a default of 8. A deployed value must be read from its own configuration.
interpretation_seconds and work_seconds
The interpretation deadline is the earlier of the remaining work deadline and a new interpretation window. The same interpretation_seconds also supplies the chat exchange budget. Scientific preparation can run inside a tool call under the work deadline; a late rejection cannot start another model request.
