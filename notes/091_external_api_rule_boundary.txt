Separate external API rules from operational code
================================================

2026-11-19 — proposed separation; implementation remains pending

Keep code that depends on an external API's rules in clearly owned areas. An API
change should lead maintainers to its validators and adapters, rather than
require searching through execution, delivery and recovery code.

Scope includes identifier formats, limits, field names and required structures,
allowed states and codes, routes, headers, signing rules, request/reply encoding
and the meaning of replies. Include inline checks and checks used only once.
The deciding question is whether the rule comes from the external API.

Put these checks in the validation package's upstream area, grouped by API and
supported version. Keep each API-specific constraint, its check and its rejection
diagnostic together. For example, a length limit on result_schema_id belongs to
that API field's validation; it does not establish a universal SDK text limit.

Keep API-specific request construction, signing, encoding and reply translation
in adapters: the code that connects SDK operations to that API. Operational code
uses those adapters and their checked results. It retains workflows, resource
ownership, locks, retries and cleanup.

First inventory the API-specific code, then move checks and adapter functionality,
update callers and remove the displaced implementations. Keep the external
contract definitions and selected versions unchanged during this separation.

Verify exact request bytes and signatures, response classification, and the
distinction between refusing before sending and losing a reply after sending.
Keep validation at the same points relative to parsing, locks and effects.

---------------------

separation or a claim that the listed tests pass. Application code was unchanged.
Production Python and shell entrypoints in packages/, operations/, host/ and

For SDK locations below, core/ means packages/provider-core/src/provider_core/.

Move API-derived checks into upstream validation and API-specific operations

Coverage and migration cautions
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- Existing contract tests authenticate fixture contents and exercise consumed
  rules; they do not establish live server compatibility or complete schema
  enforcement. Chat, store and tooling evidence is distributed across focused
  tests and donor references. Fill source/version gaps before changing rules.
  The sixteen pinned HTTP schemas contain no private signing-credential artifact
  schema; that artifact's documented API source is a separate authority.
- A source port from Magnet or SECS does not by itself establish an upstream
  contract. Local policies remain local even when borrowed from another project.
- No separate service-wire implementation was identified in the searched
  production examples/mocks. Their SDK calls and scientific schemas are callers
  and local models, not additional wire authorities.
- Copied validation enters the SDK wheel, wheelhouse zipapp and acquisition
  bundle through different offline build closures. The existing shared
  type-requirements source is a packaging precedent; moving checks must update
  each affected closure and hash manifest without requiring SDK installation
  during bootstrap.
  This inventory follows authored sources and build declarations; generated
  bootstrap bundles were not independently re-qualified or made new authorities.
- For each extraction, separate the upstream check/interpretation from the
  adjacent operation. Preserve parser-hook timing, exact signed/retained bytes,
  error classification, full original response evidence, and uncertainty after
  sending. Keep lock, custody, retry, file and queue decisions with their owners.
- Focused SDK lanes use TEST_PATTERN=test_<name>.py and PRIVACY_TESTS=0. Repository,
  wheelhouse, acquisition and deployment lanes cover the other consumers. Test
  names above are evidence pointers; this inventory did not execute those lanes.
