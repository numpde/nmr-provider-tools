Compose acquisition: functional refactor and completion checklist
================================================================

Branch: refactor/compose-acquisition
Base: 2d41b944eca481670362ab705514c2fa191ec0d5
Status: first tools-owner tranche implemented; API integration remains pending.

Priority gradient
-----------------
P0: working functionality. Run acquisition through Compose, return usable worker
output, consume it offline, and retire the operation. Complete one actual API
browser acquisition path before generalizing the design.

P1: required correctness. Preserve clean stdout, package exit status, selected
route, mapped identity, cancellation, and truthful cleanup results. Keep existing
callers working. A known failure of these contracts blocks completion; they are
part of functionality, not optional hardening.

P2: maintainability and reuse. Delete replaced mechanics in the migrated path,
keep package policy local, and document the working configuration for adaptation.
Do not require a new package, universal worker language or other repo migrations.

P3: targeted assurance. Exercise changed failure paths and representative supported
engine modes. Reuse existing tests for unchanged proxy/identity behavior. Tests
follow completed slices; they do not become a separate qualification programme.

P4: optional hardening. Extra engines, platforms, rare failure combinations,
storage redesign and performance tuning require an observed need and separate
scope. They do not hold this refactor open.

Excluded: validation fetish. No exhaustive package/engine/failure matrix, generic
Compose validator, duplicate dependency inventory, new retirement certificate,
periodic resource census or parallel package resolver. Every new check must name
the changed behavior and concrete failure consequence it protects.

Parallel assignments and integration order
------------------------------------------
Owner worker: common Compose definitions, sourced controller, scope integration
and generated bundle inputs. API worker: package overlay/caller patch and existing
end-to-end run sequence. Auditor: independently challenge owner duplication,
stdout/status preservation, actual consumers and unnecessary machinery.
Workers prepare isolated patches; the coordinator integrates and controls engines.

Owner implementation -> generated candidate bundle -> API refresh -> integrated
acquisition/browser run is sequential. API patch preparation and read-only audit
can overlap owner work. Test preparation can overlap implementation against the
specified contract. Runtime tests use a fixed source revision and isolated writable
state; serialize them when engine resources, caches or publication locks overlap.

Deferred P4 work
-----------------
Keep today's private temporary artifact staging. This refactor introduces no host
npm installation or reusable host node_modules cache, but does not eliminate host
scratch. Do not claim otherwise. No tmpfs prerequisite, engine volume or streaming
handoff is added. No additional engine/platform port or new distribution system
is required to finish this checklist.

Done means the actual API acquisition path works with the Compose owner, existing
callers remain usable, required failure behavior is honest, and the implementation
is understandable enough to adapt. More assertions are not a completion goal.
