Testing shared execution and provider migration
===============================================
2026-11-08 | Historical source review and supporting test guidance
Revised 2026-11-09 | Order and priorities: 065; target design: 066

Purpose
-------
Build the useful shared package, with focused tests alongside each feature.
Permission checks, correct ownership and resource limits belong in the first
implementation. Broader generated tests and test infrastructure follow need.

Note 065 sets priorities and replaces the old test-every-service-first sequence.
Design the shared package for SECS, NMRNet, NMRPeak and Magnet together, with
interfaces future scientific implementations can use. No provider sets the design
or has a prescribed first place. First implement the shared contribution and
execution interfaces in provider-core and all four provider repositories. Their
actual scientific and guarded execution paths must use them. After that common
boundary is in place, pools, services and provider internals can improve in
separate runnable increments. Tier 0 still includes useful local pools and the
common service for all four; adopting the interface alone does not complete it.
This note preserves historical source review and safety rules, not new run or
release claims. Results in 058/060/061 apply only to their named revisions and
artifacts; 065 records the current source map.

Control faults through observed events, such as the original operation stopping,
rather than guessed delays. Test deadlines and Retry-After separately. Reuse
existing runtime code, publisher and fixtures, including Magnet's fixes below.

At the reviewed revision, Magnet's outage test restores service after two
original controllers have settled and released their claims. It checks requests
and refusals for both failed Jobs, then requires a later Job to succeed. It no
longer uses the fixed 2.8-second outage or 0.2-second cooldown probe present at
the earlier review, 1bdd01e. Cooldown observations come from the parent event
sink and each actual START. A watchdog bounds each wait for settlement while
checking that a finite backlog finishes. Reuse these changes; test the revision
being adopted before claiming that another consumer has them.

Who owns what
-------------
1. provider-core owns transport/process lifetimes, Interpreter, AttemptController,
   AttemptClaims, permission, retained reports and publication. Tests follow code.
2. Announcing offerings, finding and accepting Jobs, pacing requests, observing
   active work and shutting down move into the shared service under 065/066.
3. Scientific code interprets inputs/configuration, initializes/disposes of models,
   prepares data, computes and defines results. It declares capabilities and
   resource needs. AnalysisSession is the current integration API, not a required
   numerical signature. The shared host/service manages workers and scheduling.
4. RunnerSession/AsyncRunnerSession stay in the SDK. Retain actual worker-exit and
   resource-release tests. Provider-specific streams, readers and loaded-worker
   reuse can stay behind backend bridges until a concrete shared replacement
   exists. They implement the common execution contract; scientific functions
   do not acquire process-management responsibilities.
5. Deployment, identity and image tooling remain separate from service tests.

The execution client is scoped to one analysis. It may submit, observe and stop
that analysis's operations and close its scientific state. Retiring a shared
instance belongs to the pool's administration interface. A loaded scientific
instance, scientific state for one analysis and a prepared value have different
lifetimes; per-analysis state may exist before preparation succeeds.

Deployment records configuration and assets in an immutable configured binding.
The host loads its factories and scientific hooks; the scheduler sees
plain descriptions of calls and requirements, not callables or scientific objects.
Accepted work keeps its binding revision when a deployment alias changes.

Adapters do not add a poller or shutdown loop. No provider-name branches or
mandatory class hierarchy are needed. The current process-local registry prevents
duplicate ownership of a Job within the scope it manages. It is not a distributed
lock. An available worker does not grant execution permission.

Keep different events separate
------------------------------
A single ready flag cannot describe all of these:

- The server accepts START; the client receives the matching permission.
- HTTP bytes arrive; the parent interprets that exchange's result.
- Input is selected; the interpreter retains its result; the session accepts a
  PreparedAnalysis or worker validation handle; scientific work actually starts.
- A scientific call returns; the host retains that return and any new state;
  encoding succeeds; a result becomes available through its exact ResultRef.
- A model HTTP exchange stops; computation stops; the worker exits; input files,
  access grants and scratch space can be released.
- A final result is selected; reporting is resolved; the Job claim is released.
- The local durable queue accepts a report; the Jobs API publishes it; the queue
  removes it. A local acknowledgement proves neither worker exit nor publication.
- Execution releases a retained ResultRef; analysis cleanup finishes. Output
  files must survive cleanup until their result's independent custody ends.
- shutdown_ready becomes true; all claims disappear. These are not equivalent.
  A retained record may still exclude a Job while shutdown is safe. An active
  worker or a selected report awaiting acceptance cannot be treated as such an
  inactive record.

A claim is the registry record that prevents another owner from taking the Job.
SupervisedChatTransport owns one active exchange. Concurrent operations need
separate transports, interpreters and controllers, using the appropriate shared
claim registry. ProseService may share backoff for work using the same configured
model service. Keep announcement, discovery, observation, input acquisition and
report delivery independent where they must progress at the same time.

The current registry limits live entries, control bytes and pending report bytes.
Local delivery acceptance can free report capacity while the original operation
still owns resources. Recording its acknowledged Attempt identity does not create
a second live entry. These limits do not replace accounting for actual workers
and their memory or compute use.

Safety and progress rules
-------------------------
A worker generation identifies one particular worker instance. A prepared handle
that refers to its state stays tied to that instance; restarting a worker under
the same name does not make the old handle usable there.

Registered calls declare named state arguments and whether they borrow or consume
each one. Requests supply the references, not new access rules. Borrowing alone
does not make state immutable or concurrent use safe. An accepted or uncertain
operation retains its claims; consuming a reference does not prove that the
underlying resources have been destroyed. Note 066 specifies these contracts.

S1. Another operation may reuse a resource only after the original owner confirms
    that its operation and prepared handle are safely inactive, or that the
    worker has fully stopped, as that resource requires. The confirmation must
    identify the exact resource and worker generation.
S2. An operation cannot release another operation's claim, transport, input,
    prepared handle, report or worker allocation.
S3. A cancellation request, closed socket, sent signal or expired observation
    timeout does not prove that work has stopped or resources are safe to release.
S4. Expired or confirmed revoked permission cannot allow new scientific work.
    Check permission immediately before the effect, including after intervening
    awaits. An earlier check does not reserve permission for later use.
S5. Keep accepted preparation and its original evidence owned when cleanup fails.
    Keeping them does not permit execution after permission is withdrawn.
S6. Recovery must not repeat accepted scientific work or work whose outcome is
    unknown. Explicitly rejected input may be corrected. A separately authorized
    scientific retry must satisfy its original-worker cleanup, identity and
    resource/time-budget rules.
S7. Select at most one logical final decision for an Attempt. Permitted delivery
    retries keep the same operation, exact bytes and idempotency key.
S8. A late event from an old owner cannot change its successor's state or evidence.
I1. Independent work progresses when its resources, permission, shared capacity
    and configured continuation policy allow it.
I2. One operation's failure cannot corrupt another's deadline, status, claim,
    accepted preparation, report or delivery state.
L1. The original owner can finish its duties when the required cleanup is
    confirmed and a valid execution/reporting decision is available.
L2. Freed capacity allows eligible work when its worker is ready and the other
    conditions for accepting it are met.
L3. Shutdown completes when all required cleanup and report handoff duties finish,
    following the documented rules for safely retained inactive Job records.

Progress assumes external replies and exit observations eventually arrive and
tasks receive CPU time. Tests cannot promise progress under permanent missing
replies or arbitrary starvation. Physical cleanup alone neither justifies a FAIL
report nor resolves uncertainty about whether START was accepted.

Today, AnalysisSession bindings perform required S4 checks. Keep them until
equivalent checks in the shared host are implemented and tested. Numerical
functions need not receive Attempt authority or controller objects.

Provider facts at the reviewed revisions
---------------------------------------
These describe old code, not limits on the new architecture. They do not require
an exhaustive review or test run of all old services before useful new work.

SECS has one resident worker and stops accepting Jobs while an old owner still
holds it. After a normal operation the worker may be safely reused without exiting.
An abandoned prepared handle or an uncertain request may require worker exit
before releasing input files. An explicit input_rejected response allows corrected
preparation. Track the accepted handle and its use, not just prepare-call counts.
The production controller reads verified Job input after START; do not add a
second read merely to imitate another provider.

NMRNet retains verified upload bytes and owners for input readers, geometry
preparation, worker setup and prediction. Selected input is not yet an accepted
SDK handle. Its configured zero-or-one prediction retry requires all of:
a validated ModelCallFailed reply, confirmed exit of the original worker,
continuing permission, the same frozen request batch, a matching replacement
runtime and the original total budget. Losing a reply leaves the outcome unknown
and permits no retry. An allocation used only to test cleanup does not show that
scientific work was submitted.

NMRPeak has separate loaded HF/CHF workers, with shared discovery, capacity limits
and delivery pressure. Confirmed completion can make a worker reusable without
exiting. Explicit validation rejection permits correction; unfinished validation
or an accepted handle cannot simply be submitted again. Typed input requires no
model HTTP request. A failure can currently stop all work using that API connection.
The shared service may narrow that effect; test that unaffected work completes.

Magnet supplies different scientific implementations with their own readiness,
version and failure policies. Its existing independent-lane tests do not justify
putting E01/E02/G01 names or its status-board API into generic shared code. Move
tests for accepting Jobs and shutting down with the service implementation.

How to test without building another framework
---------------------------------------------
Start with existing fixtures and deterministic tests for the feature being added.
For generated tests later, distinguish chosen actions, observed events and expected
state. Calculate expected ownership independently; do not copy runtime branches
or read mutable runtime state to decide what the answer should be.

Record the necessary source, event kind, known operation/resource identity and
collection order. Add owner/generation where late events could be confused, and
monotonic timestamps when timing matters. Never assume the nth HTTP request
belongs to the nth START.

Collection order is not execution order across processes. Use actual interactions:
a request precedes its reply, and the parent must observe and accept the reply
before the test relies on it. Delayed logs cannot establish child-exit time.
Keep chosen actions separate from observations so failures can be reproduced.

Observe facts at their owners: API acceptance, interpreter decisions, scientific
entry, local report acceptance and original-controller completion. Prefer existing
structured events to log parsing. Test observers must not grant permission,
release claims, clear backoff or restart science to manufacture success. General
event APIs, reference models and shrinking demonstrations are not entry gates.

A watchdog may cancel its disposable waiter, not the operation being watched.
Retain original owners and check their failures even if an event arrives at the
same wake-up. Decide pass/fail and capture diagnostics before emergency cleanup
releases gates or kills children. Cleanup cannot supply the successful outcome.

Different tests establish different things
------------------------------------------
Choose evidence for the changed behavior, rather than a ladder every feature
must climb:

A. Generated SDK tests, added when useful.
   Reuse real interpreters, supervised transports, controllers/executors and
   claims, with two operation slots and small limits. Control external replies,
   science completion and delivery. Explore relevant orders: lost replies,
   uncertain START, late cleanup, permission changes, accepted preparation,
   lost acknowledgements and shutdown.

   Use one managed event loop per Hypothesis example; a new loop per action can
   cancel the work being tested. Preserve useful failures as named regressions.
   Simulated time requires consistent simulated clocks. Generated commands do not
   control internal asyncio or child scheduling. Check reached events and improve
   shrinking/replay for concrete failures or claims. Keep the existing stateful
   outbox test; a new generator alone does not justify replacing it.

B. Real-process tests for exit and resource release.
   Reuse tests/fakes/b3_provider_shutdown.py and its creation, cancellation,
   signal, repeated-observation and exact-exit gates. Use real processes, IPC and
   monotonic time. Withholding observation of an exited child tests missing exit
   evidence; it does not simulate an unkillable child.

   When adding shared pools, use small real-process examples drawn from all four
   providers' different needs: reuse a loaded worker, create separate per-analysis
   state, retain a prepared handle on its worker, finish a result produced in
   stages, and run different implementations together. This follows the initial
   interface adoption across the actual providers. Examples check new shared
   machinery; they do not replace that adoption or establish real-model behavior.

C. Actual provider integration when migrating or releasing that provider.
   Use the real adapter and production assembly path. A recording fake does not
   test a native protocol; scripted processes do not test a deployed model.
   Shared SDK tests do not replace a check of the consumer's worker connection.

   For the first coordinated interface change, use focused checks in each
   repository's existing lanes. Its actual scientific adapter and existing
   guarded backend route must use the new contracts. An unused Protocol, alias
   or separate demonstration is insufficient. Preserve preparation correction,
   portable input or worker-bound state as the implementation requires. Select
   checks for the changed behavior: separate per-analysis state from prepared
   values, enforce declared state use and prevent one analysis from retiring a
   shared instance. Where encoding or output files are involved, retain the
   scientific return on encoding failure and keep output usable after analysis
   cleanup until its exact ResultRef is released. Releasing that result is an
   owned, idempotent operation, separate from local report acceptance or central
   publication. No new validation phase or exhaustive old-service campaign is
   needed.

For independent progress, hold A's original cleanup observation, let B finish
on separate resources, then supply A's evidence. Use a valid release case such
as confirmed pre-entry revocation followed by settle_revocation. Also test that
unresolved Job state can require retaining a claim after cleanup. A successor
starts only when allowed. Test accepted preparation separately; do not invent
another model turn after ToolFinished has ended interpretation.

A supervised chat exchange keeps its original fixed cleanup allowance. API,
upload and delivery callers may have bounded budgets for observing the same
operation again. Neither rule becomes a universal timeout policy.

Useful consumer tests
---------------------
Use existing files. Keep scientific meaning and ownership checks when changing
assembly; replace assertions about old topology when the new behavior improves
it. Select affected scenarios rather than running this whole inventory upfront.

SECS: reuse test_sdk_runtime_drain.py, test_sdk_session.py, native_worker tests
and the end-to-end fixture. Check safe failure followed by next-Job readiness,
accepted-handle/input lifetime during interruption, and exact report handoff
through stop. The reviewed e2e fixture manually builds ChatEndpoint with
HttpTransport. Use production ChatEndpointFactory to test supervised-child wiring.
A pending durable queue row proves local storage, not final API publication.

NMRNet: reuse service_ports.py, runtime_ports.py, retirement_ports.py and native
session fixtures. Keep verified bytes through interpreter interruption and retain
late worker setup/cleanup under the original owner. Preserve exact report bytes
through delivery pressure and stop. Keep scientific-retry and result-format tests
local; replace private task/call-order assertions when their code moves.

NMRPeak: reuse test_shared_provider_process.py and test_native_runner_session.py.
Keep typed-input bypass, ownership of validation and accepted handles, and the
separation of report acceptance from cleanup. Keep stop/lost-acknowledgement tests.
The reviewed held-cleanup test calls _select on another lane; it does not show
that lane finishing under the running service. Test actual independent completion
when adding that behavior. Keep tests for reuse of a loaded process and its final
exit. Note 060's extra prose-stop tests belong to a separate test revision.

Magnet: retain event-controlled outage, finite-backlog and independent-lane tests.
Add shared observation helpers only where consumers use them. Replace remaining
status-file polling with observation of the actual held operation, and check
normal shutdown before test cleanup. In a later deployment test, hold E02 while
E01 completes and G01's earlier report is published. Actual process IDs, model
loads and API publication need evidence from that deployment test.

Do not claim that old SECS already had spare independent workers, old NMRNet
preserved a warm process, or old NMRPeak kept unaffected work running. Show the
new one/two-worker behavior directly. Old limitations are not design requirements.

Test packaging and longer runs
------------------------------
The SDK source archive already contains helpers. NMRNet's
tools/provider_consumer_tests.py verifies its checksum, copies allowed support
files, verifies the installed SDK location and excludes shared SDK tests/source
from consumer discovery. Extend this route when two real consumers need a helper.

Keep Hypothesis and pinned test dependencies outside runtime/native installs.
Do not import a sibling checkout. For release or candidate comparison, identify
the actual runtime wheel, support archive and provider revision. Reuse packaging;
new support files/interfaces need a concrete consumer.

Keep the small generated profile. Longer runs, repeat quotas and CPU-contention
tests follow specific risks; they do not gate features. Configured run sizes are
not executed evidence. Faults follow observed events. Dedicated timing tests check
deadlines and Retry-After: server arrival times alone cannot prove dispatch waited.

Bound repetitions and retain failures; never retry until green. Report the missing
event instead of resetting watchdogs on log chatter. Load can legitimately cause
a deadline to expire; do not hide that by raising every timeout.

Migration and completion
------------------------
Follow 065: implement the lasting contribution and execution interfaces in the
shared package and adopt them in all four repositories first. Both the real
scientific calls and their existing guarded backend routes use the boundary.
Keep existing permission checks until equivalent host checks work and are tested.
This is a coordinated set of runnable commits, with no privileged provider and
no requirement for one giant commit.

Then improve providers, shared pools and the common service independently behind
those contracts. Complete direct/hosted one/two-worker operation and the useful
service for all four within Tier 0. Actual model or deployment claims still need
the relevant run; interface adoption does not establish them. Compare old/new
code on the same candidate only for a concrete risk. Never run two live schedulers
under one provider identity.

Deliver working increments. Keep observing original work when capacity is full,
no new Jobs are accepted or no offerings are announced. The first shared design
allows independent progress and applies retry delays to affected work. Move tests
with their code, remove duplicates and replaced local paths, and keep scientific
and native tests with small consumer scenarios. Add focused tests for changed
behavior; broader test infrastructure follows need.

Before deployment, stop the old service accepting Jobs, then finish its duties or
confirm their durable transfer. A timeout does not transfer an in-memory Attempt.
Keep the outbox and publisher. Death before durable handoff remains separate
recovery work in 065/066. A hash cannot reconstruct report bytes or authorize
repeated science.

Generic service changes should live in shared code and its tests; consumer tests
still exercise real adapters. New providers supply science, requirements and a
small integration test, without another poller or shutdown loop.
