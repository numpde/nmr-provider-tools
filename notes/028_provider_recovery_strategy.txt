Provider recovery strategy
==========================

First milestone: API recovery budgets
-------------------------------------

Use the existing SDK recovery loop for Attempt observations and condition
publication. ObservationRecovery.gap_seconds is the whole fresh-observation
budget, not an initial retry delay. ConditionRecovery.window_seconds begins
when the first condition PUT fails and bounds retry dispatch and pacing; the
initial PUT and a final in-flight exchange and its retirement can extend the
total time. Pass both policies by keyword and keep their budgets distinct from
retry pacing. Initial backoff uses the lesser of the poll interval and backoff
cap; subsequent delays use capped exponential backoff with jitter and honor
Retry-After.

Choose budgets against each deployment's actual exchange and retirement
allowances, leaving useful retry opportunities. A longer observation gap can
delay detection of cancellation or loss of fresh state. NMRPeak's old setting
called an initial retry delay was actually the entire observation and condition
recovery budget; in the investigated deployment it was shorter than a single
exchange. Its fix names the gap explicitly. NMRNet already has separate budgets;
SECS needs both SDK policies wired in. Check Magnet against its actual transport
and confirm each provider's running configuration after cutover.

Prove the same controller resumes the same Attempt after a transient outage,
with one generation submission and no duplicate terminal handoff. Exercise
condition retry and its matching receipt separately. On exhaustion preserve
uncertain effects and do not infer that the Attempt settled. Keep live host
configuration, private identifiers and scientific payloads out of this note.

Later work: failure isolation
-----------------------------

A Job failure must not stop unrelated Jobs. The API expires abandoned Jobs.
For a positively acknowledged Attempt with no undelivered result and retired
local work, the desired path is to log the outcome, release local capacity and
continue; no provider-side recovery queue is needed. Current SDK operation
settlement does not release its separate Attempt claim, so that disposition
needs shared ownership and proof. An uncertain START, undelivered result or
unretired resource is a different case; retain the actual owner as necessary,
without blocking independent available capacity.

Fresh API feed queries exclude Jobs with an existing Attempt for that provider,
regardless of Attempt state. Before releasing the local exclusion, establish
whether stale buffered pages, API consistency and Attempt retention could select
the Job again. NMRPeak's simulated stale-page witness shows a new selection is
possible after a hypothetical release; it does not establish that the real API
or current SDK permits that sequence. SECS's newest-first, first-page discovery
can also starve older Jobs; fairness is separate follow-up work.

Interpreter availability needs capped backoff and one budget across rounds;
its disposition must not turn an outage into a scientific failure. Persistent
shared outages should be paced and recover automatically where possible. Do
not halt a provider merely because individual Jobs fail; reserve a halt for an
established provider-wide condition and define how it clears. These scheduling,
interpreter and systemic-failure changes are separate from the first milestone.
