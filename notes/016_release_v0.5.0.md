# provider-core 0.5.0

This release adds shared native-session adaptation, bounded source recovery and private API route tooling. Providers still own scientific preparation, inference and model policy. They can use `DeliveryClient` without adopting the execution controller. See the [package documentation](https://github.com/numpde/nmr-provider-tools/blob/v0.5.0/packages/provider-core/README.md) for the contracts and integration points.

Controllers now retain their original lifecycle task. Cancelling a `run()` or `join()` wait ends that observation; it does not stop the lifecycle. Request stopping explicitly, join the original task, then settle remaining obligations while preserving any passive held Job exclusion. A separate admission-stop event can stop new START requests while admitted work drains. Selected reports still require their original delivery handoff. Use `shutdown_ready`, together with every other resource owner, before ending an orderly supervisor lifetime.

`AsyncRunnerSession` keeps native setup and retirement observation off the event loop while retaining their original operations. An expired observation wait does not authorize another reader. Unexpected process-control exceptions and independent cleanup failures remain available to protected diagnostics; they do not authorize a scientific failure report. An uncertain lifetime-descriptor close stays uncertain and is not retried against a potentially reused descriptor.

`JobUploads` can opt into `UploadRecovery` within its original request, byte and time limits. Recovery requires the current failure to qualify and its original resources to retire. `UploadRecoveryExhausted` identifies that specific settled outcome and retains the current outage as its cause. One-shot callers keep their existing behavior. Take ownership of a returned verified source before reporting recovery diagnostics. Exhaustion alone does not release a held Job or grant permission to rerun science.

`HttpTransport.exchange_decoded` applies finite wire and per-stage decoded limits under the original exchange owner. Its identity, gzip and deflate profile rejects unsupported, incomplete or trailing data. Complete concatenated gzip members are supported. The bounded profile can reject valid metadata-heavy encodings and ambiguous raw-deflate prefixes; it does not promise HTTPX-equivalent acceptance. Direct model HTTP requires explicit opt-in and cannot use the proxy. Raw exchanges and signed API HTTPS verification retain their existing roles.

Shared deployment rendering supplies the selected binding's API proxy, read-only client socket grant and dependencies. Single-binding providers can request stable `api` and `api-init` service names; shared delivery keeps its per-binding names. The binding remains the authority for destinations, TLS and resolver inputs. Unspecified destinations and local routes that point into the wrong loopback namespace are refused. Render with the actual runtime UID/GID and preserve ownership checks during replacement.

Python 3.12 or later is required. API, delivery, chat and HTTP consumers must declare `provider-core[api]` or use the full issued installation lock: 0.4.0 installed those dependencies automatically, while 0.5.0 makes them optional. The native-only lock supports the dependency-free native interfaces. GitHub assets include the wheel, source distribution, both hash installation locks, source record, hash manifest and qualification logs. Earlier published assets remain unchanged.

Qualification checks installed packages, source rebuilds, bounded decoding and source recovery, native ownership, and disposable private API routes. Consumer checks and scientific CPU comparisons have their own recorded scope. These results do not establish GPU behavior, canonical consumer-image adoption or production rollout. Acquire verified release assets through each repository's ordinary build path and qualify that exact consumer image before claiming deployment.
