How the shared provider platform should work
=============================================
2026-11-09 | Target design | Runtime reviewed: SDK 1178115

Purpose and status
------------------
Providers supply the science. Shared code runs the service: finding work, deciding
when it can start, running it, reporting results and stopping safely. The number
and location of workers should be configuration choices. The same scientific
code must run with one worker or several.

Design the boundary for SECS, NMRNet, NMRPeak, Magnet and future contributions
together. No provider defines the default architecture. Small adapters connect
their numerical functions to the common host; the scheduler has no provider-name
branches. Note 065 maps the existing implementations to this boundary.

This is the target, not a description of a finished platform. The runtime review
was at 1178115c8b1ea89556f4c04f73d69471be8e1b5f. Note 064 records the provider
versions reviewed; it does not identify what is currently deployed. Earlier test
results apply only to their named versions and files.

This note replaces the older assumption that extraction should preserve each
provider's worker layout. Note 065 gives the implementation order. The safety
rules S1-S8 in 064 still apply. Keep scientific meaning and real ownership of
work; replace unnecessary polling, worker and failure-handling restrictions.

Build a useful local service first, then broader capabilities and recovery, then
measured performance improvements. Add focused checks with each change. Broad
fuzzing, test frameworks and stress campaigns must not delay that useful service.
Section 9 defines the tiers. A plan alone does not authorize release or deployment.

1. The things we need to distinguish
-----------------------------------
These terms describe responsibilities; each does not need its own Python class.

Offering: an analysis available through the Jobs API, including its input schema
and the conditions under which it may be used.

Implementation: a particular scientific program, its settings, preprocessing and
any model files it needs. Record the exact version, files and settings that affect
its results.
Switching to a different model or numerical policy requires an explicit scientific
choice; infrastructure must not silently make that choice after a failure.

Execution backend: how shared hosting starts and watches work. Start with local
isolated workers. A remote service can be added later under the same rules.

Allocation: a particular worker or other assigned resource, such as a device
partition or remote slot. Identify the actual instance, not just its name: a
restarted worker is a different instance. Several allocations may run the same
implementation. Compatible work may share physical capacity, but per-job mutable
state remains separate.

Reservation: capacity held for a particular owner and phase. Available capacity
is not a reservation, and a reservation is not permission from the Jobs API to
start science. Track who must release it, including after partial acquisition.

Operation: one submitted preparation or computation. Track its identity, input,
implementation, exact worker instance and permission. Provider work also records
its Job Attempt; direct hosting does not require a Jobs service. Checking status
again does not create another operation. An Attempt may contain several operations.

Prepared analysis: the accepted scientific input or state needed for computation.
Immutable input may be portable. A handle into a live worker must stay with that
exact worker instance until used or safely discarded. Having input bytes does
not permit repeating work that may already have been submitted.

A lane can be a useful scheduling or status view. It must not permanently bind
one offering to one worker or one job.

2. Who does what
----------------
Scientific contribution
  Decodes and checks scientific input, supplies tools, prepares and computes
  results, and defines what those results mean. It supplies any needed model
  initialization and cleanup, scientific settings and model files. It declares
  resource needs, compatible environments, worker-bound state, supported batching
  and permitted scientific retries.

Shared service in provider-core
  Announces offerings, finds a bounded amount of work, schedules it fairly,
  manages Job Attempt permission, maintains existing work and drains on shutdown.
  It selects a registered implementation and passes input bytes or a reference
  without interpreting them. It supplies operation identity, reserved capacity,
  deadlines and limits. It does not select checkpoint files, construct tensors
  or understand peaks and molecules.

Shared host and execution backends
  Manage worker pools, start operations, communicate with workers, supervise
  cancellation and establish when work and workers have actually stopped. The
  host calls scientific initialization and analysis functions and keeps their
  operational records. It enforces permission without handing controller internals
  to science. A temporary protocol adapter may translate an old worker interface;
  it must not hide another scheduler, pool, retry loop or shutdown mechanism.
  Reuse existing native-runner supervision when needed. Contributions that can
  run directly need no artificial native protocol, checkpoint or validation phase.

Deployment tools and operator configuration
  Provide images, files, identities, device limits and permitted files, sockets
  and network access. They bind approved scientific settings and model files to
  the implementation. Shared tools may fetch and verify files; scientific code
  understands their formats and compatibility. Operators choose pool limits,
  placement and approved backends. Privileged Docker and host access stay out of
  scientific code and the service loop.

Result delivery
  Keep the existing outbox (the saved report queue) and publisher. Science returns
  a result or scientific failure. Shared code associates it with the Attempt and
  constructs the exact final report. Acceptance into the local durable queue and
  publication to the central API are separate events. Queue acceptance means
  the report is saved so it survives a restart.

These owners can run in separate processes and packages. The common runtime
must not import every scientific framework. The execution interface may be a
Python call, IPC or a network call; it is a responsibility boundary, not a
requirement to add another network service.

3. One implementation, one or several workers
--------------------------------------------
Support a fixed local pool first. Changing its size must not change scientific
source code. The pool owns worker startup, readiness, assignment, health, drain
and shutdown.

Count memory used by loaded models separately from active computation. Also count
workers still starting, draining or of uncertain status. An operation may retain
input files, scratch space or a device after its caller stops waiting. Those
resources remain occupied until the responsible owner establishes otherwise.

A worker must match the implementation, any model, runtime, device and isolation
requirements. Its model name alone is insufficient. Do not create an unlimited
stream of replacements for an unconfirmed worker. New work may use a separately
budgeted replacement, but the old operation remains owned and is not repeated.

Several independent workers, several simultaneous operations inside one worker,
and batching are different capabilities. Begin with independent workers. A
serial worker protocol stays serial within each worker until it is changed and
checked. Later, use measurements to decide whether keeping idle models loaded,
resizing pools or batching is worthwhile.

Batching is optional and needs scientific support. Preserve each member's input,
Attempt, result, permission, cancellation and failure. Cancelling one member
must not resubmit another. If a running batch cannot stop one member separately,
that member's resources remain occupied until the batch finishes. Sharing batches
across tenants requires an explicit isolation policy. Check numerical equivalence
when adding batching; an implementation need not support it.

4. Reserve resources when they are needed
-----------------------------------------
The service finds work, accepts it, prepares it when needed, computes a result,
retains the result, hands it to delivery and completes remaining duties. Keep
these steps within the same Attempt; no general workflow language is needed.

Tier 0 may conservatively reserve the resources needed for the whole analysis.
Tier 1 separates those reservations by phase. Waiting for a prose-model HTTP
reply should then leave unrelated GPU capacity available. Preparation that
actually uses a GPU declares that need, and a worker-bound prepared handle may
require keeping its worker reserved until computation finishes.

Bound waiting work by count, bytes and time, including retained source files and
prepared inputs. Acquire multiple scarce resources together or in a defined
order so two tasks cannot each hold a resource the other needs. Cancellation
must release any partially acquired resources once they are safe to release.

Before START, reserve enough control, preparation and report capacity and a
bounded route to execution. Do not accept an unlimited backlog. Readiness is only
an observation: shared hosting checks current permission and the reservation
immediately before each managed submission, including after an await. Already
submitted work remains owned if permission later changes.

Begin with simple fair scheduling and bounded discovery pages. Add cost estimates
or priorities only when needed. Capacity limits must cover all implementations
sharing a device. Across processes, use a common allocator or enforced resource
assignments that cannot overlap. Separate counters cannot safely reserve the
same GPU.

5. Track what is running, what occupies resources and what remains unresolved
----------------------------------------------------------------------------
Keep Job/Attempt permission, active control tasks, occupied resources, staged
input bytes and retained final reports distinct. Use the existing Attempt
registry; do not create a second authority for the same Job. Each outstanding
duty has one owner.

In the target design, a stopped but unresolved Attempt can remain excluded from
being accepted again without occupying a proven-free GPU forever. Its record still
needs bounded storage. Conversely, an unconfirmed native operation still counts
against capacity even after its Python task or observation deadline ends.
Calling it quarantined does not establish that its resources are free.

Today, settle_revocation correctly keeps the original claim for some revoked
Attempts that have passed the SDK's entry checkpoint. Passing that checkpoint
alone does not say whether a scientific effect occurred.
Keep that conservative rule until a stronger replacement is implemented and
checked. The replacement should combine authoritative API state with the backend's
records of submission, completion and cleanup, and return a clear decision about
what to retain or release. It must not invent FAIL or erase an earlier operation.

Limit a failure to the part actually affected: one operation, one worker, an
implementation or service connection, a delivery credential, a device, or the
host itself. A failed worker need not stop healthy siblings when they have
independent resources and trustworthy ownership records. A shared-device fault
or corrupted supervision may require a wider stop. Do not label an arbitrary
exception local merely to keep running.

Maintain original operations, result delivery and cleanup even when new jobs
are refused, offerings are withdrawn or there is no spare capacity. Settle work
when the required evidence arrives. If it cannot settle, explain what is missing
and the supported operator action. Tier 1 improves automatic recovery; Tier 0
may safely retain unresolved work and require explicit intervention.

6. Recover after the supervisor dies
------------------------------------
The current SDK keeps live Attempt state in memory; a supervisor crash can lose
that state and results not yet handed to durable delivery. Tier 0 keeps this
limit explicit, supports orderly drain and never treats restart as permission
to repeat possibly submitted work.

Tier 1 adds durable operation and result records. Before submission, save the
operation's stable identity and owner. A supporting backend must recognize a
repeated command for that identity, retain status and result information, and
let a replacement supervisor reconnect. Keep the exact selected final report
until durable delivery confirms that it has accepted responsibility for it.

Check crashes separately around submission, acceptance, completion, result
storage and delivery handoff when implementing this recovery. If the backend
cannot establish whether work was submitted, retain that uncertainty and refuse
automatic duplicate science. Deduplicating messages alone does not establish
that computation ran exactly once.

The receiving backend must reject commands from an obsolete supervisor. A local
generation label or expired lease does not stop the old process from running.
A remote backend also needs authenticated permissions, bounded communication,
resource ownership and a defined response to network partitions and reconnection.
These are requirements for the corresponding recovery/failover feature, not
prerequisites for the first local service.

For upgrades and rollback, send new work to the selected pool while old owners
finish or transfer their existing work safely. Preserve queued reports. Do not
move a prepared handle to an incompatible worker or let an old supervisor alter
its replacement's state.

7. The boundary between orchestration and science
-------------------------------------------------
There are three separate interactions:

  Registration/deployment -> host: configured science and its permitted resources.
  Service -> execution interface: identified work, reservations and limits.
  Host -> scientific functions: implementation-specific setup and scientific input.

The service asks to run work X with implementation Y within reservation Z. It
receives a way to observe that operation and obtain its result. The host retains
the operational identity and permission; these do not need to become arguments
to numerical functions. No large scientific-context object is required.

7.1 Where the inputs come from

Scientific input
  For provider work, comes from the Job and its permitted sources; direct hosting
  can receive scientific input without a Job. Shared transport authenticates,
  fetches and limits the bytes or references. The contribution decodes and checks
  their scientific meaning and constructs numerical input. The service can route
  these bytes without inspecting peaks or tensors. A hash identifies bytes; it
  does not establish that the data are scientifically valid. Fetching and decoding
  may be deferred, but their resources still need an owner.

Scientific settings
  Come from the versioned implementation or explicitly permitted per-job settings.
  Deployment binds them; the contribution validates them. The service selects the
  registered implementation and may carry settings without interpreting them.
  It does not choose precision, preprocessing or defaults. Record changes that
  affect scientific results; do not silently reuse an incompatibly configured model.

Model files
  Are declared by the contribution and installed, mounted or fetched by authorized
  packaging/deployment tools. Shared code checks file identity and source.
  Scientific initialization understands the checkpoint format and model
  compatibility. Model files need not travel with every Job. The scheduler does
  not choose them, and a load failure does not permit substitution of another model.

Device and runtime environment
  Come from the assigned resources. Hosting exposes only what the implementation
  needs. Scientific initialization creates framework-specific device and model
  objects. The service never passes such objects. Science declares its needs;
  it does not choose among global devices, discover hosts or create worker pools.

Operation identity
  Is managed by the host/backend to match replies and results, reject stale owners
  and detect duplicate submissions. Science may receive a diagnostic token when
  useful, but it does not need Job/Attempt objects or permission to manage them.
  Batch results must still be associated with the correct members.

Progress and cancellation
  May be small optional interfaces: a progress sink or a cooperative stop signal.
  Shared code translates progress into approved events and rejects stale reports.
  Science does not call the Jobs API, decide whether an Attempt is active or
  authorize a replacement. A stop request, a returned function and an exited
  worker are different facts; lack of cooperative stopping remains an explicit
  implementation/backend limitation.

7.2 Instance setup and one analysis

Keep the scientific adapter small. Initialization binds settings, assets and the
permitted environment to an instance. The required run operation accepts input
directly, or a prepared value if the contribution explicitly supplies a separate
prepare operation. Provide cleanup where analysis or instance state needs it;
stateless contributions need no dummy cleanup hooks.
Adapters leave numerical functions unchanged; no universal workflow or call
registry is needed. Optional preparation does not remove input checks that
the scientific implementation requires.

Initialization may load a reusable model or retain settings for loading during
execution. A contribution may need no model at all. Separate mutable analysis
state from instance state, and keep unfinished initialization or cleanup owned.
This covers worker-bound accepted state in SECS/NMRPeak, lazy iteration, tensor
preparation and per-analysis models in NMRNet, and Magnet's one-call G01 and
optional native execution. These are supported shapes, not provider-name cases
inside hosting. Future contributions use the same boundary.

Hosting records which exact worker instance owns a prepared native handle.
Science uses that state; the handle itself carries no execution permission.
Portable input and discarded handles do not authorize repeating an operation.
An iterator or queued device operation is not yet a completed result. The adapter
finishes the required lazy work and device synchronization before reporting final
completion. Work still in progress remains an owned operation, not a final result.
Input sources stay owned until their readers finish. Scientific cleanup and
confirmed process or resource retirement remain separate; a returned function
alone proves neither.

7.3 Check permission where work is submitted

The host or compatibility binding checks current permission immediately before
each managed scientific submission, including a tool call after an await. It
continues to own work already submitted when permission is withdrawn. Algorithms
may iterate or sample within their authorized operation and budget. Submitting
another operation requires a new managed permission check.

Numerical functions must not receive AttemptController, AttemptClaims,
ProviderAPI, ReportCondition/report_condition, Jobs credentials, the global
allocator or Docker access, including through nested catch-all arguments.
Cooperative cancellation is not a way to pass them that authority.

Existing AnalysisSession.prepare/execute/retire bindings currently receive SDK
objects and perform required permission checks. Preserve those checks until
equivalent host-managed checks are implemented and shown to work. These bindings
translate verified Job input and scientific results into the SDK contract; they
are temporary integration code, not the final numerical API or another scheduler.

Model-specific disposal stays in science. Shared hosting owns waiting for native
readers, supervising processes and establishing full shutdown. For prose input,
scientific prompts, tools and candidate validity stay in the contribution;
conversation execution, transport, pacing and supervision can be shared. The
scheduler does not construct chemical prompts.

7.4 Check the first working boundary

Use a small deterministic set of checks through the actual host/worker path:
run the same science directly without Jobs and through one/two hosted workers;
initialize from bound settings; keep analysis state separate; hold one worker
while another completes; check permission and handle rules changed by the work.
Reuse existing checks for unchanged behavior.

The first runtime increment uses small runnable contributions covering resident
prepared state and lazy/per-analysis or one-call work, with different inputs and
settings. It exercises actual workers through the common pool without Jobs or
scientific framework dependencies in the host. It is not evidence that the four
providers have migrated. Connect all four through the same interface in separate
runnable increments; their minimal integrations complete Tier 0. Inspect what
actually reaches science, including nested arguments. Input errors belong to
the contribution; revoked execution is refused by hosting. Changing worker count
leaves scientific code unchanged. Check new placement/backend modes when added.

Resource needs do not grant access. Deployment enforces permitted images,
devices, files, endpoints and credentials. Workers receive the minimum access
they need. Keep mutable state and diagnostics isolated so pooling cannot leak
data, handles or credentials between jobs or providers. An API boundary alone
does not provide that isolation.

8. What remains to be built
---------------------------
G01-G12 identify end-state gaps against the reviewed source. Note 065 uses these
IDs. Completing one useful part does not close an entire gap, and the first local
service does not have to close all twelve. Checks support the capability being
claimed; the provider baselines remain those recorded in 064.

G01  Common service. Replace provider-local job acceptance, maintenance and drain with
     one shared service. Keep scientific input/settings in contributions and
     permission in hosting. Use section 7.4 throughout. Minimal integrations of
     all four providers complete Tier 0; earlier working subsets remain partial.

G02  Worker pools. Run the same implementation with one or two independently owned
     workers. Show two jobs progressing and one held worker not blocking the other.

G03  Resource scheduling. Job counts do not measure GPU use, loaded-model memory
     or staged input. Tier 0 uses fixed bounds and nonoverlapping assignments
     where needed.
     Tier 1 adds phase-specific reservations and shared-device scheduling. Check
     competition, partial cancellation and HTTP waits without device overcommit.

G04  Prepared state. Separate portable input from handles tied to an exact worker
     instance. Preserve accepted work, reject wrong/stale handles, and separate
     scientific disposal from complete worker shutdown. Remove unnecessary coupling
     without assuming an old protocol can run simultaneous operations.

G05  Recovery decisions. Replace provider knowledge of private checkpoints and
     nested exceptions with clear decisions from the owner of each operation.
     Distinguish revoked permission, uncertain submission and late cleanup. Free
     resources only when justified, without repeating science or inventing reports.

G06  Surviving supervisor crashes. Save operation and result records, reconnect
     to existing work and reject obsolete supervisors. Check the relevant crash
     points as this feature is added. Unresolved work stays explicit. This must
     work before claiming unattended supervisor failover.

G07  Scheduling and maintenance. Use bounded, fair discovery and queues. Continue
     maintaining work while new jobs are refused. Restrict delivery pressure and
     failures to the connections and resources actually affected.

G08  Adaptive pools and batching. After fixed pools, measure model-load cost,
     memory, latency and useful concurrency. Add these optimizations where they
     help; retain bounds, equivalent scientific results and per-member cancellation.

G09  Remote execution. Add a real second backend with authenticated resource
     permissions, receiver-enforced rejection of old owners, partition/rejoin
     handling and safe treatment of unconfirmed remote work.

G10  Deployment. Reuse shared build, file acquisition and identity tools. Configure
     pool count and placement without editing scientific code. Check minimum access
     and safe upgrade/rollback for the deployment capability actually offered.

G11  Test reliability. The current generated campaign uses real children and
     scheduling yields; its command order does not establish every internal event
     order. Focused tests should wait for the events their conclusions depend on.
     Keep passing tests and state their scope. Independent generated reference
     models, coverage accounting, shrink/replay demonstrations and broad matrices
     are later work for a concrete remaining risk; they do not gate M1 or the
     first local service. Check a new backend's actual behavior when adding it.

G12  Provider migration. SECS needs independent workers instead of global worker
     coupling; NMRNet needs shared preparation/prediction management while retaining
     its permitted scientific retry rules; NMRPeak needs independently sized pools
     instead of a fixed HF/CHF pair; Magnet needs configurable pools instead of
     permanently named workers. Complete each change with its real adapter and
     preserve scientific behavior rather than the old process layout.

9. Priorities and completion
----------------------------
Tier 0: a useful local package for all four providers. Deliver direct and hosted
science, fixed one/two-worker pools, and the common service from discovery through
execution, existing durable delivery and orderly drain. Integrate SECS, NMRNet,
NMRPeak and Magnet with small adapters, preserving permission checks, exact
ownership, worker-bound handles, resource limits and independent maintenance.
Safe holds and explicit operator recovery are acceptable within the stated limits.
Build this in separate runnable increments: generic hosting/pools first, then
service integration and the four consumers. Useful early subsets are explicitly
partial Tier 0; all four are not required in the first commit.

Tier 1: extend that path with phase-specific resource use, bounded staging,
stronger recovery decisions, durable operation/result records
and a concrete remote backend. Choose increments for useful capability or a real
operational failure. Check the new behavior, including crash and failover cases
when claiming that support.

Tier 2: improve load time, memory use, latency or throughput where measurements
show a benefit. This includes adaptive warm pools and supported batching. Higher
tiers extend the Tier-0 path; they do not replace its scheduler or scientific API.

Testing supports the work. A focused check can be essential when changing
permission, ownership or isolation. Broad fuzzing, stress campaigns, compatibility
matrices and new evidence tooling come later when a concrete risk justifies them.
Existing test records suffice for routine development; identify exact files and
versions when publishing or checking a consumer against a release.

SECS, NMRNet, NMRPeak, Magnet and future providers share this architecture. An
early usable subset may be released under its stated scope without being called
Tier-0 completion. Full extraction removes the displaced generic service and
worker-management loops from all four existing providers.
