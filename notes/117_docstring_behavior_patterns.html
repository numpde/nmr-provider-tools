Docstrings that explain behavior

A docstring should let a caller understand what a function does and use it correctly without reading its implementation.

Each example shows the current source docstring first and the revised proposal second, followed by the workshop issue, a concrete learning and an example test. References to earlier proposals describe drafts from this workshop, not necessarily the current source docstring.

The recurring problems were hidden rules, repeated facts, unclear responsibility for checks, and missing failure or lifetime distinctions. The examples below show the specific wording and contract decisions that resolved them.

Criteria for every proposal

Assume a reader who knows Python and the surrounding API, but has not read this implementation. Review public functions, methods and private helpers against the needs of their actual callers.

Required: truthful and sufficient for correct use. Identify the governing contract, if one exists, and check the implementation, callers and relevant tests. Reject unsupported guarantees and omissions that could cause incorrect use or recovery. If sources conflict or leave a consequential guarantee unresolved, identify the disputed claim and leave its assessment open for resolution by the responsible owner. Do not select whichever source makes the proposal sound correct. A fact being true of today’s implementation does not make it a promise callers should depend on.

  1. Behavior in the opening. State what the operation does: what it returns, changes, creates, waits for or rejects. Include a defining condition when needed to distinguish that behavior. “Validate the code” or “apply the v1 rules” leaves the behavior hidden. The opening may be the whole docstring; expand it only when useful facts remain.
  2. Enough information for correct use. State the results, restrictions and failures that affect the caller’s next action. Distinguish what the function checks or guarantees from what the caller must arrange. Include effects, ownership, ordering, cancellation and repeated-call behavior where they matter, including state left after failure. Ask: could a missing fact cause a wrong call, mistaken result, wrong recovery or resource leak? Do not inventory unrelated exceptions.
  3. Observable, precise claims. Given the documented inputs and conditions, a reader can distinguish permitted outcomes from violations. Where results depend on scheduling or external state, state the stable guarantee and allowed variation rather than promise one outcome. Test what the caller can observe or must manage: returned values, failures, effects and event order. Examples illustrate rules; they neither replace the rules nor establish guarantees from one successful run. Private representation matters only when callers are entitled to depend on it.
  4. Clear English at the caller’s level. Name concrete inputs, outcomes and responsible parties. Explain unfamiliar terms; supporting links must not hide the operation’s essential behavior. Use a short expression such as state == "in_progress" when it states the rule more clearly than prose. Reject expressions that merely reproduce implementation steps. A reader should understand what happens without decoding the implementation.
  5. Proportionate detail and structure. Keep a detail when it changes what the caller understands, expects or must do. Before deleting it, identify any distinction it protects, including during failure recovery. Remove repeated rules and facts already clear from the signature or nearby explanation unless repeating them resolves a real ambiguity. A summary may introduce detail; it need not repeat it. Use headings only when they improve navigation through the contract, never to fill a template.

Category structure. Each category below defines the relationships a contract must express. A reviewer must be able to point to the phrase or signature fact that fills each applicable part. For each applicable part, the stated conditions must lead to identifiable outcomes. Unresolved resource ownership is an incomplete outcome where the caller depends on it.

Parts may fit in one sentence or need several clauses. Use the forms for the behavior actually performed: an operation that returns a Boolean and changes state needs both a truth condition and a state transition. State each fact once. Include optional claims when changing them would change the caller’s permitted use, interpretation or recovery. An annotation declares a type; it does not prove that a runtime check occurs.

To assess a proposal, use ordinary and boundary cases, plus failure or lifecycle cases where relevant. Derive expected behavior from the prose, compare it with the governing evidence, and identify the clause responsible for each mismatch. Also try a shorter version: does it preserve the reader’s understanding and ability to use the operation correctly?

Score each criterion separately and give a concrete reason: 0–3 means misleading or unusable; 4–6 requires reconstruction of important behavior; 7–8 is usable with an actionable weakness; 9 has only a minor actionable weakness; 10 has no identified weakness after the case and shortening checks. Scores apply to the inspected scope, not universal perfection. State missing evidence separately; if it prevents a required check, leave that assessment open. An unsupported guarantee or consequential omission rejects the proposal regardless of its other scores.

1. Guards

State the condition that raises, then explain the accepted values and successful return.

Contract form. accepted condition → success result; each rejection condition → exception.

  1. Accepted condition: define the input set precisely enough to decide membership, including type, range or syntax when relevant.
  2. Rejection branches: pair rejected conditions with their observable exceptions; conditions with the same outcome may share a clause. State precedence when a guaranteed order changes the outcome.
  3. Success: state what is returned when all checks pass.

Structural check. Can a reviewer partition the supported inputs into acceptance and rejection branches and identify the permitted result or exception for each? If overlapping checks have a guaranteed failure order, is that order stated? An undefined “valid” condition fails this check.

Example mapping. require_failure_code first rejects a non-str runtime type with TypeError; an exact str outside the length or grammar rule raises ValueError; an accepted string returns None.

require_failure_code

"""Require 1–128 ASCII characters, starting with a lowercase letter.

    Allow lowercase letters and digits, with single underscores between segments.
    """
"""Reject failure codes outside the 1–128-character lowercase ASCII format.

The first character must be a lowercase ASCII letter. Allow lowercase letters
and digits, with single underscores separating nonempty segments.

Return None on success. Raise TypeError unless type(failure_code) is str,
or ValueError if the string violates the length or syntax rules.
"""

Issue. The initial proposal opened with “v1 string length and syntax rules”, hiding the actual rule, then spread acceptance and rejection across Returns and Raises blocks.

Concrete learning. Put the length and alphabet in the opening. Define the remaining grammar once, then distinguish exact-type rejection from invalid string contents.

Example test. Assert that "a" and "a" * 128 return None; "a" * 129, "a__b", "A", and "" raise ValueError; None raises TypeError.

require_identity_text

"""Require nonempty printable identity text without whitespace."""
"""Reject identity text that is empty, contains whitespace or is not printable.

Unicode is allowed; each character must pass str.isprintable() and fail
str.isspace(). Return None on success. Raise TypeError unless type(identity_text) is str, or ValueError
for disallowed text. The ValueError message includes the value of identity_role.
"""

Issue. A revision left “printable” undefined for Unicode and said the error “identifies” identity_role without saying how.

Concrete learning. Name str.isprintable() and str.isspace() so Unicode boundaries are decidable, and state that the role value appears in the ValueError message. The role supplies diagnostic context; it does not select a different validation policy.

Example test. Assert that "é" returns None; "a b", "a\nb", "\u00a0" (a nonbreaking space), and "" raise ValueError; 1 raises TypeError. A Unicode letter is valid here.

require_attempt_ref

No docstring.

"""Reject references that are not "execution_attempt:sha256:" followed by 64 lowercase hexadecimal digits.

Return None for a matching string. Raise TypeError unless
type(execution_attempt_ref) is str, or ValueError for any other string.
"""

Issue. The initial opening named the reference’s wire syntax instead of showing it; the literal prefix and digit count appeared later.

Concrete learning. When syntax is the contract, the prefix, alphabet and count are clearer than a format label. Keep bad-type and bad-string outcomes distinct.

Example test. Use the same prefix with 63, 64 and 65 lowercase hexadecimal digits. Only the 64-digit reference returns None; an uppercase hex digit also raises ValueError.

2. Predicates

Define what True and False mean.

Contract form. within the input domain: True if and only if P; False otherwise.

  1. Domain: identify the inputs for which the Boolean contract applies.
  2. Truth condition: give the complete condition P, including how multiple conditions combine.
  3. Complement: False covers the remaining inputs in that domain. For state observations, identify which snapshot or source is read.
  4. Outside the domain: if malformed inputs return False or raise, state that behavior. Otherwise restrict the Boolean promise to the declared domain; do not imply that unsupported inputs return False.

Structural check. Can a reviewer determine both True and False cases, including a case where only one part of a compound condition changes? ‘True implies P’ alone is weaker than ‘True if and only if P’.

Example mapping. observation_revokes_execution is True for an expired attempt regardless of Job state, or for an in-progress attempt with a cancelled Job; all other supported state combinations give False.

attempt_is_in_progress

"""Read the API state without granting local execution or replay permission."""
"""Return whether the supplied attempt’s state is "in_progress".

This reads the supplied snapshot; it neither refreshes the server state nor
authorizes local execution or replay.
"""

Issue. The initial proposal restated one state comparison under a Returns heading, while the source’s warning about execution permission needed to remain visible.

Concrete learning. State the exact Boolean condition once. Preserve the distinction between reading an in-progress snapshot and authorizing execution or replay.

Example test. For valid records with states in_progress, succeeded, failed and expired, assert True, False, False and False respectively.

observation_revokes_execution

"""Recognize expiry or cancellation without claiming local work has stopped."""
"""Return whether the attempt is expired or is in progress with a cancelled Job.

Use only the supplied observation; this predicate does not stop local work.
"""

Issue. The initial opening said “revokes execution permission” without showing which combination of attempt and Job states produces True.

Concrete learning. Put the Boolean relationship in the opening: expiry suffices alone; Job cancellation matters here only while the attempt is in progress. Classifying a snapshot does not stop work.

Example test. Build a truth table over valid attempt and Job states: expired is always True; in_progress is True only with cancelled; succeeded and failed are False.

token

"""Return whether value has exact type str and contains exactly 32 characters from 0–9 or a–f.
"""

Concrete learning. One sentence can give the exact type, length and alphabet. “Return whether” already defines False for other inputs; a second section adds no contract fact.

3. Queries and selections

Name the returned information and the selection rule. Explain absence, ordering and freshness where they matter.

Contract form. search scope + matching rule → selected result; no match → explicit absence outcome.

  1. Scope and match: identify the collection or source searched and the rule that selects a match.
  2. Result: specify whether the operation returns one, the first or all matches; include ordering, identity and freshness when callers depend on them.
  3. Absence and rejection: state the no-match outcome. If invalid inputs are checked, distinguish their outcome from absence; otherwise identify the input restrictions as caller preconditions.

Structural check. Can a reviewer predict inclusion and exclusion, the number and order of results, and the no-match outcome? Naming a ‘relevant’ item without the selection rule fails this check.

Example mapping. HostedContribution.call searches this handle’s exported operations by function identity. A permitted function or correctly bound method selects the retained CallBinding; an unexported function or wrong receiver raises ValueError.

HostedContribution.call

"""Select an exported method of this receiver without string dispatch."""
"""Return the existing CallBinding for an exported method without invoking it.

Pass an unbound function or a method bound to this contribution’s instance.
Raise ValueError if the function is not exported, or if a bound method’s
receiver is not this contribution’s instance.
"""

Issue. The initial proposal described unwrapping a bound method and looking up its underlying function, following the implementation’s steps.

Concrete learning. Describe the accepted call forms and receiver restriction instead. Preserve that the existing binding is returned and that looking up a method does not invoke it.

Example test. Look up the same registered function twice and assert object identity of the bindings. A sibling instance’s bound method raises ValueError; the scientific method has not run.

decoded_error_evidence

"""Expose decoder-owned facts to protected consumers, which must redact them.

    Exact reconstructed types and a private immutable record distinguish these
    facts from arbitrary exception attributes, properties and mutable notes.
    """
"""Return retained process-decoder evidence, or None when it is absent or unsupported.

Supported exact exception types are RemoteScienceError, BaseExceptionGroup,
ExceptionGroup, CallRejected, ScientificRejection, StartDeadlineExpired,
TypeError, ValueError, OSError, RuntimeError, TimeoutError and PermissionError.
Their _process_error_evidence attribute must have exact type
_DecodedErrorEvidence. Return that record itself; otherwise return None.
Callers must redact the record’s contents before public disclosure.
"""

Issue. An auditor suggested omitting the private record type as an implementation detail, but that exact type determines whether the helper returns evidence or None. “Recognized by the decoder” still left the supported exception types undefined.

Concrete learning. Judge a detail by its effect on the caller, not by whether its name is private. Keep the type condition, retained-object behavior and caller-owned redaction duty. A query needs a decidable matching rule. Name the supported types when no caller-facing definition supplies that set; an internal mapping name alone still requires reading the implementation.

Example test. A decoded supported exception returns the retained record by identity. A plain exception, an unsupported subclass and a supported exception with a wrong-type evidence attribute each return None.

select_images

No docstring.

"""Return a list of obsolete SDK image IDs in inventory order, or [] if none qualify.

This function does not contact Docker.

current is (current_checker, current_recipe, current_bootstrap). Read ownership
labels under org.nmr-provider-tools.; each required recorded hash must be 64
lowercase hexadecimal digits. Only these roles qualify:
- checker or no role: inputs differs from current_checker; the permitted tag
  is checker:<inputs>.
- checker-bootstrap: inputs differs from current_bootstrap; the permitted tag
  is checker-bootstrap:<inputs>.
- delivery: recipe differs from current_recipe, and inputs is also required;
  permitted tags are delivery:<inputs> or delivery-recipe:<recipe>.

Tags have the nmr-provider-tools/ prefix. Allow an untagged image or exactly
one permitted tag. Exclude protected IDs and images with repository digests.

Malformed inspection records raise RetirementRefused; missing or invalid
ownership hashes exclude the image. Before removal, the caller must recheck
live references and current build identities.
"""

Issue. An early draft said ownership labels and tags “agree” and referred to the “relevant build hash”. It hid the role-specific rules and the missing-role checker case. The category review also exposed an unstated empty result and ambiguous scope for hash validation.

Concrete learning. Keep each role’s hash comparison beside its allowed tags. Describe the resulting policy rather than every defensive branch: the role/hash/tag rules already exclude current tags, so repeating that exclusion is unnecessary. State the no-match result explicitly and distinguish validation of recorded ownership hashes from comparison with supplied current identities.

Example test. Use an obsolete checker input hash with no role label and assert selection. A checker-bootstrap image compares its inputs with the bootstrap hash; a delivery image compares its recipe, not its inputs, with the current delivery recipe. Then separately add a protected ID, repository digest, foreign tag, second tag or current build tag and assert exclusion. Malformed inspection structure raises RetirementRefused.

4. Conversions and derivations

Describe the input-to-output transformation and its representation, ordering or validation rules.

Contract form. input → output relationship, including preserved and changed information.

  1. Relationship: define how the output is derived from the input, not merely the destination type.
  2. Representation: state consequential encoding, ordering, normalization, precision or information-loss rules.
  3. Failure: state the supported input domain and any rejection or propagation rule the operation actually promises. Errors may propagate from a named conversion or constructor; do not invent additional validation.

Structural check. For a specified input, can a reviewer derive the expected output or its permitted properties and identify what information may change or disappear? A type name alone fails this check.

Example mapping. parse_resource_requirements constructs a record from each keyword mapping and returns a frozenset: equal records collapse and input order disappears; expansion and constructor errors propagate.

parse_resource_requirements

"""Project the resource-only field for full startup or direct binding callers."""
"""Convert requirement mappings into a frozenset of ResourceRequirement records.

Each mapping supplies keyword arguments to the record constructor. Equal
records collapse and input order is lost. Errors while iterating requirements,
expanding mappings or constructing records propagate.
"""

Issue. The draft used generic Returns and Raises sections, and “mapping errors” did not say which operation could fail. The later category review found that iteration failures were omitted from the propagation rule.

Concrete learning. Describe the mapping-to-record conversion, equality-based duplicate removal and lost ordering. Name keyword expansion and record construction as the sources of propagated errors; do not imply collection-wide validation. Include iteration when consuming an iterable; a conversion can fail before it reaches an element’s constructor.

Example test. An empty iterable produces frozenset(). Repeating one valid mapping produces one record; reordering valid mappings produces an equal set.

JsonDataclassCodec.encode

No docstring.

"""Serialize this codec’s exact dataclass type to compact ASCII JSON bytes.

Use its JSON-mode serialization, sort object keys, omit separator whitespace
and escape non-ASCII characters. Raise TypeError if type(value) is not
value_type. Serialization errors propagate; nonfinite JSON numbers are rejected.
"""

Issue. The example claimed failure for a “normally serialized” nonfinite float without defining the serializer. An auditor’s explanation of default conversion was also unverified and was withdrawn.

Concrete learning. Scope a guarantee to the stage that enforces it: allow_nan=False rejects nonfinite numbers remaining after serialization. Use a concrete fixture for examples rather than guessing how an earlier transformation behaves.

Example test. Encode a simple dataclass with fields declared b then a and respective values 2 and 1; assert bytes b'{"a":1,"b":2}'. Passing a subclass instance raises TypeError.

frame

No docstring.

"""Return a process-wire frame: a four-byte length followed by ASCII JSON bytes.

Encode the value through pack(). The prefix is an unsigned big-endian count
of the JSON body bytes, excluding the prefix itself. Raise ValueError if the
body exceeds MAX_FRAME_BYTES; packing and JSON serialization errors propagate.
"""

Issue. The initial proposal spread a small framing transformation across Returns, Raises and Effects, including an unnecessary no-send sentence.

Concrete learning. Spend words on the protocol facts: a four-byte unsigned big-endian prefix, a count of body bytes only, and the body-size limit. Do not list unrelated effects simply to fill a section.

Example test. Assert that the prefix equals len(frame) - 4 and that decoding the body reconstructs a supported value. Exercise body lengths exactly at and one byte over MAX_FRAME_BYTES.

5. Construction and declaration

State what is created or attached, when work starts and who takes ownership.

Contract form. construction or declaration → object and immediate effects; later activation → separate trigger.

  1. Immediate result: name the object or declaration produced and any state changed during this call. State new-versus-retained identity when callers depend on it.
  2. Phases: distinguish checks and work performed now from those deferred to decoration, registration, startup or later use. An annotation does not establish that a runtime check occurs.
  3. Defaults and overrides: state omission-versus-explicit-value behavior that the signature does not make clear.
  4. Resources, when involved: identify the ownership-transfer point and who retains ownership if construction fails.

Structural check. Can a reviewer distinguish construction from activation and determine the caller-visible result, state and ownership of any resources involved after success or consequential failure? ‘Creates a ready object’ fails if readiness actually requires a later step.

Example mapping. operation(...) returns a decorator; applying it attaches a declaration and returns the same function; HostedContribution later validates the hosted signature and codecs. Decoration does not execute the method.

ExecutionSettings.create_host

"""Construct only; the caller immediately enters the returned host lifetime.

        Successful process-host construction transfers session custody. Refusal
        leaves it with its caller. No adoption, initialization or start occurs here.
        """
"""Return a new thread or process host without starting a contribution.

A supplied host mapping replaces the configured host options. Process mode
rejects process_session=None; thread mode rejects a non-None value, both with
ValueError. A process session’s connection must not have been started.

Successful process-host construction transfers session ownership to the host;
construction failure leaves it with the caller. Create the host on the running
event loop that will use it, and immediately enter its async context to manage
its lifetime.
"""

Issue. The draft omitted the running-loop requirement and called the option mapping “host”, which could be mistaken for an existing host object.

Concrete learning. Follow a factory into each constructor before stating its requirements. Both backends capture the running loop. A supplied mapping replaces options rather than merging them; process-session ownership transfers only after successful construction.

Example test. On a running event loop, construct each backend with valid options and assert its host type. A non-None session in thread mode and None in process mode raise ValueError. Verify option replacement rather than merging, caller custody on construction failure, and no contribution startup during construction.

operation

"""Export an ordinary method without wrapping or changing direct calls.

    Parameters after self are keyword-only. Annotations identify the payload,
    optional analysis session and control; explicit state ports name live inputs.
    Omitted resources use the contribution's common call requirements. Explicit
    empty resources mean that this operation has no call resource requirements.
    retryable_failures names exact exception types for which repeating the entire
    calculation is scientifically permitted. Subclasses and undeclared failures
    do not qualify; deployment policy still decides whether to retry.
    """
"""Return a decorator that exports an instance method without wrapping it.

On decoration:
Attach a declaration and return the same function without
calling it. A non-function raises TypeError; a repeated declaration raises
ValueError. HostedContribution checks the signature, declaration relationships
and codecs when it constructs the binding.

When hosted:
- Use a synchronous, non-generator method; no parameter may have a default.
- Annotate the return and all parameters after self; those parameters must be
  keyword-only.
- Allow at most one payload, one analysis-session and one control parameter.
- state_inputs declares the names and types of live input arguments.
- state_outputs requires a ScientificReturn[Result] return annotation.
- A ScientificControl argument is required exactly when progress or cooperative
  interruption is declared; otherwise omit it.

Codecs and resources:
Omitted codecs become JsonDataclassCodec instances for the payload and result
types; non-dataclass values need explicit codecs. An explicit codec’s value_type
must match the corresponding annotated type.

requirements=None inherits the contribution’s call requirements; an explicit
empty set declares no call resource requirements.

Concurrency:
concurrency declares the required serialization scope: one instance
(INSTANCE_SERIAL, the default), the entire process (PROCESS_SERIAL), or no
serialization requirement (PARALLEL). The selected host must support it.
Decoration adds no synchronization to direct calls.

Retry eligibility:
retryable_failures names exact exception classes for which repeating the
entire calculation is scientifically permitted; a subclass qualifies only if listed itself.
Deployment policy still decides whether to retry.
"""

Issue. The first proposal explained decoration but omitted constraints checked later during hosted binding, so an apparently valid declaration could fail when hosted. The phase summary named signature and codec checks but left declaration relationships implicit. The integrated review also found that concurrency requirements were unexplained.

Concrete learning. Separate declaration-time effects from hosted validation. Make required signatures and control/state/codec relationships explicit. Group the longer contract by phase, and distinguish scientific retry eligibility from deployment policy actually choosing a retry. The activation summary must cover the deferred relationships described below it. Describe concurrency as a host requirement; attaching a declaration does not synchronize direct calls.

Example test. Decorate a synchronous method and assert the returned function is the same object and its body has not run. A second declaration raises ValueError. Separately, decoration of an async method succeeds but HostedContribution construction rejects it. Exercise state_outputs with and without ScientificReturn[Result], and progress with and without ScientificControl, to verify the hosted signature requirements.

6. State changes and external effects

Name what changes, which record or resource is affected and what happens on failure.

Contract form. initial state + trigger + matching condition → resulting state and return; failure → remaining state and exception.

  1. Target and condition: identify exactly which state or resource may change and what permits the change.
  2. Success transition: state the changed fields or effects and any returned result. Identify preserved state when callers rely on it, such as unrelated queue rows.
  3. Failure transition: pair each consequential failure with both its exception and the state left behind; scope atomicity claims to what is actually guaranteed.
  4. Repeated action, when supported or consequential: state whether another call repeats the effect, replaces data, does nothing or fails. Separate caller duties from checks performed here.

Structural check. Can a reviewer compare before and after state for success and a failed condition, plus repetition when supported or consequential, without assuming every exception implies rollback?

Example mapping. DeliveryQueue.hold changes the exact matching row’s state and reason; a second hold replaces the reason. With no exact match it raises DeliveryConflict and leaves the queue unchanged. Reviewing the reason is the caller’s duty.

DeliveryQueue.hold

"""Retain a reviewed operator explanation, never raw remote response text."""
"""Mark the exact queued request as held and store the operator’s explanation.

Match the whole request, including its body. Holding it again replaces the
reason. If no exact match remains, raise DeliveryConflict and roll back.

The caller supplies a reviewed operator explanation, not raw remote response
text. This method checks that reason has exact type str and 1–512 characters;
wrong type raises TypeError and invalid length raises ValueError.
"""

Issue. The initial draft scattered one update across Requires, Returns, Effects, Raises and Repeated calls.

Concrete learning. Keep matching, mutation and repeated-call behavior together. Separately identify the caller’s duty to review the reason: this method checks type and length, not whether the text is appropriate for disclosure.

Example test. Hold one of two queued requests and assert only its state and reason changed. Hold it again with another reason and assert replacement. A mismatching body raises DeliveryConflict and leaves both rows unchanged.

DeliveryQueue.remove_published

"""Delete only after the API owner validated its matching terminal receipt.

        This internal method has no producer IPC endpoint. Receipt verification
        stays with ProviderAPI; the transaction protects exact queued identity.
        """
"""Delete the exact queued request after its matching API receipt has been verified.

The caller must verify the terminal receipt; this method does not contact the
API or verify receipt evidence. Match the full request, including its body,
inside one transaction. Raise DeliveryConflict and roll back if no exact
match remains, including when the same deletion is repeated.
"""

Issue. The initial opening described deletion without its receipt prerequisite; that prerequisite appeared later.

Concrete learning. Put the prerequisite beside the action and name its owner: the caller verifies the receipt. Scope rollback claims to the specified conflict, rather than promising that every storage failure leaves the same state.

Example test. Delete one matching row while retaining an unrelated row. Repeat the same call and assert DeliveryConflict. Receipt verification belongs in the caller’s test.

DeliveryQueue.discard_held

"""Operator disposition only; removing held bytes proves no API receipt."""
"""Delete a held request matching the API origin, provider, attempt and body digest.

Require a canonical HTTPS origin, valid provider and attempt references, and

7. Observation and waiting

State what ends the wait and what is returned or raised. Explain cancellation and timeouts.

Contract form. observed state → continue waiting, return or raise; applicable interruption → effects on waiter and observed work.

  1. Observed work: identify what is being watched and whether the call starts it or observes existing work.
  2. Decision rule: define the conditions for continued waiting, successful return and failure, including precedence when several conditions hold.
  3. Time and interruption, when they affect outcomes or recovery: state deadline ownership and distinguish cancellation of the waiter from cancellation of the work.
  4. Re-entry, when supported or consequential: state whether another call observes the same work or starts a new attempt.

Structural check. Can a reviewer assign continue, return or raise to each relevant observed state? When interruption affects the outcome or recovery, can they identify what remains active? An elapsed-time example cannot substitute for the decision rule.

Example mapping. observe_cleanup keeps waiting while unsettled and failure-free, returns a settled failure-free observation, and raises reported failures even before settlement. An overdue flag alone does not end the wait; observer cancellation does not cancel cleanup.

observe_completion

"""Wait on an existing operation without submitting or stopping work.

    The caller owns this wait's timeout. Cancelling it leaves the original
    operation available for another observer; it does not establish that
    scientific effects have stopped. Completion preserves the independent
    scientific outcome, result availability and cleanup facts in Observation.
    """
"""Wait until the existing operation reports finished, then return its observation.

Finished does not mean successful: inspect the scientific outcome, result
availability and cleanup separately. Observation errors propagate.

This helper imposes no overall timeout; the caller supplies any deadline.
Cancelling the wait does not request an operation stop. Another observer can
continue watching the same operation.
"""

Issue. The initial proposal separated related wait facts into Returns, Waiting and Cancellation sections, making the reader assemble their relationship.

Concrete learning. State what ends the wait and what the returned observation means. Finished is not necessarily successful; cancellation of an observer is not a stop request, and the overall deadline belongs to the caller.

Example test. Provide an unfinished observation followed by a finished failed observation and assert the latter is returned. Cancel a waiter while unfinished and confirm no stop request was made.

observe_cleanup

"""Wait for cleanup already requested by provider code; raise its original failures.

    Pass the control returned by analysis.close(), operation.release_result() or
    host.retire(). This helper keeps waiting if cleanup becomes overdue: the flag
    alone does not end the wait or emit a warning. To react before cleanup finishes,
    call control.observe(...) and inspect the returned observation's
    allowance_expired field.

    Canceling this wait leaves cleanup running. A single cleanup failure is raised
    directly; independent failures keep their original causes together. Waiting
    again observes the same cleanup rather than starting it again.
    """
"""Observe already-requested cleanup until it settles or reports a failure.

Return the settled observation when it has no failures. Raise a single failure’s
original cause, or a BaseExceptionGroup of the original causes for multiple
failures. A reported failure ends this wait even if cleanup has not settled;
observation errors also propagate.

An overdue flag alone does not end the wait, and there is no overall timeout.
Cancelling this wait does not cancel cleanup. Repeated calls observe the same
cleanup rather than requesting it again.
"""

Issue. The important distinction to preserve during shortening was that a reported failure can end the wait before cleanup settles.

Concrete learning. Document the actual exit condition: settled or failed, not simply “cleanup complete”. State whether original causes are retained and grouped, and whether an overdue flag alone changes the wait.

Example test. An unsettled observation with one cause must raise that same object immediately. An overdue observation without failures keeps waiting. A settled failure-free observation is returned.

_join_settlement

"""Defer observer cancellation until this exact cleanup task returns or fails."""
"""Wait for the owned task’s result or failure, deferring cancellation of this waiter.

Shield the task from cancellation of this waiter; the wait may be indefinite.
Without observer interruptions, return the task’s result or propagate its
failure or cancellation.

If the observer was cancelled, retain those interruptions until the task ends.
Then raise the single interruption, or a BaseExceptionGroup when there are
multiple interruptions or an interruption together with task failure or
cancellation.
"""

Issue. The grouping sentence initially mentioned task failure but left concurrent task cancellation implicit. The example exercised observer-only and task-only cancellation separately.

Concrete learning. Cover observer cancellation, task cancellation and their combination. Explain shielding and deferred propagation separately. Do not promise original cancellation-object identity unless that identity is actually preserved.

Example test. Block the owned task on an event, cancel its observer, and assert the task remains live and the join remains pending. Release the event and verify observer cancellation is then propagated. Separately cancel only the owned task and assert CancelledError reaches the observer. Finally cancel the owned task after an observer interruption and assert both cancellations are retained in the raised group.

8. Resource lifetimes and orchestration

Describe the ordered work and ownership handoff: what starts, what is returned or yielded, and who handles cleanup.

Contract form. acquisition → owner and permitted use → release trigger → confirmed cleanup; consequential exit → remaining ownership.

  1. Acquisition and transfer: identify each resource, its owner and the event that transfers or lends control.
  2. Use interval: state which resources must remain available while work or readers depend on them.
  3. Release: name who requests cleanup and what observation confirms it has finished.
  4. Consequential exits: for success and failures or cancellation that affect a resource, state what remains owned or pending and what the caller must do next. Include failed transfer when it matters who retains the resource.

Structural check. At each consequential exit involving acquired, borrowed or transferred resources, can a reviewer identify the surviving owner, remaining resource state and signal that permits release? “Cleanup runs” alone fails this check.

Example mapping. UploadTransfer.acquire_file borrows directory_fd through acquisition or failed-file cleanup. Success transfers file access and deletion to the caller; pending failure keeps cleanup with the transfer, with store retirement required before settle_file confirms cleanup.

ExecutionSettings.open_contribution

"""Own host startup and retirement for one configured contribution.

        Injected process sessions transfer custody on successful host construction,
        just as with create_host(). Earlier configuration failures leave them with
        the caller. Both backends initialize science before yielding.
        """
"""On async context entry, create and enter the host, initialize the contribution,
then yield (execution_host, contribution).

Host creation follows create_host()’s option and session rules.
Successful process-host construction transfers session ownership; earlier
failure leaves it with the caller.

Initialization failure, body failure and cancellation all exit the host context
and invoke its retirement handling. Cleanup failures propagate, grouped with
a distinct body or initialization failure when both occur; context exit does not by
itself prove that retirement succeeded.
"""

Issue. “Retire the host on exit” could be read as a guarantee of successful cleanup, and the proposal repeated the initialization-before-yield rule. The category review found that the opening hid context entry as the activation event and that “both failures” included the same exception object twice.

Concrete learning. Describe retirement handling and its failure outcomes separately from successful retirement. Locate session transfer at host construction; initialization failure still enters cleanup without yielding a usable handle. Name the event that starts work. Distinguish two failure causes from one cause observed again during cleanup.

Example test. Record initialize, yield/body and host-exit events; assert their order. Force initialization failure and assert host exit occurs without yielding. Also exercise body failure.

ResultConsumption.consume

"""Observe acceptance, then request and observe the exact result release.

        Known acceptance lives in the completed task even if requesting release
        raises. Re-observation retries only that exact idempotent release request,
        or observes the original release control once one has been returned.
        """
"""Wait for receiver acceptance, then request result release and observe its cleanup.

Return a settled release observation with no failures. A receiver failure
propagates without requesting release. Acceptance means the receiver returned
successfully; it does not by itself establish durable storage or publication.

A single reported cleanup failure is raised as its original cause; multiple
causes are grouped. A failure can end this wait before cleanup settles.
Keep this owner and resources needed by unfinished cleanup alive after such
an error; the exception does not confirm that release has finished. Further
consume() calls can raise the retained failure again; use release.observe
to inspect settlement directly when failures remain.

Repeated calls reuse the original receiver task and any retained release
control. If requesting release raised before returning a control, retry only
that same idempotent release request; never retry a failed receiver.

Cancelling the wait does not cancel acceptance or cleanup. Keep resources
needed by unfinished acceptance alive as well.
"""

Issue. The draft delegated cleanup behavior to observe_cleanup() without stating that consume() can raise while cleanup remains unsettled.

Concrete learning. Carry consequential failure state through wrappers. After an early cleanup failure, retain the owner and needed resources; repeated consume() calls may raise again, so use the retained release control to inspect settlement directly.

Example test. Block the receiver and assert release has not been requested. After acceptance, observe release. Call again and assert the receiver ran once and the retained release control is reused. Separately report a cleanup failure with settled=False: assert the original cause escapes, while the same owner, release control and resources remain available for continued observation.

UploadTransfer.acquire_file

"""Verify one transfer into a closed private file; lend its directory.

        Keep directory_fd open and exclusively controlled until success or
        settle_file confirms failed-file cleanup. A successful receipt transfers
        file lifetime to composition, which must wait for readers before deletion.
        """
"""Download an Upload into a private file and return a VerifiedUploadFile receipt.

directory_fd must name a directory owned by the effective user with mode 0700.
The caller keeps it open and exclusively controlled until success or confirmed
failed-file cleanup. No transfer may be active and no private-file
cleanup may remain pending. The store exchange must have confirmed retirement
before starting, and retirement_seconds must be finite and positive.

Create the file before requesting a grant from grant_factory. Verify the byte
length and content hash against that grant, close the writer, then return the
receipt. After success this transfer no longer uses directory_fd. The caller
owns subsequent file access and deletion, and must wait for readers before
deleting the file.

Initial argument checks precede allocation of file-cleanup resources. Failures
during or after file creation retain failure evidence. If file_cleanup_pending
remains true, this transfer still owns the unfinished cleanup: retire the exact
store exchange before calling settle_file(), and keep the
directory open until cleanup is confirmed. An uncertain close can require
process retirement. Cancellation does not establish that cleanup has finished.
"""

Issue. The review exposed two different lifetimes: the transfer’s loan of directory_fd and the caller’s ownership of the successful file. “Private directory” also omitted concrete preparation requirements. “Before a file owner exists” did not tell the reader whether it meant a bookkeeping object or the physical file.

Concrete learning. State the effective-user ownership and 0700 mode requirements. The transfer stops using the descriptor on success, but the caller still owns file access and deletion. Pending failed-file cleanup requires retiring the store exchange first; it is a different path from successful handoff. Separate allocation of cleanup resources from file creation: creation itself can fail after cleanup responsibility begins.

Example test. An unretired store is refused before a grant request or file creation. For matching bytes, assert the returned file’s length and digest and that the writer descriptor is closed. A digest mismatch returns no receipt; drive cleanup to confirmation before closing the directory.

Research behind the structure

PEP 257 calls for a behavioral summary plus relevant results, effects, exceptions and calling restrictions. numpydoc provides familiar Returns, Yields, Raises and Examples sections. This note uses those distinctions where they help explain the contract; they are not a template to fill for every function.

Design by Contract separates caller obligations from guarantees and compares state before and after an operation. Here, that distinction separates what callers must arrange from what the function checks or changes.

Sphinx doctest executes examples and compares their output. Hypothesis stateful testing exercises action sequences and checks invariants. Deterministic values suit examples; transactions, cancellation and retries need controlled state and event assertions in tests.

Ask of every clause: what setup and observation would demonstrate that this claim is false?
