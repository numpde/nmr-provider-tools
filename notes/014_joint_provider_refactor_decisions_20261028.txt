D007 -- Magnet normal stop must not impose report loss (20:27 UTC)
----------------------------------------------------------------

Serious alternatives, submitted by Magnet:
A. Increase the current finite 600-second grace. This delays the same forced
   kill and still cannot establish successful drain during indefinite outage.
B. Send SIGTERM manually and poll. This can interact with unless-stopped restart
   policy and requires additional lifecycle mutations/ownership to be correct.
C. Request engine-managed stop without a daemon kill deadline, retain the existing
   bounded local command wait, and report blocked/uncertain stop if that wait ends.
   No runner reconciliation, down, or removal follows an unconfirmed provider stop.

Choice: investigate C as the smallest existing engine primitive, conditionally.
Docker documents container stop --timeout=-1 as waiting without a kill timeout:
https://docs.docker.com/reference/cli/docker/container/stop/
Compose documents a stop timeout but does not state the -1 behavior there:
https://docs.docker.com/reference/cli/docker/compose/stop/
Therefore this source alone does not establish the exact Compose/client-cancel
path. First run an isolated offline fixture against the installed engine/client,
including a child that retains an obligation past the local caller wait. Prove
no SIGKILL, no accidental restart, and no following runner/down/removal action.

Product edit is conditional on that probe. If supported, change the existing
provider-first stop operation and its honest blocked-stop diagnostics, keeping
normal stop separate from a deliberate emergency loss decision. Do not replace
it with an unbounded host CLI or assume Compose down of all services preserves
provider-before-runner ordering. Inspect actual provider exit/disposition before
subsequent mutations. No new force framework or production stop is authorized.

Installed-platform evidence: Compose 5.5.1 with finite stop=1 killed the held
fixture child (137). stop=-1 plus a four-second local waiter left it running;
explicit release then produced exit 0 without restart. Evidence:
/tmp/magnet-drain-compose-probe.log. This supports the selected stop operation,
not a universal property of every container stop path.

D201 — Who supplies a provider's delivery binding?
--------------------------------------------------

The user objects to the current central binding and restart model and expects
provider-supplied information. The exact referent and required contract are being
clarified. Today the provider owns its credential, but an operator lists that file,
identity, route and socket in the shared delivery definition. The deployment
renderer grants each credential read-only, and DeliveryService constructs a fixed
binding tuple at startup. DeliveryClient submits through an already configured
endpoint; it has no dynamic registration or credential handoff. Adding a binding
therefore changes the shared definition and currently cycles the service.

Serious alternatives to workshop, not a decision:
A. Keep a centrally assembled static definition, with provider-owned inputs
   supplied during deployment. This has a single queue owner and explicit grants,
   but adding a provider coordinates and interrupts existing consumers.
B. Let providers register their own binding with the shared service, which owns
   durable binding and delivery authority after the provider exits. This avoids a
   restart but needs an authenticated registration lifecycle, durable credential
   access, per-provider isolation, quotas, revocation and crash recovery.
C. Give each provider its own independently durable delivery service and queue.
   Provider deployment then supplies its own configuration, but service lifecycle,
   storage, resource limits and operational burden multiply; shared code can still
   implement the delivery contract.
D. Have providers supply fragments that a host owner composes into the current
   definition. This reduces central hand editing but by itself does not remove the
   current restart or solve durable authority when a provider disappears.

No redesign selected or authorized here. The owners must compare actual lifecycle,
credential grant, retained-outcome recovery, backpressure and security semantics,
including whether a service can publish after its provider has exited. The already
authorized ProArt NMRPeak cutover continues under the existing contract while that
discussion proceeds; its proposed configuration has not yet been installed.
NMRNet favors evaluating B; Magnet favors evaluating C first; SECS supports

Signing authority has its own alternatives, independent of where configuration
is assembled. The provider could grant delivery durable, scoped access to its
credential; delivery could hold an API-issued delegated per-result authority if
the API defines one; or delivery could call an independently available signer.
The first needs explicit secret grants and rotation/revocation handling; the second
needs a new API contract; the third adds a service whose availability and lifetime
must be owned. Current SDK signatures expire 300 seconds after creation, so a
single pre-signed request cannot on its own guarantee delivery after an unbounded
outage. No one of these signing mechanisms has been selected or qualified here.
