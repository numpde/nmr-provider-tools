Plan: build the shared package, then extend it
==============================================
2026-11-09 | Design: note 066 | Reviewed runtime: 1178115, SDK 0.6.8

What to build next
------------------
Start M1 now. Build the execution boundary for SECS, NMRNet, NMRPeak, Magnet and
future contributions together. Make scientific code work directly, then through
shared code on one or two workers. Build the common service and connect all four
providers in separate runnable increments: find a job, run the science, keep the
result, deliver it and shut down properly. No provider has a prescribed first
place or defines the architecture for the others.

Scientific code supplies the model, settings, input interpretation and numerical
work. The shared service chooses jobs and assigns resources. The execution host
is the shared code that loads the scientific implementation and calls it. The
service passes input through without interpreting peaks, choosing weights or
creating framework-specific device objects. Note 066, section 7, explains these
three interactions and who supplies each input.

Existing worker counts and process layouts can change. One and several workers
must use the same scientific code. Keep scientific behavior and the protections
in note 064; replace incidental restrictions of the old service loops.

This note sets the work order. Note 066 describes the intended system and lists
unfinished work as G01-G12. Note 064 records earlier source reviews and useful
tests. Older instructions to qualify all existing services first are superseded.

Build in this order
--------------------
Tier 0 -- Make a useful local package for all four providers. Complete M1, M2
and their minimal integrations in M3, through separate runnable commits. The
first commit builds generic hosting and a fixed local pool; it does not migrate
four repositories at once. Useful earlier subsets are partial Tier 0. Include
fixed one/two-worker settings, result delivery and orderly shutdown. Keep
permission checks, separate job state, resource limits and exact ownership of
work. Where automatic recovery is missing, retain uncertain work and explain the
supported operator action. A restart never authorizes repeating unknown work.

Use a few deterministic tests through the installed service and actual workers:
finish a job and hand its result to the existing delivery queue, which preserves
accepted reports across restarts; hold worker A while B finishes, then settle A
when its original evidence arrives;
reject revoked permission and handles from the wrong worker; retain unfinished
work and selected results during shutdown. Local queue acceptance and central
API publication are separate events. These tests accompany implementation.

Tier 1 -- Allocate resources separately for each stage, improve recovery,
preserve work across supervisor crashes, and add a real remote execution
backend. M4-M6 and M7.3 describe this work. Tier 0 may reserve resources for
a whole operation until the finer controls exist.

Tier 2 -- Improve speed or resource use where measurements justify it. Examples
are adjusting worker counts automatically and processing compatible jobs in
batches. M7.1/M7.2 cover these changes. All tiers extend the same working system.

Keep testing proportional to the change. Fix a demonstrated defect with a
focused regression test. Large generated-test campaigns, elaborate models of
expected state, stress runs and broad compatibility testing come later when
they answer a concrete question. M0.3/M0.4 do not block M1. Stop expanding tests
once the changed behavior is adequately checked. Known permission, ownership
or scientific-correctness failures still block the affected feature.

Work on main in small commits that each leave something runnable. Include the
code, necessary tests and installation changes together. Explain what changed,
what ran and what remains unfinished. Append history. Releases, dependency
repins and deployment changes need their own authorization and checks.

1.1 First implementation commit: common local hosting and a fixed pool

Proposed title: Add shared scientific hosting and fixed local execution pools

Deliver working runtime code, with two small contributions that can be called
directly and hosted in actual child processes. Run the same contribution with
one or two allocations by changing configuration. This first commit needs no
Jobs service, model download or scientific library. Its examples exercise the
different execution shapes below; they do not establish real-model compatibility
or complete provider adoption.

Scientific calls
  A registered, configured factory creates a scientific instance. Deployment
  selects the factory, binds its own settings/assets and grants its environment.
  The factory interprets those inputs. Its instance may load reusable resources
  at startup or load them lazily/per analysis during scientific calls.
  Registration declares capabilities and resource/environment requirements;
  allocation count and placement are separate configuration. Shared code must
  not invent a common model-settings object.

  The instance supplies run(input), or run(prepared) when it explicitly supplies
  optional prepare(input). It also supplies analysis and instance cleanup where
  needed. A one-call contribution needs no dummy preparation or cleanup method.
  Keep numerical functions unchanged behind these small adapters. Adapters
  decode scientific bytes/references and encode final results; prepared Python
  or framework objects stay in their worker. No pickling arbitrary objects across
  the boundary. Consume lazy results and finish relevant device work before the
  adapter reports completion.

  Neither these functions nor their nested inputs receive operation controllers,
  permission callbacks, claim registries, Jobs credentials or process-management
  objects. The host keeps identity and authority outside scientific arguments.
  Initialization has no job-specific authority. Cleanup remains possible after
  execution permission is revoked. Cooperative progress/cancellation hooks can
  be added when a real contribution needs them; do not build that protocol now.

Local hosting and pool
  Use existing runner.py, RunnerSession and AsyncRunnerSession for child lifetime,
  control ownership and retirement. Deployment supplies a fixed worker command
  and permitted environment; Jobs cannot supply commands or import paths. The
  runner currently inherits its environment, so provision its supervisor without
  Jobs credentials. This commit adds no sandbox or container-management system.

  Configure a fixed list of local allocations and their resource grants against
  registered implementations. One registration can supply several allocations;
  mixed registrations use the same pool code. Each allocation initially accepts
  one active analysis, including its prepared state. This is an explicit first
  backend limit, not a permanent scientific API or topology requirement.

  Reuse the separate science socket for a small bounded command/reply format.
  Keep lifecycle framing separate. The host reads only the operational envelope;
  scientific bytes remain opaque. Bound message sizes and retained operations,
  and refuse admission when capacity is exhausted rather than creating an
  unbounded command queue. Fixed grants must fit deployment limits; no new global
  allocator or phase scheduler in this commit.

  Keep registration identity, worker incarnation and analysis/dispatch identity
  separate. The existing RunnerSession operation identifies the child/control
  lifetime, which can span several analyses. Do not rename it into a per-analysis
  identity or create a second registry of process owners. Match worker readiness
  to its configured registration and incarnation before accepting science. A
  prepared handle binds its analysis and exact worker incarnation, stays
  single-use and is invalid after retirement. No moving or reconstructing live
  prepared state.

  Record the original operation before awaiting startup or sending a command.
  The operational caller supplies a host-only permission check. Run it immediately
  before each managed scientific dispatch, including prepare and after any wait
  for readiness/capacity. Have no unchecked queue of future scientific commands.
  This checks permission at dispatch; it does not promise an atomic remote check
  at the later numerical instruction. Existing AnalysisSession guards stay.

  Waiting again observes the same operation. Cancelling or timing out a waiter
  never resubmits science, frees its slot or renews the operation's deadline.
  Keep original science readers and control observations owned. A result, finished
  analysis cleanup and confirmed worker retirement are separate events. Reuse a
  warm worker only after analysis state/readers are settled; release its physical
  allocation only after the existing supervisor confirms retirement. Keep a
  received result if cleanup fails. If partial initialization/preparation leaves
  uncertain state, retain and retire that worker rather than pretending no work
  was acquired. Starting, held and uncertain workers count against the fixed cap.

  Stop admission during drain, observe accepted work and run its cleanup, then
  close instances and confirm worker retirement. A bounded drain may report work
  still held; it cannot call that work finished. No automatic scientific retry,
  unbudgeted replacement, durable crash recovery or central publication claim.

Focused checks that accompany this commit
  1. Direct and hosted calls produce the same example results with the same bound
     settings. Exercise both contribution shapes and repeat analyses on a warm
     instance. No Jobs service or scientific dependencies are available.
  2. With one allocation, another analysis is refused while it is occupied. With
     two, hold A's original cleanup/retirement observation and let B finish; A
     stays unavailable until its own observation arrives. Release the hold after
     an observed event. Change worker count without changing contribution code.
  3. Refuse a revoked dispatch and wrong, stale or consumed prepared handles
     before their scientific effect. Check revocation after readiness and between
     preparation and run. Inspect what reaches the scientific hooks.
  4. Cancel a waiter or fail initialization/cleanup and keep the original owner,
     result where available and resource charge. Drain reports a remaining hold
     honestly. Existing supervisor tests already cover its TERM/KILL/reap logic.

Use make tests/unit/provider-core with the existing Docker context/wheelhouse;
it builds an installed wheel and also runs the dependency-pure native suite.
Use the relevant integration tests if existing session behavior is changed.
No fuzz expansion, separate expected-state engine, stress matrix or all-provider
native campaign is required for this generic increment. A few actual-process
scenarios check its new behavior; they are not a new testing project.

Not included: Jobs discovery/admission/delivery (M2), real adapters/service
replacement (M3), phase-specific allocation (M4), stronger reconciliation (M5),
crash-durable operations/results (M6), remote execution or batching (M7), release,
dependency repins and deployment. Do not turn these omissions into restrictions
on the scientific interface.

Done when both contributions work directly and through the installed common

authority and ownership checks above. Report which examples and commands passed.
Then build real adapters and the common service together; do not open another
general validation phase before proceeding.

6. Preserve work across a supervisor crash
------------------------------------------
Tier 1. G06. Required for unattended crash recovery; not a Tier-0 prerequisite.

[ ] M6.1 Save operation identity and intent before dispatch. Define what the
    backend records when it accepts work, which status/results survive a crash,
    and how a new supervisor reattaches or refuses unsafe recovery.
[ ] M6.2 Save the exact final report until durable delivery accepts it. Resolve

    Keep the existing publisher and the same report identity and bytes on retries.
[ ] M6.3 Make the execution backend reject obsolete supervisors. Check duplicate

[ ] M6.5 Check upgrade and rollback: new work goes to the new workers while old
    work finishes or transfers with verified ownership. A result hash cannot
    reconstruct the result, and a timeout cannot transfer ownership.

    Claims of failover require M6's recovery checks.
[ ] M7.4 Reuse deployment, image, acquisition and identity tools for worker count

Done when: these operational choices use configuration and the same scientific

The finished system
--------------------
Providers supply scientific code, settings, capability/resource requirements
and a small integration test. Shared code supplies the service, worker management,
recovery, delivery and deployment mechanisms. Science remains callable without
Jobs authority. Worker count and compatible placement change through configuration.
Tier 0 is useful while later work is still being built.
