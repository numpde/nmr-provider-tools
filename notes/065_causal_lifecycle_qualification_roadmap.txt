Plan: build the shared package, then extend it
==============================================
2026-11-09 | Design: note 066 | Reviewed runtime: 1178115, SDK 0.6.8

What to build next
------------------
Start M1 now. Make the same scientific code work directly, then through shared
code that runs it on one or two workers. Connect the first real provider and make
the whole service work: find a job, run the science, keep the result, deliver it
and shut down properly.

Scientific code supplies the model, settings, input interpretation and numerical
work. The shared service chooses jobs and assigns resources. The execution host
is the shared code that loads the scientific implementation and calls it. The
service passes input through without interpreting peaks, choosing weights or
creating framework-specific device objects. Note 066, section 7, explains these
three interactions and who supplies each input.

Existing worker counts and process layouts can change. One and several workers
must use the same scientific code. Keep scientific behavior and the protections
in note 064; replace incidental restrictions of the old service loops.

This note sets the work order. Note 066 describes the intended system and lists
unfinished work as G01-G12. Note 064 records earlier source reviews and useful
tests. Older instructions to qualify all existing services first are superseded.

Build in this order
--------------------
Tier 0 -- Make a useful local package. Complete M1, M2 and the first SECS
integration (M3.3). Include fixed one/two-worker settings, result delivery and
orderly shutdown. Keep permission checks, separate job state, resource limits
and exact ownership of work. Where automatic recovery is missing, retain
uncertain work and explain the supported operator action. A restart never
authorizes repeating work whose outcome is unknown.

Use a few deterministic tests through the installed service and actual workers:
finish a job and hand its result to the existing delivery queue, which preserves
accepted reports across restarts; hold worker A while B finishes, then settle A
when its original evidence arrives;
reject revoked permission and handles from the wrong worker; retain unfinished
work and selected results during shutdown. Local queue acceptance and central
API publication are separate events. These tests accompany implementation.

Tier 1 -- Connect the other providers, allocate resources separately for each
stage, improve recovery, preserve work across supervisor crashes, and add a
real remote execution backend. M3-M6 and M7.3 describe this work. Tier 0 may
reserve resources for a whole operation until the finer controls exist.

Tier 2 -- Improve speed or resource use where measurements justify it. Examples
are adjusting worker counts automatically and processing compatible jobs in
batches. M7.1/M7.2 cover these changes. All tiers extend the same working system.

Keep testing proportional to the change. Fix a demonstrated defect with a
focused regression test. Large generated-test campaigns, elaborate models of
expected state, stress runs and broad compatibility testing come later when
they answer a concrete question. M0.3/M0.4 do not block M1. Stop expanding tests
once the changed behavior is adequately checked. Known permission, ownership
or scientific-correctness failures still block the affected feature.

Work on main in small commits that each leave something runnable. Include the
code, necessary tests and installation changes together. Explain what changed,
what ran and what remains unfinished. Append history. Releases, dependency
repins and deployment changes need their own authorization and checks.

1. Run the same science on one or two workers
---------------------------------------------
Tier 0. Starts G01/G02/G04/G10 and supports later resource and provider work.

[ ] M1.0 Keep three inputs separate: deployment supplies configured science and
    model files; the service supplies work, permission and limits; the host calls
    scientific functions with their own inputs. Those functions must not receive
    controllers, claim registries, ProviderAPI, ReportCondition, Jobs credentials,
    the global resource allocator or Docker access, including through nested objects.
[ ] M1.1 Give the offered analysis, scientific implementation and particular worker
    separate identities. A replacement worker is a new instance even in the same
    slot. The host tracks operations, permission and reserved resources. Reuse
    analysis.py and existing runner helpers; add modules only as real code needs them.
[ ] M1.2 Build a fixed group of local workers using existing process supervision.
    Configuration chooses one or two copies of the same scientific code. Track
    workers from startup through readiness, use and shutdown, including partial
    startup. Load the bound settings/model files once per instance; the service
    does not interpret them. Pass per-job scientific settings through unchanged.
[ ] M1.3 Use test science that permits only one call at a time per worker. Hold A's
    original cleanup while B finishes; keep A unavailable until its evidence arrives.
    Also check the one-worker limit. Use a small deterministic actual-worker test.
[ ] M1.4 A prepared handle refers to scientific state prepared for an analysis.
    It must match its implementation and, when worker-bound, the exact worker
    instance. Reject wrong or old handles. Portable prepared data can move before
    dispatch, but portability never permits replaying an operation that may
    already have run.
[ ] M1.5 Connect SECS through a small adapter. A serial worker protocol can limit
    each worker without limiting SECS to one worker overall. Remove collisions
    between copies in mutable globals, scratch names and source-file access.
    Keep the loaded model's identity explicit.
[ ] M1.6 Run the same scientific operations directly without Jobs and through the
    host with one/two workers. Check one-time initialization, separate state per
    analysis and model-specific cleanup. Scientific code checks whether settings
    and model files make sense; a matching file hash alone cannot do that. The
    host rejects revoked work before calling science. Returning from scientific
    cleanup does not by itself prove the worker and all its readers have stopped.

Done when: the same real science works directly and through one/two workers.
Changing worker count needs no scientific code change. Any temporary adapter
restriction has a reason and a stated way to remove it.

[ ] M2.2 Combine resource reservation with AttemptClaims/AttemptController.

[ ] M2.5 Support refusing new jobs, stopping/finishing active work, handing off

4. Reserve resources for the stage that needs them
-------------------------------------------------
Tier 1. G03/G04. Tier 0 already limits resources, but may reserve them for the
whole operation.

[ ] M4.1 Track separate limits for control work, waiting/prepared inputs, loaded
    models, active CPU/GPU work, uncertain workers and retained results. Prevent
    competing implementations from overcommitting a device. Across processes,
    use one shared allocator or enforce non-overlapping resource grants.
[ ] M4.2 Let the host acquire resources from declared stage requirements. Waiting
    for a prose-model reply should not occupy an otherwise usable GPU. Preparation
    that really uses a GPU must retain the required worker/handle relationship.
    Scientific code still chooses prompts, tools and input interpretation.
[ ] M4.3 Limit prepared-item counts, bytes and waiting time. Acquire combined
    resources together or in a consistent order to avoid deadlocks. Check
    cancellation during partial acquisition. Starting workers count against
    limits until their actual outcome is known.
[ ] M4.4 Support portable data before dispatch and worker-bound handles where
    necessary. Never repeat accepted preparation to conceal a failed move.
    Keep credentials, input files and scratch state isolated when workers are reused.

Done when: waiting on conversation or delivery does not unnecessarily occupy
compute, and every queue and retained resource remains bounded.

5. Recover automatically when enough information arrives
---------------------------------------------------------
Tier 1. G05/G07.

[ ] M5.1 Return clear typed results for continued observation, accepted delivery,
    uncertain work, safe resource release and final resolution. Keep permission,
    stopped effects and final job outcome separate. These are shared service
    decisions; scientific functions do not receive new controller arguments.
[ ] M5.2 Improve release after cancellation only where authoritative API state
    and backend dispatch/termination evidence support it. Keep f26ef5f's present
    conservative rule until the replacement is tested. A zero execution counter
    in a test is not runtime proof that no effect occurred.
[ ] M5.3 Separate unresolved job records from occupied resources. Once work is
    proven stopped, its job can remain excluded from retry without holding a GPU
    forever. Unknown work still counts against possible occupancy. Bound retained
    records and define retention/compaction and alerts; never discard identities
    silently when storage fills.
[ ] M5.4 Resume cleanup/recovery when new evidence arrives, even while new jobs
    are refused. Repeated observation must not restart deadlines or submit science
    again. Report exactly what information or resource is still missing.

Done when: supported recoverable failures no longer need routine restarts.
Unresolved cases stay explicit and affect only the scope justified by the evidence.

6. Preserve work across a supervisor crash
------------------------------------------
Tier 1. G06. Required for unattended crash recovery; not a Tier-0 prerequisite.

[ ] M6.1 Save operation identity and intent before dispatch. Define what the
    backend records when it accepts work, which status/results survive a crash,
    and how a new supervisor reattaches or refuses unsafe recovery.
[ ] M6.2 Save the exact final report until durable delivery accepts it. Resolve
    lost acknowledgements by checking the receiving component's stored state.
    Keep the existing publisher and the same report identity and bytes on retries.
[ ] M6.3 Make the execution backend reject obsolete supervisors. Check duplicate
    dispatch, late replies and ownership transfer. An expired lease alone does
    not prove the old process can no longer run.
[ ] M6.4 Interrupt the supervisor around intent, send, acceptance, completion,
    result storage and outbox handoff. Restart and check reattachment, safe
    resolution or an explicit unresolved hold. Do not repeat uncertain science
    or claim exactly-once execution where the backend cannot establish it.
[ ] M6.5 Check upgrade and rollback: new work goes to the new workers while old
    work finishes or transfers with verified ownership. A result hash cannot
    reconstruct the result, and a timeout cannot transfer ownership.

Done when: each supported backend meets its stated crash/upgrade guarantees.
List the remaining failure windows.

The finished system
--------------------
Providers supply scientific code, settings, capability/resource requirements
and a small integration test. Shared code supplies the service, worker management,
recovery, delivery and deployment mechanisms. Science remains callable without
Jobs authority. Worker count and compatible placement change through configuration.
Tier 0 is useful while later work is still being built.
