Roadmap: useful shared execution, then broader capability and assurance
=====================================================================
Revised 2026-11-09 | Target: note 066 | Source baseline 1178115
Priority revision: executable capability first; assurance proportional to risk

Authority and delivery practice
-------------------------------
066_provider_execution_end_state.txt defines the target architecture and gaps
G01-G12. This roadmap replaces the earlier preserve/extract-serial/add-lanes
sequence. Notes 058, 060, 061 and 064 retain their historical source/evidence
records; 064's S1-S8, I1-I2 and L1-L3 remain behavioral contracts. They do not
require completing a general validation harness before implementing the service.

Do not promote current provider topology into requirements. The shared platform
must support multiple allocations of the SAME scientific implementation before
its interface is declared complete. A one-worker deployment is a configuration,
not a first service architecture that later needs replacing. Characterize current
providers only to protect scientific semantics and identify bridges. Obsolete
polling, fail-stop, lifetime or lane assumptions may intentionally change.

The orchestrator routes opaque work and operational authority to an execution
interface. Deployment/registration binds the scientific implementation, its
configuration and assets. The host invokes scientific initialization and analysis;
it does not make the scheduler choose weights, scientific parameters or device
library objects. Section 7 of 066 defines input provenance, invocation surfaces,
loaded-instance/per-analysis lifetimes and the authority that must not leak into
numerical functions. Build these boundaries into the first runnable capability,
not a separate speculative framework or catch-all execution-context object.

Work on main in small, complete, runnable capability increments. Include tests,
installation support and required integration in the same coherent increment;
do not land unused abstractions merely to match the outline. Use a focused red
witness and owning fix for a genuine defect, not as the cadence for all build-out.
Append history. Each commit body records purpose, changed capability, executed
checks and limits. Report planned/implemented/omitted/added/verified in chat.
No automatic dependency publication, deployment cutover or runtime-policy change
is authorized by a planning note.

Priority gradient and acceptance
--------------------------------
Tier 0 -- A useful local package. Implement M1, M2 and the first SECS migration
as complete runnable increments: directly callable science, configured hosting,
fixed one/two-allocation pools and the service path through durable result handoff
and drain. Keep permission, exact ownership, isolation, bounded resources and
safe handling of uncertain work in this tier. A documented hold/manual resolution
is acceptable where automatic recovery is not yet implemented; restarting or
forgetting an owner must never manufacture permission to repeat uncertain work.

Tier 0 acceptance uses a small set of deterministic scenarios through the actual
installed host/service/worker boundary: input to result and durable local handoff;
one/two allocations with A held while B completes and A later settles; revoked
dispatch and stale handles refused; original resources/results retained through
stop and drain. Reuse fixtures and combine related observations in these scenarios.
API publication remains distinct from local handoff. Checks accompany the
capability that needs them. Direct science and the first real adapter must work;
a mock-only universal interface is insufficient.

Tier 1 -- Useful extensions. Migrate the remaining providers (M3), separate phase
allocation and bounded staging (M4), improve reconciliation (M5), add durable
supervisor recovery (M6), then a concrete remote backend (M7.3). These stay explicit
functional gaps; each becomes an acceptance requirement when that capability is
claimed. Existing conservative aggregate reservations and recovery limits can
bridge Tier 0 safely. All four migrations are the adoption goal, not its entry gate.

Tier 2 -- Measured optimization. Adaptive residency/replica policy and batching
(M7.1/M7.2) follow a demonstrated workload benefit. They extend the same Tier-0
execution path. Higher tiers must not replace it with an alternative architecture.

Validation supports these tiers. Preserve required guards and focused checks for
changed behavior; add a deterministic regression for a demonstrated defect. Broader
state-machine oracles, shrink/replay machinery, stress, compatibility matrices and
provenance automation are later assurance work justified by a concrete risk or
recurring need. M0.3/M0.4 and all-gap closure are NOT prerequisites to M1 or Tier 0.
Stop expanding checks once the changed contract is sufficiently exercised. A
known permission, ownership or scientific-correctness defect still blocks the
affected capability; a missing optional harness does not block unrelated work.

1. First new capability: one implementation, multiple owned allocations
----------------------------------------------------------------------
Closes the initial part of G02/G04/G10 and establishes G01's invocation boundary;
provides the foundation for G03/G12. Tier 0; begin now with runnable increments.

[ ] M1.0 In the first hosted example, distinguish configuration/asset binding,
    the operational dispatch envelope and the scientific callable's arguments.
    Use note 066 section 7's provenance map. No numerical hook receives a
    controller, registry, ProviderAPI, ReportCondition, Jobs credential, global
    allocator or Docker manager, directly or through a catch-all context.
[ ] M1.1 Separate offering and implementation identity from allocation identity
    and incarnation. Specify actual resource reservation and retirement evidence.
    Keep operation/Attempt authority in the host/backend envelope, not mandatory
    numerical arguments. Start beside existing analysis.py and runner helpers;
    proposed service/allocation modules are choices, not mandatory files.
[ ] M1.2 Build a small fixed local pool around existing runner supervision.
    Configuration selects one or two replicas of the SAME implementation; the
    scientific adapter source is identical. Pool startup, partial allocation,
    readiness, reservation, drain and reuse have owned outcomes. Bind versioned
    configuration/assets at initialization, without rebuilding them per Job or
    making the scheduler understand their schema. Keep per-Job parameters opaque.
[ ] M1.3 Use an explicit non-reentrant test adapter in two independent real worker
    allocations. Exercise distinct operations, held cleanup in A while B
    completes, no reuse of A, and correct recovery when A's original evidence
    arrives. Check that a configured pool of one admits only one allocation.
    Use one causal fixture for this contract; no generated oracle is required.
[ ] M1.4 Bind prepared handles to the correct implementation and, when necessary,
    allocation incarnation. Reject stale/mismatched handles. Support a portable
    candidate through explicit immutable identity without claiming replay rights.
[ ] M1.5 Introduce the first thin real-model bridge, with SECS a suitable initial
    consumer. Any serialized worker protocol is a temporary per-allocation
    constraint, not a global SECS lock. Inventory mutable globals, scratch names,
    source grants and model-load identity; remove cross-replica collisions.
[ ] M1.6 Run the same scientific operations directly without a live Jobs service,
    then through the host with one/two allocations. Verify initialization once
    per actual instance, isolated per-analysis state and scientific disposal
    distinct from full allocation retirement. Model configuration validation
    belongs to the contribution; asset digest verification alone cannot admit
    an incompatible model. Host dispatch of revoked work must fail before the
    scientific effect without asking science to interpret an Attempt.

Exit: the shared execution capability works with one/two allocations and the
same directly callable scientific implementation. The scheduler routes work;
configuration/asset semantics remain in the contribution. A real scientific or
backend limit has an evidence-backed bridge, not a singleton architecture.

4. Resource-efficient pipeline and placement
--------------------------------------------
G03/G04. Tier 1, after the shared reservation boundary is exercised. Tier 0 uses
bounded aggregate reservations; limits/isolation are already required there.

[ ] M4.1 Add separate budgets for control, staged inputs/preparations, model
    residency, active CPU/GPU work, uncertain allocations and terminal custody.
    Reject overcommit across implementations sharing one physical device.
    Across processes require a shared allocator or enforced disjoint grants.
[ ] M4.2 Acquire compute in shared hosting from declared phase requirements.
    Demonstrate that a blocked prose request does not reserve an otherwise usable
    GPU slot, while scientific preparation that DOES use the device retains the
    correct allocation/affinity. Domain tool selection and prompts remain in the
    contribution; scheduling must not construct scientific inputs to achieve this.
[ ] M4.3 Bound prepared count/bytes and queue wait. Implement ordered/atomic
    composite acquisition; test cancellation halfway through a resource request
    and competing phases that would otherwise deadlock. Cold starts remain
    owned and count against physical limits until their actual outcome is known.
[ ] M4.4 Exercise portable pre-dispatch placement and affinity-bound execution.
    Do not reload or recompute an accepted preparation to hide migration failure.
    Protect credential, source and scratch isolation when allocations are reused.

Exit: expensive execution capacity is not held solely because a conversation or
report is pending. Legitimate native affinity remains explicit, and all retained
resources and queues stay bounded. Stage separation is measured, not inferred
from a scheduler diagram.

5. Typed reconciliation and bounded automatic recovery
------------------------------------------------------
G05/G07. Tier 1. Extend current controller/executor contracts with owning evidence.

[ ] M5.1 Define a small typed decision surface for continued observation, accepted
    handoff, held uncertain work, eligible release and terminal reconciliation.
    Keep permission, physical closure and disposition separate. No provider needs
    to inspect a private checkpoint or reconstruct nested failures to schedule.
    These are operational interfaces, not new required numerical-function inputs.
[ ] M5.2 Qualify stronger post-entry reconciliation where authoritative API state
    and backend dispatch/termination evidence justify it. Preserve f26ef5f's
    conservative current guard until the replacement is proved. A test science
    counter of zero is not itself runtime proof that no effect occurred.
[ ] M5.3 Separate active execution reservations from bounded unresolved records.
    Proven-quiescent excluded Jobs may remain reconciliable without occupying
    free GPU slots. Unconfirmed work remains charged. Reconciliation storage
    needs explicit bounds, retention/compaction rules and alerts; overflow must
    not silently forget identities or stop unrelated bindings unnecessarily.
[ ] M5.4 Prove automatic resumption on new evidence while admission is closed,
    repeated observations without renewed deadlines, and no second scientific
    submission. Diagnose exactly which authority/resource blocks remaining work.

Exit: recoverable failures do not require routine operator restarts. Irreducible
uncertainty remains explicit and safe, scoped as narrowly as the evidence allows.

6. Durable operations and supervisor replacement
------------------------------------------------
G06; Tier 1, required for unattended crash recovery. It does not gate the first
local pooled release. This is a tracked end-state requirement, not an indefinite
exclusion from scope.

[ ] M6.1 Specify durable operation intent/identity before dispatch and backend
    status/result custody. Define which backend acknowledges a committed command,
    what survives supervisor death, and how the successor reattaches or refuses.
[ ] M6.2 Persist the exact selected terminal until verified transfer to durable
    delivery. Reconcile lost acknowledgements against authoritative custody;
    preserve the existing publisher and exact terminal idempotency identity.
[ ] M6.3 Fence obsolete supervisors at the execution receiver. Prove duplicate
    dispatch refusal, late-response rejection and ownership transfer across a
    crash; no lease-expiry-only inference that the old computation ended.
[ ] M6.4 Kill the supervisor at intent, send, acceptance, execution completion,
    result retention and outbox handoff boundaries. Restart and prove reattachment,
    safe disposition or explicit held uncertainty with no duplicate science.
    Unsupported backend ambiguity is visible, not a claim of exactly-once compute.
[ ] M6.5 Qualify rollout/rollback with new work routed to the new pool and original
    work drained or transferred under evidence. A digest-only checkpoint is not
    a recoverable result and a timeout is not permission to replace an owner.

Exit: crash recovery and rolling replacement satisfy the stated durability level
for each supported backend. Record the remaining unsupported failure windows.

--------------------------------------------------------------
G08/G09/G10. M7.1/M7.2 are Tier 2; the concrete remote capability M7.3 is Tier 1
after its prerequisites. M7.4 applies to the deployment being added. These labels
set priorities, not a demand to finish every earlier numbered item first.

[ ] M7.1 Measure model-load cost, resident/peak memory, queue wait, useful execution
    concurrency, isolation and numerical equivalence. Add bounded warm/idle and
    demand-driven replica policy using those measurements, with stable configured
    limits and no replacement storm around uncertain instances.
[ ] M7.2 For an actual scientifically compatible consumer, add batch admission
    and per-member mapping, permission, failure and cancellation handling. Preserve
    other members after one cancellation. Unsupported batching remains explicit;
    no adapter must pretend different Jobs are one scientific operation.
[ ] M7.3 Add one real remote/managed-service backend using the established
    operation/reservation contract. Require authenticated grants, authoritative
    capacity, receiver-enforced owner generations, partition/rejoin handling and
    durable receipt semantics. M6 evidence is required for failover claims.
[ ] M7.4 Reuse existing deployment/image/acquisition/identity owners to configure
    pool count and placement. Science containers receive minimum grants, never
    host Docker access merely to scale themselves. Test missing devices, stale
    artifacts, denied mounts/credentials and incompatible generations explicitly.

Exit: operational changes use declarations/configuration instead of adapter forks.
A minimal local installation still requires no remote coordinator, cluster or
batching feature. Expensive optimization is accepted only with measured benefit
and the same scientific/ownership contract.

-----------------------------------------------------

    G01 invocation/service boundary (M1/M2/M3);

    G09 remote authority (M7); G10 deployment (M1/M7); G11 scoped test fidelity

    system or requirement to close every gap before Tier 0 is accepted.
[ ] M8.2 Remove each legacy bridge with its working replacement and the focused
    test for the behavior it protected. Reuse M1/M2's one/two-allocation, affinity,
    authority and state-isolation scenarios rather than rebuilding that matrix
    in every provider. Retain a small actual adapter/host integration scenario.
[ ] M8.3 Select evidence for the changed boundary: deterministic lifecycle tests,
    actual subprocess/IPC for physical retirement, installed consumers for
    assembly, native/deployment runs for real-model/deployment claims. These are
    different scopes, not a ladder every change must climb. Stateful generation
    supplements them when useful; no universal fuzzer runtime is required.
[ ] M8.4 Repeat or add CPU contention only for a concrete scheduling/flakiness
    risk. Remove the earlier suggested ten/three repetition quota. Keep runs
    bounded and every failure visible; no retry-until-green. Fault gates follow
    observed events, and emergency teardown cannot supply a passing verdict.
[ ] M8.5 At an authorized release, identify and check the actual artifacts and
    affected consumer installations. A named local-pool release can leave broader
    recovery/remote/assurance gaps open. Do not require every consumer or a broad
    compatibility matrix for an unaffected subset. Installed claims use a wheel,

[ ] M8.6 Before an authorized deployment, stop old admission and settle or verify
    durable transfer of obligations. Preserve outbox rows and old owners that
    still hold work. Apply the same guard to rollback; never erase an unresolved
    operation to make a cutover or test pass.

End-state acceptance
--------------------
A provider supplies its science, configured implementation, capability/resource
requirements and a small installed qualification fixture. Shared code supplies
service, execution hosting/pools, recovery and deployment mechanisms. Scheduling
routes opaque work; scientific setup and meaning remain in the contribution.
Numerical code can run without Jobs/Attempt authority. Replica count, compatible
placement and residency are operational choices, not scientific rewrites.
The platform preserves scientific meaning and real ownership obligations while
retiring incidental constraints of current implementations. Tier 0 is useful
before this end state is complete; later capability gaps stay visible. Required
guards are never deferred merely because broader assurance work is deferred.
