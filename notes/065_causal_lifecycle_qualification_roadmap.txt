Plan: adopt the common interface, then improve implementations
===============================================================
2026-11-09 | Design: note 066 | Reviewed runtime: 1178115, SDK 0.6.8

What to build next
------------------
Start M1 with one coordinated implementation across provider-core, SECS, NMRNet,
NMRPeak and Magnet. Put the lasting contribution and execution interfaces into
use in every repository first. Both the scientific worker/direct path and the
guarded provider path must use them. Existing service loops and native protocols
may remain behind temporary bridges while this boundary is adopted.

After all five repositories use that boundary, improve their implementations
independently: shared pools, common service mechanics, recovery and deployment.
No provider defines the interface for the others. New providers register their
contributions through the same contract.

Scientific code supplies the model, settings, input interpretation and numerical
work. The shared service chooses jobs and assigns resources. The execution host
is the shared code that loads the scientific implementation and calls it. The
service passes input through without interpreting peaks, choosing weights or
creating framework-specific device objects. Note 066, section 7, explains these
three interactions and who supplies each input.

Existing worker counts and process layouts can change. One and several workers
must use the same scientific code. Keep scientific behavior and the protections
in note 064; replace incidental restrictions of the old service loops.

This note sets the work order. Note 066 describes the intended system and lists
unfinished work as G01-G12. Note 064 records earlier source reviews and useful
tests. Older instructions to qualify all existing services first are superseded.

Build in this order
--------------------
Tier 0 -- First adopt the common interface across all five repositories as the
coordinated set of runnable commits in section 1.1. A shared definition used only
by examples, or adapters that leave the real call path unchanged, do not complete
that step. Existing backend/service implementations can remain behind it.

Then complete M1's fixed one/two-worker pool, M2's common service and M3's service
replacement across the four providers. Those changes can proceed independently
behind the adopted contracts. Include result delivery and orderly shutdown.
Keep permission checks, separate job state, resource limits and exact ownership
of work. Where automatic recovery is missing, retain uncertain work and explain
the supported operator action. A restart never authorizes repeating unknown work.
Full Tier 0 includes the shared service and worker management in all four providers;
interface adoption is the first useful checkpoint, not the whole tier.

Use a few deterministic tests through the installed service and actual workers:
finish a job and hand its result to the existing delivery queue, which preserves
accepted reports across restarts; hold worker A while B finishes, then settle A
when its original evidence arrives;
reject revoked permission and handles from the wrong worker; retain unfinished
work and selected results during shutdown. Local queue acceptance and central
API publication are separate events. These tests accompany implementation.

Tier 1 -- Allocate resources separately for each stage, improve recovery,
preserve work across supervisor crashes, and add a real remote execution
backend. M4-M6 and M7.3 describe this work. Tier 0 may reserve resources for
a whole operation until the finer controls exist.

Tier 2 -- Improve speed or resource use where measurements justify it. Examples
are adjusting worker counts automatically and processing compatible jobs in
batches. M7.1/M7.2 cover these changes. All tiers extend the same working system.

Keep testing proportional to the change. Fix a demonstrated defect with a
focused regression test. Large generated-test campaigns, elaborate models of
expected state, stress runs and broad compatibility testing come later when
they answer a concrete question. M0.3/M0.4 do not block M1. Stop expanding tests
once the changed behavior is adequately checked. Known permission, ownership
or scientific-correctness failures still block the affected feature.

Work on main in small commits that each leave something runnable. Include the
code, necessary tests and installation changes together. Explain what changed,
what ran and what remains unfinished. Append history. Releases, dependency
repins and deployment changes need their own authorization and checks.

1.1 First coordinated implementation: adopt the interface in all repositories

This is a small set of commits across five repositories, not an atomic Git
commit and not a new pool built before any real consumer. Keep each main branch
runnable. The core implementation, provider adaptations and required dependency
updates belong to one coordinated change; independent feature work follows it.

First provider-core commit
  Proposed title: Add common contribution and execution interfaces with guarded
  operation ownership

  Add packages/provider-core/src/provider_core/contribution.py. Define configured
  factories and a small registered map of named scientific calls. Calls may be
  inspect, validate, prepare, predict or generate; no universal phase sequence is
  imposed. A contribution declares the requirements and state use for each call,
  and supplies scientific cleanup. Input/result codecs and model interpretation
  remain contribution-owned. Factories and functions receive no operational
  controller or catch-all context. Include working invocation code used by the
  adapters, rather than stopping at Protocol declarations.

  Add packages/provider-core/src/provider_core/hosting.py. Define identified
  requests, opaque state references, original operations and their observations.
  Implement the shared operation/guard helpers that the first backends actually
  use. An operation owner exists before awaiting or dispatching. Observation has
  its own waiting allowance and cannot restart the original execution budget.
  A stop request, scientific outcome, analysis cleanup, instance retirement and
  result handoff remain separate. Preserve original errors and protected context;
  transport errors are not automatically scientific rejections or public failures.

  Preserve execution.py and analysis.py as the existing API-side integration.
  Their bridge binds the current ReportCondition check to the operational host
  path, translates verified Job input and scientific results, and retains existing
  guards. Check permission immediately before each actual managed dispatch,
  including after readiness waits or scientific tool turns; never pass that guard
  into science. Neither new native module imports API clients or scientific
  frameworks. Keep local wire codecs out of both new public modules. Reuse owners;
  do not introduce another claim registry or duplicate process ownership.

  Local science framing and RunnerSession/AsyncRunnerSession stay in the existing
  native backend. Their control-lifetime identity is distinct from an individual
  scientific call. No new socket protocol, general worker launcher, fixed pool,
  remote backend or shared service is required for this commit.

  Exercise a working bridge and actual runner path using existing fixtures and
  installed-wheel lanes. The native dependency check covers the new modules.
  Update the package README with the three boundaries and direct/hosted examples.
  Small examples support the implementation, but do not close the all-repository
  adoption checkpoint.

6. Preserve work across a supervisor crash
------------------------------------------
Tier 1. G06. Required for unattended crash recovery; not a Tier-0 prerequisite.

[ ] M6.1 Save operation identity and intent before dispatch. Define what the
    backend records when it accepts work, which status/results survive a crash,
    and how a new supervisor reattaches or refuses unsafe recovery.
[ ] M6.2 Save the exact final report until durable delivery accepts it. Resolve
    lost acknowledgements by checking the receiving component's stored state.
    Keep the existing publisher and the same report identity and bytes on retries.
[ ] M6.3 Make the execution backend reject obsolete supervisors. Check duplicate
    dispatch, late replies and ownership transfer. An expired lease alone does
    not prove the old process can no longer run.
[ ] M6.4 Interrupt the supervisor around intent, send, acceptance, completion,
    result storage and outbox handoff. Restart and check reattachment, safe
    resolution or an explicit unresolved hold. Do not repeat uncertain science
    or claim exactly-once execution where the backend cannot establish it.
[ ] M6.5 Check upgrade and rollback: new work goes to the new workers while old
    work finishes or transfers with verified ownership. A result hash cannot
    reconstruct the result, and a timeout cannot transfer ownership.

Done when: each supported backend meets its stated crash/upgrade guarantees.
List the remaining failure windows.

[ ] M7.2 Batch only scientifically compatible work. Preserve each member's input,

[ ] M7.3 Implement one real remote/managed-service backend. Use authenticated

The finished system
--------------------
Providers supply scientific code, settings, capability/resource requirements
and a small integration test. Shared code supplies the service, worker management,
recovery, delivery and deployment mechanisms. Science remains callable without
Jobs authority. Worker count and compatible placement change through configuration.
Tier 0 is useful while later work is still being built.
