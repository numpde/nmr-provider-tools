Roadmap: causal qualification and the target shared execution platform
======================================================================
Revised 2026-11-09 | Target: note 066 | Source baseline 1178115

Authority and delivery practice
-------------------------------
066_provider_execution_end_state.txt defines the target architecture and gaps
G01-G12. This roadmap replaces the earlier preserve/extract-serial/add-lanes
sequence. Notes 058, 060, 061 and 064 retain their historical source/evidence
records; 064's S1-S8, I1-I2 and L1-L3 remain the qualification obligations.

Do not promote current provider topology into requirements. The shared platform
must support multiple allocations of the SAME scientific implementation before
its interface is declared complete. A one-worker deployment is a configuration,
not a first service architecture that later needs replacing. Characterize current
providers only to protect scientific semantics and identify bridges. Obsolete
polling, fail-stop, lifetime or lane assumptions may intentionally change.

Work on main in small, complete, runnable capability increments. Include tests,
installation support and required integration in the same coherent increment;
do not land unused abstractions merely to match the outline. Use a focused red
witness and owning fix for a genuine defect, not as the cadence for all build-out.
Append history. Each commit body records purpose, changed capability, executed
checks and limits. Report planned/implemented/omitted/added/verified in chat.
No automatic dependency publication, deployment cutover or runtime-policy change
is authorized by a planning note.

1. First new capability: one implementation, multiple owned allocations
----------------------------------------------------------------------
Closes the initial part of G02/G04/G10; provides the boundary for G01/G03/G12.

[ ] M1.1 Separate offering and implementation identity from allocation identity
    and incarnation. Specify actual resource reservation and retirement evidence.
    Start beside existing analysis.py and runner lifecycle helpers; proposed
    service/allocation modules are implementation choices, not mandatory files.
[ ] M1.2 Build a small fixed local pool around existing runner supervision.
    Configuration selects one or two replicas of the SAME implementation; the
    scientific adapter source is identical. Pool startup, partial allocation,
    readiness, reservation, drain and reuse have owned outcomes.
[ ] M1.3 Use an explicit non-reentrant test adapter in two independent real worker
    allocations. Prove concurrent distinct Jobs, held cleanup in A while B
    completes, no reuse of A, and correct recovery when A's original evidence
    arrives. Also prove a configured pool of one admits only one allocation.
[ ] M1.4 Bind prepared handles to the correct implementation and, when necessary,
    allocation incarnation. Reject stale/mismatched handles. Support a portable
    candidate through explicit immutable identity without claiming replay rights.
[ ] M1.5 Introduce the first thin real-model bridge, with SECS a suitable initial
    consumer. Any serialized worker protocol is a temporary per-allocation
    constraint, not a global SECS lock. Inventory mutable globals, scratch names,
    source grants and model-load identity; remove cross-replica collisions.

Exit: the shared execution capability works with one/two allocations, including
failure isolation, before the service is designed around a singleton. A genuine
scientific/backend limit is stated narrowly and has an evidence-backed bridge;
there is no promise that the legacy worker itself suddenly becomes reentrant.

2. Build the common service around the allocation contract
----------------------------------------------------------
G01/G07 and the service part of G05. M1 supplies a real first consumer.

[ ] M2.1 Compose initial/periodic Hello and bounded fair discovery using existing
    ProviderAPI operations. Keep their API owners independent of scientific work
    and terminal handoff. A failed page does not restart an admitted operation.
[ ] M2.2 Integrate reservations with AttemptClaims/AttemptController admission.
    Reserve before effects, adopt partially created sessions/controllers before
    awaiting further work, and recheck permission at actual dispatch. Refused
    admission must leave no partial Job/START/resource ownership.
[ ] M2.3 Drive original controllers and maintain them independently of discovery,
    offered capability, spare capacity and open admission. Use owner-produced
    facts/dispositions, not provider-specific nested-exception inspection.
[ ] M2.4 Implement scoped cooldown and delivery pressure with bounded retry.
    Distinguish operation/allocation/implementation/binding/device/host failures.
    Quarantine only the affected scope when its evidence permits isolation.
[ ] M2.5 Implement common stop-admission, active-work stop, report drain and
    shutdown observations. Retain unconfirmed allocations and selected reports.
    Keep queue acceptance, API publication and physical retirement distinct.
[ ] M2.6 Remove displaced generic code from the first consumer in the same
    usable increments. Reuse the existing durable outbox/publisher; do not create
    a second terminal queue or another authoritative Attempt registry.

Exit: the first consumer uses the target service with both pool configurations.
A serial setting does not select a different scheduler implementation. Default
service behavior meets the new floor; no compatibility switch restores old
whole-provider stalls or maintenance dependent on new Job arrivals.

4. Resource-efficient pipeline and placement
--------------------------------------------
G03/G04. Can develop with M3 once the shared reservation boundary is exercised.

[ ] M4.1 Add separate budgets for control, staged inputs/preparations, model
    residency, active CPU/GPU work, uncertain allocations and terminal custody.
    Reject overcommit across implementations sharing one physical device.
    Across processes require a shared allocator or enforced disjoint grants.
[ ] M4.2 Acquire compute by actual phase requirements. Demonstrate that a blocked
    prose HTTP request does not reserve an otherwise usable GPU execution slot;
    demonstrate that scientific preparation which DOES use the device retains
    the correct allocation and any affinity-bound prepared state.
[ ] M4.3 Bound prepared count/bytes and queue wait. Implement ordered/atomic
    composite acquisition; test cancellation halfway through a resource request
    and competing phases that would otherwise deadlock. Cold starts remain
    owned and count against physical limits until their actual outcome is known.
[ ] M4.4 Exercise portable pre-dispatch placement and affinity-bound execution.
    Do not reload or recompute an accepted preparation to hide migration failure.
    Protect credential, source and scratch isolation when allocations are reused.

Exit: expensive execution capacity is not held solely because a conversation or
report is pending. Legitimate native affinity remains explicit, and all retained
resources and queues stay bounded. Stage separation is measured, not inferred
from a scheduler diagram.

5. Typed reconciliation and bounded automatic recovery
------------------------------------------------------
G05/G07. Extend current controller/executor contracts with owning evidence.

[ ] M5.1 Define a small typed decision surface for continued observation, accepted
    handoff, held uncertain work, eligible release and terminal reconciliation.
    Keep permission, physical closure and disposition separate. No provider needs
    to inspect a private checkpoint or reconstruct nested failures to schedule.
[ ] M5.2 Qualify stronger post-entry reconciliation where authoritative API state
    and backend dispatch/termination evidence justify it. Preserve f26ef5f's
    conservative current guard until the replacement is proved. A test science
    counter of zero is not itself runtime proof that no effect occurred.
[ ] M5.3 Separate active execution reservations from bounded unresolved records.
    Proven-quiescent excluded Jobs may remain reconciliable without occupying
    free GPU slots. Unconfirmed work remains charged. Reconciliation storage
    needs explicit bounds, retention/compaction rules and alerts; overflow must
    not silently forget identities or stop unrelated bindings unnecessarily.
[ ] M5.4 Prove automatic resumption on new evidence while admission is closed,
    repeated observations without renewed deadlines, and no second scientific
    submission. Diagnose exactly which authority/resource blocks remaining work.

Exit: recoverable failures do not require routine operator restarts. Irreducible
uncertainty remains explicit and safe, scoped as narrowly as the evidence allows.

6. Durable operations and supervisor replacement
------------------------------------------------
G06; required for unattended crash recovery, not a prerequisite for the first
local pooled release. This is a tracked end-state requirement, not an indefinite
exclusion from scope.

[ ] M6.1 Specify durable operation intent/identity before dispatch and backend
    status/result custody. Define which backend acknowledges a committed command,
    what survives supervisor death, and how the successor reattaches or refuses.
[ ] M6.2 Persist the exact selected terminal until verified transfer to durable
    delivery. Reconcile lost acknowledgements against authoritative custody;
    preserve the existing publisher and exact terminal idempotency identity.
[ ] M6.3 Fence obsolete supervisors at the execution receiver. Prove duplicate
    dispatch refusal, late-response rejection and ownership transfer across a
    crash; no lease-expiry-only inference that the old computation ended.
[ ] M6.4 Kill the supervisor at intent, send, acceptance, execution completion,
    result retention and outbox handoff boundaries. Restart and prove reattachment,
    safe disposition or explicit held uncertainty with no duplicate science.
    Unsupported backend ambiguity is visible, not a claim of exactly-once compute.
[ ] M6.5 Qualify rollout/rollback with new work routed to the new pool and original
    work drained or transferred under evidence. A digest-only checkpoint is not
    a recoverable result and a timeout is not permission to replace an owner.

Exit: crash recovery and rolling replacement satisfy the stated durability level
for each supported backend. Record the remaining unsupported failure windows.

7. Measured pool policy, batching and a concrete remote backend
--------------------------------------------------------------
G08/G09/G10. These are bounded additions, not a general orchestration framework.

[ ] M7.1 Measure model-load cost, resident/peak memory, queue wait, useful execution
    concurrency, isolation and numerical equivalence. Add bounded warm/idle and
    demand-driven replica policy using those measurements, with stable configured
    limits and no replacement storm around uncertain instances.
[ ] M7.2 For an actual scientifically compatible consumer, add batch admission
    and per-member mapping, permission, failure and cancellation handling. Preserve
    other members after one cancellation. Unsupported batching remains explicit;
    no adapter must pretend different Jobs are one scientific operation.
[ ] M7.3 Add one real remote/managed-service backend using the established
    operation/reservation contract. Require authenticated grants, authoritative
    capacity, receiver-enforced owner generations, partition/rejoin handling and
    durable receipt semantics. M6 evidence is required for failover claims.
[ ] M7.4 Reuse existing deployment/image/acquisition/identity owners to configure
    pool count and placement. Science containers receive minimum grants, never
    host Docker access merely to scale themselves. Test missing devices, stale
    artifacts, denied mounts/credentials and incompatible generations explicitly.

Exit: operational changes use declarations/configuration instead of adapter forks.
A minimal local installation still requires no remote coordinator, cluster or
batching feature. Expensive optimization is accepted only with measured benefit
and the same scientific/ownership contract.

[ ] M8.6 Before an authorized deployment, stop old admission and settle or verify
    durable transfer of obligations. Preserve outbox rows and old owners that
    still hold work. Apply the same guard to rollback; never erase an unresolved
    operation to make a cutover or test pass.

Final acceptance
----------------
A provider supplies its science, capability/resource requirements and a small
installed qualification fixture. Shared code supplies service, execution pools,
recovery and deployment mechanisms. Replica count, placement and residency are
operational choices. The platform preserves scientific meaning and real ownership
obligations while retiring incidental constraints of current implementations.
All remaining end-state gaps have a named owner, bridge and closing witness.
