B4: Recovery after the prose interpretation service returns
===========================================================
2026-11-06 | Implementation and local qualification
SDK branch: fix/release-settled-cancelled-attempts

Status
------
The B4 SDK changes are implemented and pushed. All four actual provider
loops/adapters have been exercised against the same immutable candidate wheel.
Their selected consumer checks pass, including complete finite-backlog drain
after restoring only the HTTPS service hosting the language model used for
prose interpretation.

Native worker and deployment qualification remains open. This is not a
package release. The candidate still identifies as provider-core 0.6.6;
identify it by checksum, not by that version string. Provider dependency pins
and the Magnet transport workaround remain unchanged.

The SDK, NMRPeak and private Magnet branches are published. SECS and NMRNet
have clean, tested local branches, but the GitHub connector denied creating
their remote branches with HTTP 403, "Resource not accessible by integration".
Their three-commit histories have been saved as verified Git bundles and
ordered patches. Their publication needs connector write access.

Adjacent SDK red/green pairs
---------------------------
1. Share the prose service's retry delay across Jobs.

   Red:   33f886ba5b4382c011f2ffb5939f4efc9e852e57
   Green: bf82fa5f785d7cd9d8b65b9b3de4e495f27aa58c

   Before the fix, a subsequent Job sent its request 0.216297 seconds after
   the previous Job received Retry-After: 1. The sustained-outage baseline
   sent seven requests during a fixed 1.2-second outage for either 12 or 120
   queued Jobs, exceeding the declared ceiling of two.

   ProseService now retains retry timing for one captured endpoint
   configuration across Jobs. Providers construct it once and reuse it.
   Each HTTP exchange still has its own owner. The existing two-send budget,
   retry classification, random backoff and original interpretation deadline
   remain authoritative. A wait is interruptible by interpreter retirement.
   Waiting or retrying the HTTP exchange does not restart preparation already
   accepted for its original Attempt.
   An older in-flight success cannot clear a newer service refusal.

2. Report elapsed waits with the original retained failure or report.

   Red:   956078e6178d41d6b9f9e812f767302b6a7b192b
   Green: 3d1ce84496683eeb08963956e43225147ebe076d

   Publication notices now identify the elapsed work on that exact retained
   report. Recovery is reported only after its matching receipt from the
   central NMR Jobs API and successful removal of its local queue row.
   A different report's success cannot clear an unresolved report.

   ExecutionFailed diagnostics retain the original lifecycle failure's age.
   This is historical evidence, including after eventual settlement; it is
   not proof that a claim is still held or time since the last progress.
   The original controller and the existing queue overview remain the
   authorities for live ownership and queued-report age.

3. Warn if an accepted report's publication remains pending.

   Red:   39559384b6f1bf01fce022dec43d529cf635a6d4
   Green: 17c2fe1512aedb4b20b094032f130314a1fe1d61

   The red received a matching publication receipt over the configured TLS
   connection to a local peer representing the central NMR Jobs API, then
   held the original offloaded queue removal open.
   The publisher retained the row and storage operation but emitted no
   notice after the observation budget elapsed.

   One timer now emits delivery_stalled with the original report identity,
   elapsed publication wait and whether the API receipt has arrived.
   Its budget is the captured API exchange allowance plus retirement
   allowance plus maximum retry delay. Retries cannot renew it.
   The timer observes the original operation; it does not cancel storage,
   resend a report or transfer ownership. Recovery follows that same row's
   completed removal. The timer is cancelled when its publication call ends.

   Passing guards also cover stop while queue removal is blocked, a failed
   first diagnostic write, and absence of a stale warning after early
   success. Diagnostic output failure does not replace the storage owner.

Final SDK outage measurements
----------------------------
One complete chat-suite run captured six cases. The three-second recovery
limit was declared before execution. Receipt times below refer to the first
successful affected Job whose START occurred after service restoration:

  Outage / queued Jobs             Requests / ceiling    New receipt
  Retry-After: 1 / 12               1 / 2                 0.427 s
  Retry-After: 1 / 120              1 / 2                 0.515 s
  HTTP 503 without delay / 12      2 / 5                 0.395 s
  Invalid Retry-After / 12          2 / 5                 0.643 s
  Disconnected request / 12        2 / 5                 0.687 s
  Blocked response headers / 12    4 / 4                 0.289 s

The outage lasts 1.2 seconds except for blocked response headers, which last
2 seconds. Each case uses a real local TLS peer, the installed SDK, real
Attempt controllers, the supervised HTTP child, a counting scientific
subprocess, a SQLite outbox and a publisher sending signed requests to a TLS
peer representing the central NMR Jobs API. That peer returns the matching
publication receipt. The fixture's admission loop is an SDK test driver; the consumer
tests above exercise the actual provider admission loops.

The original pending report receives its matching API receipt during the
prose-service outage, and the independent healthy route publishes during
that same outage. All original report bytes are preserved. All 14 reports
drain in each small case; all 122 drain in the 120-Job case, within 22.877
seconds of restoration. Failed terminal Jobs retain their failure reports.

All six cases preserve the scientific worker PID and one model load.
Each successful scientific operation occurs once. Claims and queued rows
return to zero; every HTTP child exit is observed; all peer connections close;
socket and pipe descriptor counts return to baseline before fixture teardown.
The blocked-response case retains its original TimeoutError diagnostic.
