One shared API proxy for the four providers
==========================================

Governing guidelines from the joint refactor
--------------------------------------------

These summarize the agreed engineering directions for the joint refactor.
Later corrections and completed work supersede older proposals and deferrals.

1. Privacy: treat repository notes and commits as public. Read logs in place and
   carry forward necessary, sanitized decisions. Keep credentials, signed headers,
   scientific payloads, raw transcripts, session IDs and private deployment
   addresses, accounts, paths and resource identifiers out of public artifacts.
   Document public interface constants/defaults, relative source references and
   clearly marked examples; keep instance-specific private values in existing
   operator inputs or private handoffs. Review the exact diff before publication.
2. Read the recent joint Codex logs before designing, especially the user's
   recurrent directions. Read actual peer notes and thread progress; distinguish
   user decisions, peer suggestions, hypothetical probes and observed results.
3. Prioritize a speedy first joint live deployment: one good shared API router,
   all four providers AND delivery using it, and the eight old proxies retired.
   Fix material blockers through existing workflows; keep checks proportionate.
   A green build, an ACK or a ready listener does not complete the deployment.
4. Hard constraint: the shared proxy stays stable after its first joint deployment.
   Its client contract, socket/group, destination/network settings, storage and
   independent lifecycle form the baseline. Later provider improvements must not
   require proxy reconfiguration, replacement, restart or socket-volume recreation.
   Settle the proxy capabilities needed by later tiers during the first tier.
5. The shared-package owner owns the proxy and convergence of this note. Each
   provider owner writes a new repo-specific design from 020, reads the other
   designs and converges on one shared contract and rollout. Local integration
   and deployment stay with that provider; shared service changes stay with their
   owner. Coordinate shared interfaces before release.
6. Raise the common floor: apply peer findings to your own package, use the
   existing owning mechanisms and choose practical, consistent configuration.
   Preserve signing/TLS, transparent errors, effect uncertainty and durable work.
   Prefer a clean cut over legacy fallbacks, aliases and speculative frameworks.
7. Record consequential choices with serious alternatives and reasons in the
   appropriate design note. Put legitimate minor concerns in the relevant deferred
   note with an owner and trigger; do not turn every suggestion into a deployment
   gate. Check later logs before carrying an old concern forward as open work.
8. Reduce cross-thread chatter. Prefer reading notes and thread progress; send
   messages only for critical or important questions, corrections and blockers
   requiring another owner's action. Work on your own repo while peers progress.
9. Each deployment host is self-sufficient: acquire issued artifacts/source from
   GitHub and build there through maintained targets. Avoid bundle transfers and
   private source overlays. Respect host acquisition/routing choices, keep runtime
   state with its existing owner and keep private operational details out of notes.
10. Work in each repo's main checkout. Deliver through maintained repo-native build,
    deployment, recovery and cleanup paths. No side working copies, one-off scripts
    or hidden manual repairs as the implementation. Prefer the long-term design
    with the least maintenance and babysitting: clear ownership, fewer moving
    parts and routine operations. Make the first milestone a small, durable slice
    of that design; defer optional enhancements.
11. Use this machine's existing local NMR API (nmr.localhost) for the first joint
    integration lane, with the real providers and delivery using the shared proxy.
    Check the whole local system through maintained workflows. Each remote host
    still needs its own deployment and verification against its selected API.

Status: working design and joint rollout plan, revised after discussion on
30 October 2026. No implementation, release or deployment change is claimed.
Scope: Magnet, NMRNet, NMRPeak, SECS and provider-core in nmr-provider-tools.

Decision and purpose
---------------------

Run one host-managed API proxy, independently of provider and delivery-service
lifetimes. All four providers and the shared delivery service use its Unix
socket. The proxy opens a tunnel to the NMR API; each client still signs its
own requests and verifies the API's TLS certificate through that tunnel.
The proxy receives no provider signing keys and does not choose API actions.

The inspected deployment has eight such proxies: four provider-owned proxies
and four delivery-owned proxies. All eight use the same API destination, network
interface and resolver contents. Their storage and runtime identities differ.
This is a controlled host environment with one target API. Sharing the router
and its resources is desirable. Build and maintain one good router for this
deployment; separate proxy processes per provider are unnecessary.

The steady running-container count falls from 24 to 17: eight proxies become
one. Provider, scientific worker and durable delivery boundaries stay intact.
Obsolete proxy initializer containers disappear too; they are not included in
the running count. A fresh shared socket volume may need one initializer.

The priority is a joint refactor that reaches a working live deployment quickly.
Use the existing SDK, release and deployment workflows. Fix concrete integration
problems together as they appear. Keep checks proportionate to the changed code;
building a new validation system is not a prerequisite for this deployment.

Work tiers: fastest path to the joint deployment
------------------------------------------------

Tier 1 -- Do now: get the whole deployment onto one router.

Make the smallest coherent SDK and consumer changes, use the existing build and
release paths, bring up the shared proxy, and move delivery and all four providers
onto it. Fix concrete failures that prevent that deployment from working. Keep
socket access, queue continuity and existing request/retry semantics correct.
Remove the old proxies once their clients settle. The cutover sequence below is
the critical path; a working proxy with only one converted provider is not the
joint deployment.

Here, settling old clients means finishing or retiring their exchanges under
existing uncertainty rules so no client process or tunnel still uses the old
proxy. It does not mean obtaining API acceptance for every queued result; those
obligations can continue through the publisher on the shared route.

Tier 2 -- Follow up after the joint deployment works.

Improve client status/help text, simplify client code exposed by integration, and add
small regression cases for problems found during the refactor. Improve clients
within the deployed proxy's stable contract and capacity. Finish documentation
and incidental cleanup that does not affect the running topology. If a small
improvement directly helps the current cutover, do it there; do not turn these
follow-ups into a second prerequisite project.

Tier 3 -- Leave out unless a concrete need emerges.

Multiple-API support, route identifiers and discovery, a new configuration model,
dynamic registration, per-provider router accounting or fairness, compatibility
frameworks and generalized migration tooling are outside this refactor. So are
new full-topology test environments, exhaustive collision/adversarial matrices,
load or chaos campaigns and independent qualification infrastructure built just
for this change. These are possible future projects, not promised follow-ups.

The tiers order work by its contribution to getting the joint system live.
New validation machinery is one possible delay, alongside extra abstractions,
configuration, coordination and tooling. Run relevant existing checks as part
of the normal workflow. Add a check when it answers a concrete problem cheaply;
do not move an entire future project into Tier 1 under the label of validation.
An observed correctness problem belongs in Tier 1 regardless of its category.

Patterns and anti-patterns for choosing the remaining work
----------------------------------------------------------

Use these pairs when proposing next steps or deciding whether the deployment is
finished. They address deviations seen in agent roadmap exercises.

* Pattern: finish the transport cutover while a healthy publisher retains pending
  commands on their original bindings and follows the existing retry rules. Fix
  a publisher paused by incorrect route or credential inputs before calling its
  delivery cutover working; retaining the bytes alone is not functioning delivery.
  Anti-pattern: wait for an empty queue or every terminal receipt before calling
  the router deployment complete, or label a paused publisher as a normal retry.
  Never retarget queued commands or change refusal classifications to manufacture
  progress; fix the granted inputs and resume through existing delivery rules.

* Pattern: fix a demonstrated integration failure at its owner. A missing client
  supplementary group needs a corrected client projection; an outdated CA needs
  refreshed candidate trust inputs. Repeat the affected existing check with the
  intended runtime identity and TLS verification, keeping other clients moving.
  Anti-pattern: run the client as root, make the socket world-writable, disable
  TLS verification or introduce a central trust service to bypass a local fault.

* Pattern: leave nonessential status/help improvements and unrelated cleanup for
  later; they are also outside the definition of deployment completion.
  Anti-pattern: promote copy polishing, generic helper refactoring or speculative
  validation infrastructure into deployment prerequisites. Correct misleading
  instructions now only when they obstruct the actual cutover or safe operation.

* Pattern: deploy a ready consumer when its own dependencies are ready and shared
  operations are coordinated; keep other conversions moving in parallel.
  Anti-pattern: require every provider to be ready for a simultaneous cutover or
  let one owner's unrelated improvements hold up the others.

* Pattern: keep excluded projects outside this refactor unless a concrete need
  justifies reopening that decision.
  Anti-pattern: turn an excluded registry, configuration model or rehearsal
  environment into promised work merely by saying "after the first conversion."

* Pattern: keep one shared router and diagnose actual overload. Control a known
  maintenance burst with its existing concurrency setting before increasing
  shared capacity during initial bringup. Settle the bounded limit for normal
  combined traffic with its thread, PID and memory budgets in that first tier;
  later provider improvements use the deployed baseline.
  Anti-pattern: restore per-provider listeners or proxies to avoid sharing, or
  require 8x32 connections just because the previous topology had eight listeners.

* Pattern: finish with all four providers AND delivery on the shared socket,
  old proxies retired and one independently managed proxy remaining. The planned
  running-container reduction is 24 to 17. Count API proxy roles explicitly:
  a stopped scientific worker can hide an extra proxy behind a total of 17.
  Anti-pattern: declare the joint project done after one successful client, after
  converting only the providers, or while unused old proxies remain running.

* Pattern: repair maintained retirement commands so each owner removes its own
  obsolete resources and preserves the host-owned socket volume.
  Anti-pattern: bypass a broken command once and call lifecycle work complete,
  or expand one provider's cleanup into a scan of every provider's resources.

* Pattern: convert every maintained production API path, including preflight,
  journal/archive and maintenance tools, to the shared grant. Remove obsolete
  private API creation paths and copied API network settings. Remove compatibility
  branches only for those removed API route fields. Preserve client API origins,
  credentials and TLS trust, and required scientific interpreter/store routes.
  Anti-pattern: call a real-API operator path "test-only" to defer its conversion,
  or delete still-used authority and scientific routes because they repeat values
  or contain the word "proxy" or "route".

The coordinator uses these patterns to challenge proposed delays, scope changes
and completion claims, while owners continue work that is already unblocked.

Parallel agent coordination
-----------------------------

Give the agents one shared outcome: delivery and all four providers running
through the single host proxy, with the old proxies retired. Assign ownership:

* One SDK/delivery owner implements the shared interface, owns the SDK release,
  and manages the host proxy and delivery cutover.
* One owner per provider converts its repository and carries that change through
  deployment. Each owner edits its own repository and coordinates shared-file
  changes with the affected owner.
* One coordinator resolves cross-repository blockers and drives the whole graph
  to completion. This can be the SDK/delivery owner.

Agree the volume name, socket path, proxy UID, access GID and SDK interface early.
Keep private instance values in existing operator inputs or a private handoff;
this note records the public contract and intentionally public defaults.
Coordinate interface changes with the affected owners. Keep other agents on work
that does not depend on the change. Keep working shared names and interfaces
stable during cutover; cosmetic renames and dual-name compatibility add no
deployment capability.

Bring up the router with one real consumer early, giving everyone a working
integration to follow. Prepare the other provider changes in parallel. Once the
shared path works, move the remaining consumers onto it without waiting for
unrelated repository improvements. The SDK/delivery owner coordinates changes
and restarts of the shared services; provider agents manage their own services.
A ready provider can cut over once its own dependencies and shared-service
coordination are settled; readiness of every other provider is not a prerequisite.

Give every agent this assignment:

  Get all four providers AND shared delivery running through one independent
  host API proxy, and retire the replaced proxies and unused private route
  resources after their clients settle. Deliver your owned part through existing
  workflows in the main checkout, preserving signing/TLS, queue ownership and
  request/retry semantics. Use maintained paths and a durable design with minimal
  maintenance and babysitting; avoid one-off implementation and operator repairs.
  Keep the agreed shared interface. Fix concrete blockers; leave unrelated
  improvements and excluded projects outside this rollout. Correctly retained
  retries may remain pending after cutover. Report observed progress, the next
  live milestone and any blocker needing another owner. State what remains for
  the whole deployment, including old-proxy retirement.

Pass that assignment and the relevant provider paragraph below with partial
handoffs. Include the owner's task, SDK release, observed state, next runnable
milestone and concrete blocker. Use a private handoff for instance-specific
settings and diagnostic evidence; keep shared public notes at the contract and
sanitized-summary level. No new tracking service is needed. Distinguish source
changes, passing builds and observed live results.
Mark unknown peer status as unknown and release estimates as estimates. Carry
confirmed live milestones forward; do not invent work to redeploy the API or
repeat a completed cutover without evidence of a problem.

When blocked on another owner, finish useful source or launch preparation that
does not depend on the missing input, report that input, then wait if nothing
useful remains. Do not fill the wait with a framework, polling service, guessed
release pin or copied SDK source that bypasses the maintained release path.

Report at integration milestones or when a blocker or shared decision changes.
The coordinator reviews decisions that change scope, shared interfaces or
deployment timing, while owners handle routine implementation. Reassess work
that adds abstractions, tooling or checks without helping the current cutover.
A provider owner's part is complete when its change works in the joint deployment
and its obsolete private API route is retired; the coordinator finishes the whole
graph, including delivery and old-proxy removal.

Joint implementation and live cutover
-------------------------------------

Start joint integration here against the existing local API at nmr.localhost,
the documented development hostname. Use the configured API origin, trust and
credentials through the shared proxy's admitted route and client Unix socket.
Exercise real provider and delivery paths with existing maintained checks and
authorized local scenarios; no separate test-stack project is needed. Keep each
host's selected API/proxy baseline independent, and distinguish local integration
results from evidence that a remote deployment is running the new topology.

1. Agree the shared socket volume, socket path and access group once. Update
   provider-core and all four consumers around that small interface. Reuse the
   existing deployment inputs and Compose conventions; add no route registry,
   discovery protocol or separate configuration model.
2. Implement the host proxy and client mount/group projection in the SDK.
   Convert delivery and the four providers in the same joint effort, removing
   their production proxy ownership. Use the existing focused checks while
   making each change and the normal SDK release and consumer build paths.
   Each deployment host builds through its maintained tooling.
3. Start the host proxy alongside the existing topology. Use a signed API read
   from an actual candidate client to check the shared path, including TLS and
   credentials. Fix socket access or routing problems here while the old
   clients remain available; then move the remaining clients through the path.
4. Cut over delivery and providers in an agreed order using their existing
   drain and settlement procedures. Keep queue volumes, pending binding
   identities and exact queued commands. Keep each old proxy until its old
   clients have settled. Use existing candidate startup checks before replacing
   a working provider. Do not edit queue rows or infer drain from process health.
   Pending delivery may continue on its normal retry schedule after cutover when
   its queue, binding and publisher remain correct. An empty queue or eventual
   receipt for every pending item is not a prerequisite for this transport change.
5. Check the joint deployment: all four providers and delivery use the shared
   socket, API reads work, and delivery is running with pending/held state
   accounted for. Observe actual delivery progress where work is available.
   Inspect health, logs and restart counts; fix observed problems during this
   rollout rather than waiting for a separate qualification campaign.
6. Remove the eight old proxies, stopped initializers and unused private route
   volumes once their clients have settled. Delete obsolete production route
   code, copied route configuration and tests of the removed topology. Confirm
   one shared proxy remains and ordinary consumer replacement leaves it running.
   Fix maintained cleanup commands that would remove shared storage; bypassing a
   broken command for this one cutover leaves the lifecycle bug unresolved.

A mixed topology is a temporary cutover state. Finish all four consumers and
delivery in this effort. Until old routes are retired, an unusable shared route
can require coordinated rollback using preserved definitions and images, managed
with the shared-service owner. That remains an incomplete migration, not a
consumer-selected fallback. After final retirement, consumer operations do not
re-create private proxies. For a component-local failure, recover that component
with a known-compatible image on the shared socket where possible; healthy shared
services and other providers stay in place. Fix or retire the failed candidate
through the owning workflow instead of making a broad helper rewrite a
prerequisite for recovery.

Rollback of software does not rewind durable state. A compatible delivery binary
uses the current queue and original binding identities, retaining all acknowledged
commands. Stop and settle its current owner before starting the replacement;
neither restoring an older queue backup nor overlapping two queue owners is a
shortcut. Preserve existing uncertainty rules and do not duplicate scientific work.

End state and ownership
------------------------

* Exactly one proxy process serves this host's target NMR API.
* Starting, replacing or stopping any provider cannot start, stop, remove or
  recreate that proxy or its socket volume. The same applies to delivery.
* Host deployment owns destination, interface, resolver, runtime identity and
  socket access. Consumers receive the shared socket mount and group; they do
  not own copies of the router's network settings. Their API origins still name
  the same target API.
* API credentials, TLS trust and request/result ownership remain with existing
  clients. No shared provider identity, TLS termination or new API protocol.
* Provider-specific delivery queues, intake sockets, quotas and acknowledgements
  retain their current semantics. This is not the delivery-registration redesign
  discussed in the SDK's note 019.
* No provider composition contains an API proxy or its initializer. Delivery
  composition contains its daemon but no per-binding API proxies.

Shared implementation
-----------------------

nmr-provider-tools owns the proxy implementation, client projection and host
deployment tooling. The operator uses it to manage one separate Compose project,
supervised by the Docker engine with restart policy. Proposed maintained commands are
make api-proxy/deployment/{config,up,status,down}; provider and delivery commands
never invoke its up/down operations. A host reboot must restore the proxy and
clients must tolerate startup ordering and temporary unavailability.
Keep its deployed image and settings as the host baseline; a provider SDK upgrade
does not redeploy or reconfigure the shared proxy.

Use the ordinary SDK release path and existing artifact/version records. Each
host acquires the release and builds its proxy image through maintained tooling;
it does not depend on another workstation's temporary artifacts or image.

Split the present deployment_route responsibilities into two explicit operations:
render the owned host proxy, and project its socket mount and group to a client.
Keep protocol parsing, interface-bound DNS/TCP and bounded connection handling
with provider_proxy and bound_http_proxy. Keep credential admission with signing
and deployment_binding. Keep the transport interface small: a shared volume,
socket path and access group. Configure the router's destination and network
settings once using the existing deployment inputs. Each binding keeps its own
API identity, credential and trust inputs. A new provider for this API borrows
the same socket and adds no proxy or API-router registration step. Its delivery
binding still uses the existing static operator workflow described in note 019;
socket access does not register a publisher or transfer a terminal obligation.

The client projection must serve both Compose services and one-off candidate
containers: external volume declaration, read-only mount, socket path and
supplementary group, with no proxy services or service dependencies. Add these
grants to the client's existing mounts/groups; preserve delivery intake and
scientific grants. The agreed helper and concrete defaults below are the consumer
implementation target; the current private-route renderer is not that interface.

Agreed design contract (not yet an issued SDK interface):

* Keep the existing operator binding TOML and its admission path. Move repeated
  bindings.route settings to one top-level api_proxy.route table; add api_proxy
  project, uid, gid and origin there. Keep delivery project/identity/limits and
  every bindings.api identity/trust/budget unchanged. The host proxy origin is
  the one allowed CONNECT authority; selected client API origins must agree.
  This is one extension of the existing input, not a second configuration system.
  Selected DeploymentBinding objects carry api_proxy with only project and gid;
  render_api_client reads that grant, not the host's routing policy.
* Public example project: nmr-api-proxy. Its owned socket volume is derived as
  <api_proxy.project>-socket. UID/GID remain explicit operator choices; do not
  infer them from a provider identity. Inside every client, mount at
  /run/nmr-api-proxy and connect to /run/nmr-api-proxy/proxy.sock. Host project
  selection may differ; these in-container paths need no per-provider setting.
* In provider_core.deployment_route, render_api_client(binding) returns
  ApiClientProjection with exactly compose, client_socket, client_mount and
  client_group_add. compose contains only a volumes entry named shared-api,
  external: true with the derived exact volume name. client_mount uses that
  alias, the path above, read_only: true and volume.nocopy: true;
  client_group_add is a list containing the API GID as a decimal string.
  It accepts no image, provider UID, namespace or resolver relocation inputs.
* The installed-image CLI is python -m provider_core.deployment_route client
  --definition FILE --binding NAME, emitting those same four JSON fields.
  This serves shell consumers without a second TOML parser. One-off clients
  resolve the mount alias through compose.volumes and apply the same GID;
  before docker run, their maintained launcher checks that exact volume exists.
  Docker run can auto-create named storage even with volume-nocopy; Compose's
  external flag does not cover it. Absence fails without launching the borrower.
  The projection never creates a volume or starts a service.
* input_paths for selected bindings grants only credentials and optional CA.
  Proxy resolver acquisition moves to the host-owned render/config operation.
  Existing operational capture retains the client grant and API inputs, without
  requiring provider access to router-only files. SDK host rendering consumes
  api_proxy independently; provider/delivery operations cannot invoke it.
* In deployment_binding, client_definition_bytes(definition, *, binding_name)
  emits the existing binding TOML with that binding and its unchanged delivery
  settings, plus api_proxy.project/gid only. Add a client-definition CLI action
  with --definition FILE --binding NAME, emitting those TOML bytes. This is the
  maintained capture operation for callers that currently freeze the raw whole
  document; they do not implement another TOML projection. The same SDK client
  loader accepts this projection without api_proxy.uid/origin/route. Host
  render/config requires those fields in the original operator definition; it
  cannot use a client capture. Reparse and compare using the existing
  frozen-input workflow.
  Host-baseline inputs stay with their independent owner, rather than becoming
  required files or redundant network-policy copies in every client generation.
  This CLI emits raw TOML, not JSON: existing JSON projection wrappers must not
  decode it or add it to ApiClientProjection. Clients that mount an operator
  definition directly use the same maintained operation to provision their
  client-only input; a read-only mount does not make its contents immutable.

Keep the private render_api_route interface only for its remaining disposable
authored-API fixtures; it is not a production fallback. Agree any fixture-input
adjustment with the owning test callers when removing per-binding route fields.
In particular, today's renderer reads binding.route: make fixture route inputs
explicit at that test-owned boundary rather than keeping a production route
field or accepting the old operator schema as a fallback. Fixture APIs use their
own test proxy resources and never retarget the deployed host proxy.
No release number is reserved or assumed by this design.

Use one named socket volume, writable only by the proxy and initialized for a
dedicated nonroot proxy UID and operator-selected shared access GID. The proxy
UID must differ from consumer UIDs. Consumers mount that volume read-only and
receive that supplementary group. Existing runtime UIDs stay valid. The proxy
grants directory traversal and socket connection to the group (directory 0710,
socket 0660), while its lock and readiness internals remain private. This
requires SDK changes: today's owner-only directory/socket checks must be adapted
for shared group access. Keep the existing lifetime lock and stale-socket safety;
clients must not be able to change route state or take the proxy's lock.
Birth permissions must already be restricted, not repaired after exposure.
Scope shared access to this host API grant; scientific and test-owned private
proxy grants keep their existing ownership and permissions.
Only the host proxy project declares ownership of the named volume. Every
provider and delivery Compose projection declares that volume external: true
with its exact host-owned name. A missing volume fails before client launch;
consumers cannot auto-create or reinitialize it. Their explicit volume-cleanup
code must exclude it as well; Compose's external flag alone does not constrain
custom Docker removal commands.

Old private storage needs explicit retirement: ordinary down commonly retains
volumes/directories. Each owner uses retained old composition, admitted mounts
and existing ownership evidence to remove only its unused API storage after its
actual borrowers settle. Keep that evidence until removal succeeds; a healthy
replacement with failed cleanup is incomplete retirement, not failed replacement.
Do not broaden normal data-volume deletion or add a generic migration framework.

All clients granted that socket have the same network destination permission.
The proxy cannot identify a provider from encrypted HTTP or a shared Unix peer
UID. Do not claim per-provider attribution or fairness at this listener. API
authentication still distinguishes providers; delivery retains its own quotas.

Consumers and lifecycle
-----------------------

Magnet: replace render_api_route in deployment_inputs with the shared client
grant. Its api/api-init roles are the old proxy and initializer: remove them from
production and real-API validation compositions, including launch and teardown.
Keep candidate startup and signed API reads before stopping the incumbent; give
those clients the same shared mount/group. Capture client credentials and trust,
not the router's network settings. Private disposable test-API routes stay in
test infrastructure; the authored-API fixture still calls the private renderer,
so remove production ownership without deleting its remaining fixture use.
Magnet's existing frozen-volume ownership check already skips external volumes;
preserve that distinction in custom retirement and repair paths too. Its detailed
consumer design is notes/048_shared_api_proxy_adoption_20261030.txt in Magnet.
Build the product selected by the retained deployment
through the existing build target; preserve its image/input identity checks.
Status diagnostics that expose this selection more clearly are a follow-up in
note 015, not a reason to retag the wrong product or delay a correct build.
Within the provider's existing deployment authorization, carry the candidate
through maintained up and report the running image/grant and retired old roles;
a green source commit or build is readiness, not completed deployment.

NMRNet: deployment.py projects the external client mount/socket instead of
merging route services. Its generation retirement must never remove shared
storage. Add the shared API mount and GID to existing grants; replacing entire
volumes or group_add lists can break delivery intake and scientific interfaces.
Keep interpreter, store, reader and scientific routes independently owned, and
preserve the provider's existing network isolation. Check the affected projection
and existing connections rather than switching the client to host networking.
Coordinate its original delivery binding/intake with the shared owner; a working
API read does not establish delivery readiness or permit using another identity.
Ownership admission must recognize the specifically borrowed host API volume
without relabeling it or dropping guards on owned journal/worker storage. Keep
the borrowed volume excluded from both ordinary and custom retirement paths.
Its current proxy uses a private bind directory, not a named volume, and existing
retirement only removes unused bundles. Preserve the inspected old mount/bundle
evidence until narrow owned directory retirement succeeds. Its down/install/up
replacement is not Magnet's candidate-preserving replacement; do not promise a
rolling update. Convert maintained real-API staging and signed Job readback too,
while keeping authored-API fixture routes and scientific routes test-owned or
independently owned as appropriate. Its detailed design is
notes/023_shared_api_proxy_adoption_20261030.txt in NMRNet.

NMRPeak: deployment_runtime and generation/maintenance tooling borrow the same
shared API grant. Put client socket/group settings in the existing operational
capture with its credentials and trust; keep scientific generation identity and
model products unchanged. Resolver and interface inputs stay with the host
router, without per-generation copies. Journal/archive and maintenance API reads
use the shared grant too. Removal of a provider generation leaves the route live.
An already running old archive retains its generation lock and borrowed route
until its original work settles; preserve unacknowledged work and report old-route
cleanup as pending. Other providers can continue their own conversions meanwhile.
Historical scientific snapshot housekeeping is separate from API proxy retirement.
Check the owner's latest private status before treating an old deferral as open;
retain the applicable design lesson without publishing instance cleanup history.
Maintenance docker run clients need explicit --group-add and an exact borrowed
volume existence check before launch. Ordinary down already has an owned API
volume cleanup path; adapt that path rather than introducing another remover.
Its detailed design is notes/010_shared_api_proxy_adoption_20261030.txt in NMRPeak.

SECS: _apply_api_route grants the shared volume, group and socket path; it no
longer merges proxy services. Interpreter and upload-store routes remain distinct.
The shared proxy grants the NMR API destination; scientific source/store origins
keep their own existing routes and access limits, as scoped in note 021.
An absent external socket volume blocks client launch, not source conversion;
report it to the shared owner, who creates and initializes it. SECS adds neither
a replacement root initializer nor direct-network fallback.
Safe API/store failure context in existing client logs is a follow-up in note
015; it does not require identifying providers inside the shared listener.
Current stop retains containers, and strict inventory includes api/api-init.
Removing those roles from the new plan alone would obstruct old-topology
admission. Retire the exact inspected old roles and their private mounts through
a maintained operation after settlement, then use normal new-topology admission.
SECS currently has no Magnet-style pre-stop candidate read. A narrow maintained
check-api may help establish the actual signed path without launching science,

Its detailed design is notes/010_shared_api_proxy_adoption_20261030.txt in SECS.

Delivery: all four bindings select the shared route while retaining their own
signers and pending rows. Remove its four rendered proxies and initializers.
Keep queue storage and provider-specific delivery intake grants. A proxy outage
does not transfer or discard any pending terminal obligation.

Start the host proxy first during cutover; there is no cross-project depends_on
guarantee. Use the existing client startup and API checks with the shared socket.
Do not add a route-identity protocol or a new mandatory reachability gate to
every launcher. Temporary proxy loss follows existing client failure/retry rules;
delivery retains its local queue. Consumer launchers never start private fallback
proxies.

Proxy restart breaks existing tunnels. Clients retain existing effect-certainty
and retry rules: do not add an unconditional START replay or science rerun.
Another restart cannot establish whether the API accepted a lost request; preserve
that uncertainty and use the existing recovery policy rather than repeating work.
The delivery service retains and retries exact commands under its current rules.
Health distinguishes proxy process readiness, successful API reachability and
delivery progress; a ready listener alone cannot establish all three. Diagnostics
preserve safe DNS/TCP/native causes without credentials or request contents.

Design convergence and implementation handoff
----------------------------------------------

All four provider notes listed above have read the other three designs and
reviewed the concrete four-field client projection, client-definition capture
and public example paths. Their convergence records report no remaining caller
or capability conflict. This is agreement on design, not an issued SDK or live
deployment. Do not infer runtime status from it.

Peer review changed the common plan: use the same grant in normal and one-off
clients; prevent one-off volume creation; preserve additive delivery/scientific
grants; capture client-only TOML through the SDK; and retire old resources through
each repo's actual lifecycle with retained ownership evidence. No later provider
tier identifies a need for another host proxy capability.

The SDK owner implements the agreed projection/capture, host group-access and
independent deployment path, converts delivery and issues artifacts through the
normal release workflow. Provider owners implement their documented seams and
retirement through their normal dependency/build paths. Prefer an early real
candidate signed read on the local shared proxy, then move ready consumers with
their original delivery bindings; do not wait for simultaneous provider readiness.
The implementation handoff is these agreed symbols/fields and the per-provider
notes. The next shared dependency is an issued SDK artifact and a usable local
host grant, not another design framework or an assumed version number.

Why these choices: one block in the existing operator input keeps host settings
together without adding another configuration system; a small installed-SDK
projection supports all callers without copied parsers; a fixed client path
removes per-provider naming choices; selected client capture keeps host policy
out of client generations; and owner-specific retirement avoids a generic
migration tool. Keeping raw full definitions in every capture, retaining private
production routes, or forcing every launcher into one replacement pattern would
undo those ownership and maintenance benefits.

Caveats during cutover
-----------------------

Eight present listeners each have a 32-connection cap. One current listener has
32 total. Start with that existing bounded limit during initial joint bringup.
Resolve observed overload and select the deployed limit in that tier, accounting
for thread, PID and memory limits. Later provider improvements work within that
baseline. A saturation benchmark or a new capacity configuration framework is not
required before the first live cutover.
If a shared-router failure is disrupting clients, pause further affected cutovers
while its owner fixes the cause and checks recovery through existing means.
Resume ready consumers after recovery; a client-local configuration failure
blocks that client rather than the whole rollout.

Route or resolver changes are deliberate host operations. A stopped-and-replaced
proxy interrupts all API clients; that shared resource and failure domain is
accepted. Provider deployments never silently rewrite its network settings.
A later change to this host baseline is separate from the provider-improvement
tiers; those tiers must leave the deployed proxy undisturbed.

The host is controlled and collisions are unlikely. Choose distinct runtime
identities and clear resource names, and retain existing filesystem safety.
Do not build a general collision detector, live configuration attestation or
adversarial admission layer before the joint deployment works. Fix actual
misconfiguration where it occurs.

Working API reads and healthy services establish the transport cutover, not a
scientific end-to-end result. Record what was observed without requiring a new
synthetic science campaign to complete this router refactor.
