Shared API proxy and delivery outbox
====================================

Governing guidelines
--------------------

1. Privacy: repository notes and commits are public. Keep credentials, signed
   headers, scientific payloads, raw transcripts, session identifiers and private
   host, account, path and resource values out of them. Record durable decisions,
   alternatives and relative source references, not discussion or ACK history.
2. Read recent joint Codex logs and the other owners' designs. Distinguish actual
   work and user decisions from proposals. Work in each repository's main checkout.
3. Prioritize a speedy first joint deployment on this machine against the existing
   nmr.localhost API: all four providers and delivery working through one shared
   API proxy, with replaced API proxies and private delivery intakes retired.
   Use maintained build, deployment and cleanup paths. Source changes and passing
   builds are not proof of a live deployment.
4. The shared API proxy must remain running with its socket volume intact across
   later provider and outbox changes. Its first deployment must include the live
   controls those changes need. An operator may change those controls without
   replacing or restarting the proxy. Changes to process identity, network setup
   or mounted storage are deliberate host operations, not provider operations.
5. The shared-package owner owns the proxy, outbox, shared SDK and this design.
   Provider owners own their integrations and scientific lifecycles. Converge on
   one contract and rollout; raise the common floor by using findings in each repo.
6. Use GitHub push/pull and host-local builds through maintained targets. No bundle
   transfers, private source overlays, side checkouts or one-off operational fixes.
   Prefer durable, low-maintenance workflows. Reduce cross-thread chatter; read
   notes/progress and message only important corrections, questions or blockers.
7. Configuration replacement and service interruption are acceptable during
   this refactor, including while delivery has pending work. Do not add old/new
   configuration staging, rollback or incumbent-continuity machinery as a gate.
   Preserve existing queue ownership, signing/TLS and effect-uncertainty rules.
8. Use proportionate existing checks, not a new validation project. Record
   consequential alternatives and reasons. Defer optional enhancements; fix a
   demonstrated blocker in the first tier regardless of its category.

Status: authoritative joint design unless a serious objection requires a change.
The shared services are deployed locally; the first joint milestone remains in
progress until all four providers and delivery are verified. This note supersedes
its previous static provider-binding and per-provider delivery-socket proposal.
Provider-specific designs must align with it before they are used as
implementation instructions.

Decision: two shared services
-----------------------------

Run one host-managed API CONNECT proxy and one independently managed durable
outbox. They are separate services with separate Unix sockets and owned socket
volumes. All four providers use the API proxy for their own API exchanges and
submit terminal results to the outbox through its shared intake. The outbox uses
that same API proxy to publish results. A provider restart or removal does not
restart either shared service or remove their storage.

The proxy opens tunnels. It does not receive provider signing keys, sign requests,
interpret results or manage provider registration. Clients supply CONNECT
host:port, sign their own API requests and verify API TLS. The outbox accepts
terminal work, owns its durable queue and signs publication requests on retries.
These responsibilities cannot be collapsed into an outbox alone: providers also
make direct signed API calls. Running both roles in one process would couple
provider API connectivity to outbox replacement and queue recovery; retain two
independent services to satisfy the proxy stability requirement.

The inspected starting topology has eight API proxies and 24 running containers.
Replacing those eight with one yields an expected 17, assuming the other roles
remain running; count actual proxy roles as well as containers. The outbox already
exists, so one shared intake replaces its per-binding sockets/volumes without
adding another steady-state service. Do not infer a live count from this design.

Tier 1: one joint working deployment
------------------------------------

* Add the shared proxy and client socket grant in provider-core. Use the existing
  SDK release and host-local build paths. Include live proxy capacity, log level
  and allowed CONNECT authorities in the first proxy deployment.
* Replace static per-provider outbox bindings and their separate intake sockets
  with one shared intake and a shared-SDK result handoff. Delivery retains the
  publication material supplied by the provider, with the accepted result.
  Include its live queue, retry and log settings in the shared operator file.
  The provider-facing intake is push-only: submission and its acknowledgement,
  with no pending, status, inventory or capacity-read operation.
* Convert Magnet, NMRNet, NMRPeak and SECS, including maintained real-API
  validation, readback and maintenance paths. Keep independently owned scientific
  and disposable authored-API fixture routes. No consumer starts a private API
  proxy or owns either shared socket volume.
* Start the host proxy and outbox, use existing signed API/startup checks, then
  bring up ready providers through maintained workflows. Providers need not wait
  for simultaneous readiness. Fix concrete integration failures at their owner.
* Check all four providers and the outbox against nmr.localhost: actual API
  access, shared grants, working delivery and pending work accounted for. Observe
  delivery progress when work exists. Retire all eight old API proxies and unused
  private API/delivery socket resources through their owning cleanup paths.

A queue need not be empty, and individual retries need not have completed, to
finish the transport cutover. A paused publisher caused by a wrong grant or
credential is a problem to fix, not a healthy retry. Preserve exact accepted
commands and original API/provider identities; never overlap queue owners or
edit rows to manufacture progress. Stop and replace services as necessary: old
configuration or uninterrupted publication is not a deployment prerequisite.
The intended remote hosts each require their own later observed deployment; local
results alone do not prove those hosts are running the new topology.

Tier 2 covers client help/status improvements and small follow-ups found during
integration. Tier 3 excludes multi-API orchestration, a provider registry, dynamic
registration, per-provider proxy processes, generalized migration/validation
frameworks and speculative fairness or load-testing projects. A real blocker is
Tier 1; an optional enhancement does not become one merely by being adjacent.

Shared API proxy
----------------

One proxy socket volume is created and owned by the host proxy deployment;
providers and outbox borrow it read-only and add its access GID to their existing
supplementary groups. Proxy UID differs from client UIDs. Use restricted socket
and directory permissions at creation, retain private lock/readiness state and
stale-socket/lifetime exclusion. Do not bypass socket access with root, broad
permissions or host networking. Consumers never create, reinitialize, relabel or
remove the shared volume; custom cleanup must respect this too. A one-off docker
run borrower checks the exact volume exists before launch: nocopy alone does not
prevent Docker from creating it.

The CONNECT request supplies the destination. The operator sets a host-wide
allowed-authority policy, not a provider or API registration list. The first
host can allow its one API; the policy can change live. A narrowed policy affects
new tunnels, while admitted existing tunnels finish. A policy allowing arbitrary
destinations would broaden every socket borrower's network capability; this
design does not require an unrestricted mode. TLS and API authorization stay at
each client, and scientific/interpreter/store routes keep their own owners.

The present proxy has a hard-coded 32-connection worker bound. Replace that with
an operator-adjustable live limit; lowering it does not kill existing tunnels,
but prevents new admission until use falls below the limit. Set an initial bound
and account for the actual container PID, thread and memory budgets: the live
limit cannot conjure capacity beyond those limits. Overload remains visible to
clients under the existing bounded failure semantics. No per-provider proxy
fairness or attribution is promised by a shared encrypted tunnel.

Shared durable outbox
---------------------

All providers mount one host-owned outbox intake volume read-only and connect to
one Unix socket with the outbox access GID. The shared SDK supplies the client
and handoff format. Remove the per-binding intake sockets/volumes and the central
static list of provider bindings. There is no separate registration step: a
provider supplies the information needed to publish with its result handoff.
A new provider uses the same two socket grants and submits through the same SDK;
joining or leaving does not require an operator configuration edit or a proxy or
outbox restart. Accepted work stays with the outbox when its provider leaves.

The shared intake accepts submissions only. Its reply reports the outcome of the
submitted handoff, including durable acceptance or refusal; it cannot list or
read pending results, status, capacity or other providers' information. Keep
the actual queue and retained credentials in outbox-private storage, not the
shared socket volume. Bind the submitted identity to its credential fields and
keep private publication inputs out of acknowledgements, errors and logs. An
operator may inspect held/pending work through the existing operator-owned path;
that capability is not granted to providers by the intake socket.

The existing credential parser checks the artifact's fields and matching key
pair; by itself it does not prove that the API issued or still authorizes that
credential. The API authenticates publication. The shared socket is therefore
a trusted local submitter boundary, not cryptographic per-provider authentication.
There is no queue-read operation, but a conflict refusal for a guessed matching
identity can reveal limited existence information. This limited disclosure is
accepted for the controlled host. Do not claim zero information leakage or
cross-provider isolation beyond the absence of a read interface.

The handoff contains the exact terminal operation/body and its Job/Attempt and
API/provider identity, plus the API settings, original issued signing credential
and optional CA material needed by delivery. The SDK uses the existing issued
credential and API settings semantics; an in-memory SSL context or private-key
object is not a transport format, and a provider-container file path is not a
usable credential grant for the outbox. Preserve client-side origin, topology,
timeouts and trust as appropriate to the existing API client. Delivery owns fresh
request signing and TLS on every attempt; an old pre-signed HTTP request alone
cannot guarantee publication after an outage.

Keep the existing supported terminal-body size when adding publication material.
Today's intake request ceiling is 2 MiB, and Magnet can retain a terminal body
up to that size; placing credentials, CA data and encoding overhead in the same
bounded envelope would otherwise reject a previously supported result. Bound
the complete handoff for the supported body plus bounded publication inputs.
Keep the existing result-body byte-budget meaning and account for retained
publication material in actual storage sizing; do not truncate or silently
reduce the supported result size to fit the old IPC ceiling.

Before acknowledging, the outbox durably commits the exact result and its usable
publication inputs together. If acknowledgement is lost, the producer retains
its obligation and may reconcile/replay the identical handoff under existing
uncertainty rules. A replay acknowledgement must describe what the outbox
actually retained; different publication inputs must not silently overwrite the
original or be reported as though they were stored. After the provider exits or
the outbox or host restarts, the outbox retains the material needed to retry
independently; publication still depends on valid authority and API availability.
Reconstruct the API/signing owner from retained material, preserve receipt
verification and original identity, and never silently retarget an accepted
result. Credential rotation/revocation must not silently substitute another
identity: preserve pending work and report a held or failed publication through
the existing operator path when authority cannot be used. A durable acknowledgement
is not API acceptance or a guarantee against host/storage loss; the existing
pre-ack producer-crash uncertainty is unchanged.

Publication material contains private signing capability. Keep it out of logs,
status, error text and public artifacts; use outbox-owned private durable storage
and include database, journal/WAL, backup and cleanup paths in that protection.
The shared intake is a submission capability granted to its borrowers, not an
identity or a queue-reading capability. Retain meaningful per-provider and total
backpressure through the existing queue owner. A full outbox refuses new work;
the producer retains the exact result and uses its existing retry/settlement
rules. This is a controlled host; do not build a new identity registry or
general control plane.

Push-only changes provider admission: NMRNet and NMRPeak currently call pending()
to check capacity and exclude queued Jobs before starting science. NMRPeak also
reserves room for its two concurrent lanes. Replace those reads with the existing
bounded live owners and the authenticated API's provider-relative
has_provider_execution_attempt=false feed. That feed excludes a Job with any
Attempt by that provider, regardless of Attempt state. The inspected API's Job
cleanup deletes Attempts after marking the Job DELETED; the feed requires OPEN.
Keep the original provider identity and verify the deployed API contract during
integration. The feed is not an outbox capacity check or a recovery receipt.

NMRNet keeps its serial live controller; NMRPeak keeps its two-owner limit and
admission lock. NMRPeak's selection can race between lanes before START claims
the Job; treat a duplicate claim as a no-START retry only when the existing
claims owner confirms that Job is already owned. On a full or unavailable outbox,
an existing controller retains the exact handoff and pauses new admission;
NMRPeak pauses both lanes while its
blocked owners settle. Already admitted work may finish within those owner and
body bounds. Once the matching durable acknowledgement arrives, the outbox owns
the work and the controller can settle under its existing lifecycle. A full
outbox can first be discovered after science, and at startup its availability
is unknown until submission. This is an accepted loss of the former pre-start
outbox-capacity gate, not equivalent behavior or a reservation guarantee.

After producer restart, retain the existing START/checkpoint recovery rules and
the already unresolved producer-crash-before-acknowledgement window. Do not
claim an unacknowledged result survived, rerun science to replace it, or add a
new local durable queue, hidden outbox read, per-provider socket or registration
as a shortcut. Fix demonstrated correctness blockers in Tier 1.

For the old queue, retain accepted items and their original identity and signing
inputs through the existing owning deployment path when converting them to the
new representation. If required old publication inputs are unavailable, retain
and report the affected work for recovery rather than discarding or retargeting
it. Do not require an empty queue, a parallel old deployment or preserving old
configuration as a rollout gate. This is a narrow conversion of actual retained
work, not a general migration framework.

Operator configuration and live reload
---------------------------------------

Common configuration practice:

* Each repository owns its own named deployment settings under its existing
  `config/deployments/<name>/` convention. A provider does not read another
  repository's configuration file, at deployment or at runtime.
* Keep credentials, private keys and trust files in the owning provider's
  private secrets location. Track placeholder examples; keep host-specific
  settings out of Git.
* Keep the proxy and outbox's operational settings in their shared owner's
  file. Each provider records only the project and group needed to borrow the
  sockets in its own existing configuration; the shared SDK derives the volume
  names and in-container socket paths. The operator keeps these grants aligned.
* Document whether a value is sampled at deployment, read at startup or reloaded
  live. Keep Make help honest about which services a command replaces and
  which persistent volumes it retains. Do not introduce another configuration
  layer or elaborate validation to enforce these conventions.

Use one operator-owned TOML input for both shared services under the ignored
`config/deployments/<name>/settings.toml` path. It contains host/proxy and outbox settings, not provider
bindings, identities, credentials or CA files. Each service owns and applies its
own settings. Mount the containing dedicated configuration directory read-only
into the services so an atomic replacement of the file is visible. Each provider
uses settings in its own repository, not this shared-services file, and obtains
the socket grant projection from the shared SDK. The operator aligns the shared
project and access group across those deployment settings. Use existing operator paths and deployment
inputs; do not add a second configuration model or host-specific public values.
The selected local engine determines the container group that can read the
host settings group. Grant it only to the proxy and outbox, independently of
their socket group. The settings directory must remain group-searchable and
each replacement file group-readable; preserve its group and read permission
when editing so atomic replacement remains visible to both readers. Resolve
the mapping from a short-lived container on the selected local engine as seen
by the host, not from a container's potentially parent-relative self map.

The proxy periodically reloads max_connections, max_admission_delay_seconds,
admission_order, log_level and allowed_authorities. The admission delay is zero through 50% of
active forwarding capacity, then rises linearly to the configured maximum at
100%; its default is seven seconds. Each waiting connection keeps the delay
calculated on arrival. Waiting sockets do not occupy forwarding slots, their
number is bounded by max_connections, and disconnected or expired waiters are
closed. The wait uses the caller's existing exchange timeout, and a full waiting
queue can still refuse a connection. A delay change affects new waiters.
The default `ready` order starts the oldest connection whose delay has elapsed;
`fifo` keeps arrival order even when an older delay holds up ready connections.
Order changes apply to the current waiting queue. Delay is configurable from
zero to 30 seconds; waiters expire 30 seconds after their scheduled start.
For mapped/local routing, it reloads the corresponding hostname/address mappings
from the same file with the authority policy; an unmapped allowed hostname is
not silently resolved through another route. Existing tunnels keep their original
policy and connection. The network interface and Docker network remain fixed.
The outbox periodically reloads its queue capacity, retry policy and log level.
Lower capacity only constrains new admissions; it does not delete pending work.
Retry changes apply to subsequent attempts, not an already running exchange.
Each service retains its last successfully applied settings if a reload fails and
reports the failure without secrets. On restart, the intended file supplies the
settings again; the new value is not merely in-memory. If the file is missing or
invalid at startup, report the failure instead of silently inventing settings.
Keep reload handling small and independent of provider lifecycle. Fixed socket
paths/groups, process UIDs, network interface, resolver and mounts are deployment
settings; changing them is
not required for a provider to join or leave.

Illustrative shape, not an implementation or private host configuration:

    [deployment]
    project = "nmr-shared-example"
    uid = 10001
    proxy_uid = 10002
    gid = 10003
    request_seconds = 10

    [api_proxy]
    max_connections = 32
    max_admission_delay_seconds = 7
    admission_order = "ready"
    log_level = "INFO"
    allowed_authorities = ["api.example.invalid:443"]

    [api_proxy.route]
    mode = "mapped"
    interface = "eth0"
    addresses = ["api.example.invalid=192.0.2.1"]

    [outbox]
    provider_items = 8
    provider_bytes = 16777216
    total_items = 32
    total_bytes = 67108864
    retry_initial_seconds = 1
    retry_max_seconds = 30
    log_level = "INFO"

The host deployment also supplies its fixed proxy network and both socket grants
through this same input. The UID is the installing user's UID; proxy_uid must be a
different nonroot UID and gid is the shared socket group. The dedicated settings
directory and replacement file use the host settings group described above.
Values above are examples, not host settings.
For project P, the maintained deployment owns the P-proxy-socket and
P-outbox-socket volumes; clients borrow their proxy.sock and http.sock leaves,
respectively. The proxy runs as a separate Compose project and its socket volume
is external to the outbox project. A later outbox update must reuse the running
proxy without replacing it; incompatible fixed grants require operator attention.
The shared-package owner selects concrete SDK/CLI names with the provider owners
before release, including the shared intake mount/group and exact handoff. Earlier
020 symbols for per-binding projections and client-definition exports are not an
agreed implementation contract for this redesign.

Provider integration and retirement
-----------------------------------

Magnet converts production and real-API validation to the shared API grant and
outbox intake, retaining its existing candidate and scientific ownership. Its
old API-volume retirement must use its existing ownership evidence; ordinary down
retains volumes. Authored-API test routes remain owned by disposable fixtures.

NMRNet converts its provider and maintained real-API staging/readback paths,
preserving interpreter/store/scientific grants. Its old API route uses a bind
directory. Install prunes unused generations, so use the old owning recipe to
retire that directory before install removes the evidence. This is ordinary
resource retirement, not a requirement to keep an old deployment running.

NMRPeak converts its provider and journal/archive/maintenance API clients; one-off
borrowers need the shared mount/group and exact-volume existence behavior. Preserve
journal locks and existing retained-work rules. Adapt its existing owned-volume
teardown without granting it ownership of shared volumes.

SECS converts only the API and delivery grants; interpreter/store and worker
routes stay independent. Its current strict service inventory includes old API
roles and normal stop retains containers. Its maintained retirement must admit and
stop the observed old graph from the upgraded checkout before removing old API
resources. A separate optional check-api command is not a first-tier prerequisite.

The shared owner converts the existing delivery daemon and retires its old API
roles, private route volumes and per-binding intake resources after their users
stop. Preserve the queue and original obligations. Every owner keeps its existing
scientific, delivery and lifetime storage out of transport cleanup. A failed
cleanup retains enough ownership evidence for the owning workflow to finish it;
a healthy new service alone does not establish old-resource retirement.

Working agreements and remaining decisions
-------------------------------------------

The shared package supplies two client grants and the handoff through the existing
provider SDK. Agree concrete socket volume names, in-container paths, access groups,
SDK symbols and wire representation with the four owners. Do not assume the old
static binding parser or delivery's all-bindings client export still applies.
Keep the host-level operator file independent of provider identities; its live
settings and allowed-authority policy do not reconfigure the deployed proxy by
restarting it. Provider owners should identify only concrete integration conflicts
and necessary changes, then implement through issued SDK artifacts and their own
main-checkout workflows. No separate provider registration or compatibility layer.
