# provider-core 0.3.0

This release adds bounded live Attempt bookkeeping and reporting of positively observed worker crashes. Providers can use the shared SDK controller while retaining their own scientific preparation, model execution, offerings and configuration.

`AttemptController.live` and `AttemptClaims.live` keep the current supervisor's actual controllers and scientific sessions in memory. Capacity is reserved before START. Defaults allow eight reservations, 128 KiB of encoded control metadata per reservation, and up to 2 MiB for each terminal request. These limits cover bookkeeping and reports, not the whole process's memory or permission to run that many calculations. Live mode does not reconstruct Attempts or rerun calculations after a supervisor restart; the existing durable checkpoint interfaces remain available separately.

Each scientific session receives the original START acknowledgement and input checked against API-issued metadata. When preparation succeeds, calculation consumes that session's exact prepared handle once. A live START invocation allows its initial send and at most one permitted replay of the identical request and key within a 90-second decision window. Repeating START still requires the API client's approval, the configured retry wait and no stop that withdraws permission to send. Deferral preserves the original request and possible-commit uncertainty; it does not reset that budget or authorize a new key or calculation. An active-replay receipt does not prove that earlier science never ran, so providers choose that execution permission explicitly.

An original native exit associated with the current Attempt and scientific phase can produce a `worker_crashed` failure while reporting remains permitted. Its control message must identify the original worker operation. EOF, timeouts, requested stops and exit codes collected after deliberate interruption do not by themselves prove an unexpected crash. Native lifecycle messages retain the original retirement reason; an older message without that reason leaves attribution unknown. Public crash details identify the phase and verified exit status or signal without inferring an out-of-memory kill from SIGKILL alone.

Reporting and physical cleanup have separate duties. A locally selected COMPLETE or FAIL stays fixed if later cleanup fails; selection does not establish API acceptance. Before exiting, the owner must confirm physical cleanup and resolve its reporting duty: durable delivery has acknowledged the exact report, or the existing server-state and stop rules prohibit publication and the owner has retained that decision. `work_settled` alone is insufficient permission to exit; `shutdown_ready` also accounts for unresolved outcomes and reports. Unconfirmed cleanup keeps ownership held. `ProviderLifetime` uses an OS lock to prevent supervisors from owning the same private root concurrently. These mechanisms do not infer completion, create restart authority or replace server-owned expiry and capacity policy.

Delivery-intake, durable queue, publication and proxy interfaces are unchanged from 0.2.3. A delivery-intake acknowledgement transfers responsibility for the exact queued report; it does not establish API acceptance. Consumers still own their deployment, graceful drain, forced cutoff and model-specific retry policy. Native supervisors and bindings need the new observation/interruption handling to qualify unexpected exits; the SDK does not automatically classify every provider exception as a crash.

The qualified wheel passed 550 unit tests, 15 installed-package contracts and 158 contained integration tests. The source distribution rebuilt offline and its installed wheel passed another 15 contracts. Magnet and NMRNet separately tested adoption of the same wheel and source-archive bytes, including real model-free native processes and held cleanup. These checks establish infrastructure behavior; they do not establish numerical model accuracy, GPU behavior or deployment of this release.

Python 3.12 or newer is required. Runtime and build dependency versions are unchanged from 0.2.3. Distribution remains through GitHub Releases with the wheel, source distribution, complete hash installation lock, source record, artifact hash manifest and qualification logs. Earlier published assets remain unchanged.
