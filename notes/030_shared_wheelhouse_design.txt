Shared wheelhouse design
========================

Goal: one reusable host-local artifact pool; no wheel staging directories,
unnecessary downloads or cross-host artifact transfers. This is a joint design
for joint implementation. The shared tool is released; provider integration and
end-to-end qualification remain in progress.

Dependency authority
--------------------

Prefer one standard pylock.toml per supported target as the authoritative lock
for repository-owned dependencies. It records artifact URLs and hashes, avoiding
a separate committed manifest and custom index resolver. Select the declared
CPU or CUDA target explicitly. SDK-issued locks remain owned by the SDK; the
SDK owns any replacement format rather than providers independently changing it.

Implement the shared wheelhouse tool in Python, independently runnable from
provider-core. Pin PyPA packaging and use its public pylock selection API in the
actual target environment to select artifacts before downloading. This avoids a
separate Go binary and a second implementation of Python compatibility rules.

Upgrade and pin pip where needed to read the standard lock; inspected SECS and
Magnet images use pip 25.0.1, which predates pylock support. Current pip documents pylock reading
as experimental. Qualify the pinned version and existing uv compiler against
actual targets, PyTorch sources, SDK artifacts and ANTLR source builds before
changing locks or deployment. A pylock may list several wheels, so use supported
target selection before acquisition, without trial downloads; do not assume
one URL per package. Qualify the pinned packaging selector against the actual
installer and target. Avoid a second maintained compatibility lock.

Acquisition and build
---------------------

A small shared publisher, bootstrapped without provider-core, reuses valid local
files or streams a selected artifact to a unique .part file in the wheelhouse.
Verify its lock hash, sync the file, publish atomically without replacing an
existing file, and sync the directory. Coordinate simultaneous acquisition of
the same artifact so it is downloaded only once when successful.
Compare a concurrent winner; preserve and report conflicting bytes. Interrupted
transfers may need retransmission. Different artifacts with the same filename
cannot coexist in a flat pool; report the conflict.

Serialize publishers with a persistent pool-local acquisition lock, and hold a
shared pool lock during acquisition. Warm readers can use already-published
artifacts during a long download; existing exclusive pool writers still wait.
Keep the acquisition lock file in place so all publishers lock the same inode.
A reader that needs an artifact still being downloaded can report it missing;
only a successful acquisition establishes that its whole selection is ready.

Install from the selected local artifacts offline, preserving lock hashes and
source identities. A URL in a pylock does not automatically resolve to a local
wheelhouse just because indexes are disabled. Use a disposable local-path
projection of the canonical lock, or an equivalent supported remapping method;
it is not another committed authority. Verify target installation against the
selected files. Pip's normal cache may reduce network traffic but is not an
offline artifact authority: entries can expire and its layout is private. It is
not a required second cache.

The released wheelhouse tool can locate artifacts for an existing target-specific
requirements lock from index metadata without downloading wheel bodies. Run it
under the target Python, and pass the same original lock as `--source-lock`
when consuming its projection. The tool checks the selected package closure,
versions and hashes against that lock, including direct URLs recorded there.
Separately supplied source URLs remain the provider's responsibility: matching
the locked hash establishes the bytes, not the origin of such a URL.
With a selected pool, the locator can freeze an already cached compatible
wheel into the projection. Consume that projection throughout acquisition and
build when the same artifact choice must be preserved; a later independent pip
selection over the whole pool may choose a different compatible wheel. This
preference must not override an issuer's direct source or source policy.
When an equality pin admits more than one concrete version, such as local
versions, a projection selects one version. Source preference and then cached
wheel reuse take precedence over selecting the highest admitted version; this
can differ from an independent pip selection.

Supply only selected files to BuildKit from the shared pool. Stream a curated
primary build context containing source and selected files without an on-disk
wheel staging directory; bind selected inputs to image identity and keep
wheels out of runtime images. BuildKit may retain selected bytes in its cache.
Protect inputs until build retirement, including uncertain client disconnects.

Qualification and rollout
-------------------------

Before migration, prove the standard lock and supported installer select the
right artifacts for our pinned target environments, source variants and source
archives, and work offline with the exact pool inputs. Ensure lock compilation
does not discard a downloaded artifact only to fetch it again. Verify cache
reuse, interrupted downloads and conflicting filenames, and measure BuildKit
transfer. Adopt across shared tools and providers after this review, leaving the
current deployment working until each replacement is qualified.
If a wheel is built from a source archive, its source hash alone does not
identify the built wheel; identify the builder and resulting bytes before reuse.

Current migration limits
------------------------

Provider-core and shared delivery now use the released publisher for normal
wheel acquisition; their normal Make targets still need a genuine missing-wheel
cold-path qualification. Provider-specific migrations are tracked by their
owners and must not be inferred from these shared-tool changes.

The shared delivery image build now streams its selected wheels and captured
source into BuildKit, without exposing the pool as a build context. Its normal
preparation also uses the released shared publisher for missing release wheels.
Maintained preparation and the offline released-publisher check passed on both
hosts. These checks reused cached wheels; a genuinely missing release wheel
through normal preparation still needs qualification. A synthetic missing
wheel was acquired and reused through the generated delivery lock and released
publisher on both hosts without re-downloading a real dependency.

The shared tool's own image likewise streams its selected wheels and source;
its image build and wheelhouse suite passed on both hosts using cached inputs.

The remote offline build completed, but its system shell emitted an unbound
`PS1` warning in noninteractive execution. The host shell configuration needs
separate cleanup; the warning did not change the build result.

Some lock compilers fetch a wheel to obtain metadata when its index does not
offer a metadata sidecar. A subsequent acquisition can fetch that wheel again.
Avoiding that repeat across all supported sources is still unresolved.

One issuer-owned option to qualify is to project a complete existing pinned
closure through the package index's Simple API: use its artifact filenames,
URLs and hashes only where the hashes already appear in the issuer lock, then
issue a standard URL-bearing lock. The original lock supplies versions and
hash authority; this does not solve dependencies again. Target compatibility,
source distributions and separately pinned non-index artifacts still need
their established owners. Missing index metadata must remain a visible failure,
and this cannot recover a wheel a compiler already downloaded and discarded.
