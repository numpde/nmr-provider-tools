Isolated acquisition workers
============================

0.6.0: one common acquisition owner
----------------------------------

The shared end state includes lifecycle ownership, not just proxy transport.
One host-side implementation in this repository owns offline worker probes,
Engine-relative identity mapping, lazy gateway/relay startup, ordered worker
execution, readiness, cancellation and confirmed dependency retirement. Provider
repositories must replace their repeated lifecycle implementations with thin
adapters to that owner. Do not copy another repository's shell controller.

Adapters retain target/profile selection, worker image and application argv,
explicit filesystem grants, stdout destinations and interpretation of their
settled worker results. Docker creation grants and application argv are
separate inputs, so an application argument named --network is not mistaken
for an Engine option. Existing pool locking, hashing and publication retain
their current authorities.

An owned scope supports multiple ordered workers: offline checks, then locate
and acquire operations with per-worker output, then final offline checks. A
warm hit must not select a route or start gateway/relay containers. Worker exit
status is available only after its lifecycle is settled; Engine/client failure
or unconfirmed retirement cannot become a cache miss. Preserve clean data
stdout, original failure/cancellation and the exact unresolved ownership fact.

Probe the pinned bootstrap image once per scope and reuse its mapped host owner
for gateway, relay and workers on the same selected engine and default user
namespace policy. The owner rejects a worker user-namespace override. Worker
images do not need a Python probe interpreter. The standalone mapping API
remains available for callers outside an acquisition scope.

Docker's engine-level mappings and default namespace policy are documented at
https://docs.docker.com/engine/security/rootless/uid-gid-mapping/ and
https://docs.docker.com/engine/security/userns-remap/.

Python bootstrap imports must not write bytecode into the verified source.
Use -B explicitly for isolated Python: -I ignores PYTHONDONTWRITEBYTECODE.
Qualify two complete sessions against one source snapshot, checking its exact
inventory after each; a successful first run alone does not prove reuse.

An explicitly requested acquisition target may attempt locked repair after a
settled offline report fails to establish a usable selection. This does not
classify every report failure as a missing wheel. Keep the report diagnostic,
existing input/hash checks and mandatory final offline verification. Do not
build a second dependency resolver merely to distinguish pip's exit status 1.

Ship the complete release-verified bootstrap closure in each consumer before
an empty wheel pool is used. Include the exact qualified linux-idmap identity
component if used; an ambient host installation or an initial network fetch is
not a bootstrap dependency. Reuse one upstream implementation and generate
consumer bootstrap bytes from its qualified release. No additional operator
configuration file, cross-checkout registry or scientific runtime dependency
is required.

This repository consumes the same qualified bootstrap as its providers. Its
authored acquisition_tool remains the next release's input; build and download
operations use the checked-in prior release under bootstrap/acquisition, with
its public issuer record in requirements/acquisition-owner-release.json. This
avoids requiring a new release to acquire its own build dependencies. Normal
operations verify and source those bytes directly. Maintained
packages/acquisition-bootstrap/check and packages/acquisition-bootstrap/refresh
targets own verification and explicit refresh from reviewed ARTIFACTS.

0.5.17 already supplies the qualified Unix proxy/relay transport below. Its
consumer-owned lifecycle wrappers are the intermediate state being replaced
for 0.6.0. Preserve working deployments and audited WIP while converging on the
shared owner. Common conformance tests cover the lifecycle once; each repo
also proves its actual thin adapter and selected-host acquisition path.

Implementation and language choice
----------------------------------

Use a sourced Bash session API for 0.6.0, reusing the existing native process
supervisor and qualified linux-idmap probe. All four maintained acquisition
drivers already use Bash. Their callbacks make decisions between workers,
hold existing pool locks, and stream or capture output for the next worker.
Separate image, creation-option and application-argument arrays preserve
those contracts without adding a Docker command-line parser.

A static Go executable could simplify distribution and eliminate ambient
Python dependencies if it also supplied the identity implementation. A Go
session API is viable, but existing Bash consumers would need an explicit
session boundary or compiled adapters. Existing local Go subprocess helpers
do not establish acquisition cancellation, namespace identity or dependency
retirement. Reimplementing those for this release would add qualification
work; wrapping one-shot commands would still leave lifecycle duplication.
Keep Go as a possible replacement behind the same behavioral tests, rather
than making a language migration prerequisite for joint deployment.

The source bundle carries the complete pinned Python identity/proxy closure
and canonical shell supervisor; consumers do not install host packages or
compile during cold acquisition. The scope must preserve caller traps and
primary status, handle callback exit and direct cancellation, and clean once.
An extra background shell is not cancellation ownership. Confirm these with
real signal witnesses before claiming the shared scope is ready. Reconsider
Go if measured host/bootstrap costs or actual consumer needs justify the
session boundary and its complete, qualified replacement closure.

Cleanup authority belongs to the owning shell process, not its function stack.
Bash can unwind local variables before running EXIT after an unguarded command
fails under set -e. Early tests covered explicit exit and ordinary return with
errexit disabled, so they did not establish this failure path. Keep reserved
session state alive through EXIT, bind it to the owning BASHPID, and initialize
it afresh for every scope. A child callback shell has no authority to retire
its parent's containers; the original process cleans once and preserves the
caller trap and original status. Only one scope is active per shell process.

Requiring every callback to guard every command leaves a recurring cleanup
footgun. Calling callbacks inside a conditional would suppress their errexit
semantics; a background scope would need another cancellation owner. Retain
the inline API with process-owned state instead. Qualification includes an
actual online session followed by bare failure under set -e, direct signals,
dependent-removal failure, blocked diagnostic pipes and consecutive sessions.

Joint first milestone
---------------------

An acquisition worker must have no direct external network route. Its existing
HTTP/CONNECT clients reach the selected-route proxy through a loopback relay.
Proxy environment variables alone do not enforce that route when the worker
shares host networking.

Use three separately owned containers:

* Gateway: existing interface-bound HTTP/CONNECT proxy in host networking,
  listening on a private Unix socket. An explicit system selection retains
  normal host routing without a device binding.
* Relay: network none, loopback TCP listener forwarding only to that Unix
  socket. It owns the worker's otherwise disconnected network namespace.
* Worker: network container:<verified relay CID>, receiving the relay's
  loopback HTTP_PROXY/HTTPS_PROXY address. There is no direct-route fallback.

Do not substitute an internal bridge: a bridge can expose host gateway paths
that are unnecessary for this topology. This change enforces route selection;
proxy-mediated destination permissions retain their existing semantics.

Implemented transport and initial bootstrap
------------------------------------------

provider_core.bound_http_proxy owns the Unix listener and relay transport.
0.5.17 provides a release-verifiable snapshot of that module, container_guard.py
and __init__.py for consumers to check into their own repository. Refresh it from the exact
qualified wheel and pinned release/source record, using maintained targets.
The snapshot must already be available with an empty wheel pool, before the
wheelhouse tool or provider-core itself is acquired. No sibling checkout,
private fork, additional runtime dependency, or staged wheel copy is required.

The gateway publishes readiness only after binding its private socket. The
relay publishes its actual loopback port only after binding. The launcher
checks the exact owned relay container before admitting the worker, and uses
the engine-probed mapped identity for socket access. The worker does not mount
the Unix socket directory or receive host networking.

Gateway invocation:

    python -m provider_core.bound_http_proxy --interface <device-or-system> --unix-socket /gateway/proxy.sock --ready-file /ready/gateway

Relay invocation:

    python -m provider_core.bound_http_proxy --relay-socket /gateway/proxy.sock --port 0 --ready-file /ready/relay

Both run in the guarded container environment. Gateway readiness is exactly
the Unix socket path followed by a newline; relay readiness is its numeric
TCP port followed by a newline. The Unix listener mode is 0600, accessible to
the gateway and relay's mapped identity in their private directory. Existing
TCP proxy callers retain their explicit --interface and --port invocation.

Retire worker, then relay, then gateway. Preserve inputs while their actual
process/container reader remains unresolved; ordinary settled failure cleans
disposable inputs and preserves the primary failure. Do not let the new relay
bypass the existing CID, cancellation and cleanup owner.
If worker removal is unconfirmed, retain its supporting relay and gateway;
if relay removal is unconfirmed, retain its gateway. Local client retirement
alone cannot establish successful engine removal.

Proof and adoption
------------------

The shared package tests HTTP/CONNECT over Unix transport, relay forwarding,
bounded admission and failure without direct fallback. A maintained selected-
engine qualification uses the existing pinned Python image without pulling:
prove the worker shares the relay namespace, Unix socket access works, direct
external connectivity fails, relay traffic succeeds, and failed/cancelled work
retires in the required order. Qualify the actual topology on both deployment
hosts, rather than treating printed arguments as runtime proof.

Then prove real acquisition on each selected device, including DNS and TCP
binding evidence, direct-to-pool publication and a cold tool bootstrap. Each
provider owns its actual launcher/bootstrap tests and verifies peer findings
were integrated. Existing offline cache checks remain network none.

Deferred boundaries
-------------------

Bootstrap refresh is explicit checkout maintenance with acquisitions quiescent.
It does not hot-swap source beneath running or unresolved owners. Ordinary
refresh failure restores the old source/issuer pair; automatic recovery from
abrupt termination during a source-directory exchange is deferred.

The acquisition rollout updates the common host owner, provider controller and
configured workers through their maintained deployment paths. Preserve each
deployment's selected CPU or GPU hardware; acquisition qualification does not
require running a scientific inference job.

A Docker metadata timeout may leave an identity-probe creation unresolved.
The owner retains its operation token and inputs instead of claiming absence;
normal settled failures clean automatically. Automatic reconciliation of a
late-created probe remains a library limitation. Recovery must verify the
exact owned probe before removing it; it must not prune unrelated resources.

The broad repository quality suite is not a green release claim for this
rollout. Its outstanding findings include older silent-default annotations,
assertion formatting, target-inventory assumptions and ignored Python caches.
The acquisition, provisioning and bytecode lanes provide focused evidence;
unrelated checker-policy cleanup is deferred rather than weakening detectors
or turning this deployment into a repository-wide formatting migration.

Docker daemon bootstrap-image pulls retain their explicitly permitted normal
route. Git/source synchronization also retains its existing routing policy.
These are not runtime acquisition-worker traffic.

Networked BuildKit executors cannot use docker-run container namespace
sharing. Existing runner/test-base/benchmark apt fetches and the frontend npm
fixture require a separate offline-input/build design. They are not claimed
isolated by this milestone. Avoid delaying the common worker deployment with
an apt/npm mirror redesign or a new destination firewall.
