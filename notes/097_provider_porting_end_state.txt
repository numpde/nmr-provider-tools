# Provider porting: desired end-state

A provider supplies its science, declares its operations once, and assembles its
configuration and request workflow. The SDK supplies execution, retained request
ownership, observation and cleanup. Startup selects thread or persistent-process
execution without changing the prediction workflow.

Examples should use consistent responsibility boundaries:

- science.py: scientific types and calculations.
- binding.py: operation declarations, scientific initialization and cleanup.
- provider.py: configuration, scientific selection, backend and lifetime assembly.
- application.py: provider-specific request sequencing, where needed.
- process_factory.py: installed child construction, where process execution exists.

Optional files should represent actual optional responsibilities. Scientific
differences remain explicit; examples need not share a prepare/generate sequence,
model registry or interpretation layer.

Models and prepared state stay with their scientific owner. Original submissions,
observations and cleanup survive cancelled waits and uncertain replies. Independent
process offerings retain independent lifetimes and availability. Shared resource
allowances belong to an enclosing owner and cannot multiply when workers are added.

The examples should demonstrate complementary parts of this contract: Dummy for
minimal integration, Reference for persistent resource reuse on either backend,
Spectrum for multiple scientific stages, and NMRPeak for interpretation, checkpoint
loading, consumed state and delivery. This is a desired alignment, not a claim that
all examples already support both backends.

Next, port Reference to both backends and use that second implementation to expose
remaining NMRPeak assumptions. Then align the other examples and write the porting
guide from the working code. Preserve one allocation per process host; multiple
scientific stages require explicit provider composition and resource ownership.

Acceptance: another provider can be integrated through provider code and
configuration, using its unchanged workflow on both backends, with demonstrated
reuse, failure and retirement. Copying execution machinery, modifying the SDK for
ordinary integration, or adding backend branches inside the workflow indicates a
remaining gap. Real-model/GPU and deployment qualification remain separate gates.

## Dummy port: minimal startup and observed SDK friction

Dummy now has explicit deployment-selected startup and an installed constructor
for its weighted contribution. The same constructor captures scientific settings
and coefficient arrays in either owner; only the selected process constructs its
process-local contribution. Both startups initialize the model before yielding.
The thread initializer is called explicitly after adoption; process start already
performs initialization. Partial initialization and host retirement remain SDK-owned.

ProcessExecutionHost accepts one contribution/allocation per native session. Dummy
therefore selects one weighted offering; its separate stateless Sum remains a
binding example rather than silently adding a second worker or resource allowance.
The caller supplies the deployment-owned native RunnerSession for process startup.
Configuration refusal before host construction leaves that session with its caller.

Process hosted contributions have no parent scientific receiver. Portable callers
use hosted.call and SDK Submission.from_call instead of submit_method. The same
prepare/calculate sequence can then run on either backend with the custom sample
codec and analysis-local scientific session unchanged. No application module is
needed: Dummy has no additional request decision beyond those two scientific calls.
The SDK retains each original Submission/operation; another wait or submit on that
Submission does not create scientific work. Installed startup tests cover rejection
and correction, state transfer, report consumption, model/child reuse and retirement.

Spectrum port: concrete SDK friction (dirty-source development checks passed)

Spectrum retains baseline subtraction followed by peak detection as two independent
scientific stages. ProcessExecutionHost admits exactly one allocation, so provider
composition owns two SDK hosts and two analysis lifetimes on both backends; no SDK
composite executor or scheduler is introduced. The workflow uses the same retained
submissions and portable baseline-result handoff on either backend.

Each SDK host owns independent aggregate input_bytes, result_bytes and state_values
counters. There is no enclosing SDK counter pool spanning process hosts. Spectrum
therefore validates explicit static stage shares against one enclosing allowance
before taking native runner sessions. It cannot borrow an idle stage's share. These
are SDK accounting limits, not hardware grants; CPU/device availability remains
deployment-owned. Copying a complete enclosing allowance to each host would silently
multiply that allowance and is not the selected design.

The SDK requires positive state_values even for stateless scientific contributions.
The example configuration explicitly grants two slots, one per host, rather than
silently increasing a previous one-slot allowance. progress_records bounds retained
history per operation and is not summed as an aggregate host counter. Initialization
and retirement time allowances remain per-host policy. Shared counter pooling and
zero-state-slot hosts are concrete remaining SDK integration constraints, not
reasons to add provider execution machinery.

NMRPeak port: independent model ownership (dirty-source development checks passed)

The previous process path admitted one configured model. Startup now composes one
existing SDK process host per configured (family, index), supplied with a distinct
deployment-owned session. The prediction workflow is unchanged. These positional
keys select fresh startup entries; the surrounding service still owns durable
offering identities and native deployment grants.

Each model declares static process_capacity shares of the provider's aggregate
input, result and state allowance. Startup rejects an overgrant, missing session
or reused session before constructing any host. Progress retention remains per
operation. Thread allocations keep their existing shared-host aggregate counters;
process hosts cannot borrow another model's unused share. Hardware budgets remain
deployment responsibilities, rather than being inferred from these SDK counters.

Each entered host remains owned while a later model starts; AsyncExitStack unwinds
every entered lifetime if a later child fails. Existing scientific workflows need
no backend branch or parent model access. New installed cases exercise HF retirement
while CHF serves sequential requests, pre-acquisition capacity refusal preserving
caller descriptors, and failed CHF startup retiring the earlier HF child. The SDK
supports this composition without a new supervisor, registry or scheduler.
