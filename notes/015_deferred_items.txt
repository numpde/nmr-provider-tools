Shared wheelhouse direct publication
------------------------------------

The shared wheelhouse is the package cache. Acquisition reuses suitable cached
artifacts and downloads missing artifacts directly into that pool without a
separate pip cache or repository-managed staging directory. Pip verifies the
locked hashes, but its direct destination handling can replace a same-named
file whose bytes do not match the current lock, and its final file copy is not
atomic for concurrent readers. A failed acquisition can leave a partial file.
Do not treat a filename alone as proof of the expected bytes. These limitations
are accepted for the current controlled-host deployment; revisit publication
if a real conflict or concurrent read makes it necessary.

The delivery image build uses the selected wheelhouse as a read-only named
BuildKit context. The operation context contains the generated install lock and
expected filename/hash identities, not copied wheel payloads. The build checks
those identities against the pin and the actual install report.

Bounded diagnostic rendering across actual consumer sinks
--------------------------------------------------------

Owner: provider-core rendering, with each provider owning its logging envelope.
Priority: follow-up after the qualified outage/deadline release and deployment;
revisit sooner if a real incident loses protected diagnostic evidence.

Constructed witnesses produced a 43,290-byte record, an atomic 4,096-byte pipe
refusal, and invalid JSON after a consumer's 8,192-character slice. The inspected
live incident records were 694-3,141 bytes and valid; those observations do not
prove the general case safe. Retain valid JSON, bounded UTF-8 bytes including
the actual envelope, coherent references, explicit omissions, and primary and
independent cleanup evidence. Never substitute raw exception text or tracebacks.

The previously discussed bounded-diagnostics proposal is an experiment, not an
accepted implementation. Its fixed eight-node priority quota has no established
justification. Review cause/group versus incidental-context
ordering and repeated-reference accounting without making traversal unbounded.
Include safe symbolic DNS reasons without copying raw private exception text.

Qualification must use actual sinks: NMRNet's atomic pipe allowance, Magnet's
logging envelope and escaping, and SECS's blocking handler and fatal writer have
different contracts. A shared renderer must expose its budget clearly; consumers
must supply the allowance remaining after their own framing. Do not add another
provider-local serializer. D125, D131 and D136 in the running decision note retain
the design obligations. This work does not block the independently qualified
availability, deadline and cancellation corrections in 0.5.1.

Provider roadmap exercises suggested preserving API CONNECT/TLS versus scientific
source-acquisition context in the existing client logging envelope. Keep bounded
operation labels and safe native status/request identifiers within the same
rendering budget, without signed headers, payloads or a second serializer. This
is a proposed improvement, not a newly observed incident or API-router deployment
gate; separate listeners or a registration protocol solely for attribution are
outside that follow-up.

Absolute caller deadlines through the chat carrier
-------------------------------------------------

Owner: provider-core ChatEndpoint, with the model caller supplying its deadline.
Trigger: a caller needs an explicit no-dispatch-after-turn-expiry contract, or
the next change to the chat deadline interface.

ChatEndpoint.complete currently constructs JSON and an HTTP request before the
transport starts its relative exchange allowance. It exposes no absolute cap;
an outer asyncio.timeout cannot preempt synchronous construction. A constructed
installed-package witness shows the original transport task can enter after that
outer allowance expires. A stronger witness uses the actual _perform and records
the request reaching a fake connection pool after expiry. These authored schedules
do not prove bytes reaching a network peer, a live incident or a violated explicit
absolute carrier contract. Existing transport I/O bounds remain a separate guarantee.

If that stricter caller contract is adopted, pass one explicit absolute deadline
through the existing chat/transport owner, checking after construction and before
dispatch and retaining it for original cleanup observation. Do not infer timeout
contexts dynamically, copy the carrier into a provider or add another Task owner.
Qualify actual dispatch refusal under controlled slow construction/pacing before
claiming the effect boundary. D151 records the alternatives and deferral rationale;
the existing qualified deployment and published artifacts remain unchanged.

Cancellation cleanup diagnostics for acquisition
------------------------------------------------

Owner: shared acquisition launcher (tools/docker.sh).
Trigger: next change to launcher cancellation or an incident requiring retained
cleanup evidence; review after the current provider deployment.

On actual signal cancellation, the launcher preserves the signal exit status
and deliberately suppresses cleanup diagnostics to avoid blocking on an unread
stderr pipe. If worker or proxy identity cannot be admitted or removal cannot be
confirmed, its private scratch receipts are retained, but the caller is not told
that cleanup is uncertain or where to find them. Repository tests explicitly
exercise this silence. This is an observed diagnostic gap, not evidence that a
container survived or that a deployment failed.

Find a bounded, discoverable operator evidence channel that preserves prompt
cancellation and truthful uncertainty, including when stderr is blocked and
when evidence publication itself fails. Do not print sensitive configuration or
claim removal without engine evidence. D207 records the tradeoff.
