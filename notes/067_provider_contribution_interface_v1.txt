Provider contribution and execution interface v1
================================================
9 November 2026 | Implemented shared contract; real-provider adoption remains open

Purpose
-------
This note records the concrete provider-facing interface implemented in
provider-core. Notes 064-066 retain the architecture, safety rules and rollout
plan. This note owns the implemented v1 names and distinctions.

The dummy provider is a standalone consumer example under
examples/dummy-provider. Its installed package contains science, the
contribution binding and its local resource TOML; its ordinary tests exercise scientific behavior,
binding declarations and an installed local-host call sequence. Shared
execution and provider service responsibilities remain in provider-core.

Provider-owned scientific types
-------------------------------
A contribution defines ordinary provider-owned types for its scientific facts.
The dummy uses separate immutable dataclasses for:

- WeightedSumSettings and CoefficientSet;
- PreparationInput and SumInput;
- PreparationResult, PredictionResult and SumResult.

Equal wire shapes do not collapse distinct meanings. PreparationInput and
SumInput both contain values, but they are different types with different format
identities and different scientific functions. The science module receives no
JSON dictionaries, transport lists, anonymous tuples or execution controllers.

Live scientific state is separate from portable payloads. The dummy has a loaded
WeightedSumModel, one WeightedSumAnalysis and worker-local PreparedValues.
CalculationState is the typed view of retained state required by calculate. Calls
with no portable fields use shared NoInput and the shared
provider-core.no-input.v1 wire format; calls with no retained scientific state use
shared NoState. Contributions do not define empty records or provider-specific
empty formats merely to satisfy the host interface.

Shared structural admission
---------------------------
JsonDataclassCodec[T] owns UTF-8 JSON parsing, duplicate-field rejection, exact
field admission, finite-number checks and construction of T. Portable records
must be frozen and slotted. Mutable list and dict annotations are refused; use a
tuple or a named nested dataclass. PayloadRejected identifies structural refusal
before science runs.

DataclassStateBinding[T] checks the declared state names and live value types, then
constructs T immediately before the scientific call. The provider does not receive
Mapping[str, object].

CallBinding[InputT, StateT, OutputT] preserves provider types through the
host-local call:

    bytes
      -> PayloadCodec[InputT]
      -> InputT
      -> StateBinding[StateT]
      -> scientific call(InputT, StateT)
      -> ScientificReturn[OutputT]
      -> PayloadCodec[OutputT]
      -> bytes

CallBinding.from_json_dataclasses(...) connects explicit concrete input/state/
output types, codecs and a scientific context adapter. Typed state slots own
input kind/use and output names/disposers; the constructor derives their wire
declarations. NoState is the shared empty state; NoInput has one shared format.
CallBinding.from_function(...) binds an ordinary unary input-to-output function
without model, state or control dependencies.

An adapter accepts one positional CallContext[Instance, Analysis, Input, State]
and returns ScientificReturn[Output]. The parameter name has no special meaning.
The context contains scientific values, with control absent unless progress or
cooperative interruption is declared. Lifecycle annotations must agree with the
actual instance and analysis hooks; input/state/result annotations must agree
with their codecs. See 085 for typed named members and the identity migration.

Scientific and structural refusal remain distinct. ScientificInputRejected derives
directly from ScientificRejection and supplies the stable code and explanation
expected by shared execution. The lightweight contract lives in
provider_core.contribution_errors, so direct scientific use does not import the
host interface or require the contained runtime launcher. contribution.py and
payload.py re-export the same rejection classes for their existing callers.
Unexpected defects remain failures rather than becoming invalid input.

Scheduler description and host-local binding
--------------------------------------------
The scheduler-readable ImplementationDescription contains only immutable data:

- binding identity and explicitly versioned configured revision;
- optional configuration format and digest;
- named assets with media type, size and digest;
- resident and per-call resource requirements;
- minimum process isolation and call concurrency;
- named calls, formats and state borrow/consume rules;
- cooperative interruption and progress capabilities.

It contains no factories, provider objects, paths, credentials, framework devices
or cleanup owners. The host-local ImplementationBinding contains the configured
factories, lifecycle hooks, codecs and scientific callables inside the authorized
scientific environment. Providers declare ordinary frozen dataclass subclasses
with typed call fields such as binding.match. SDK construction derives the
private dispatch inventory from those fields once; ref(binding.match) projects
the exact configured call reference. Provider assembly factories are optional
provider-owned helpers, without discovery or a prescribed name.

provider_core.contribution_declaration owns canonical JSON encoding for
configuration/asset descriptions and their content sha256 digests. ConfiguredIdentity
owns those descriptions and derives the configured-v2 revision from their complete
semantic metadata, implementation assertion and contract version. None remains
distinct from an explicit empty configuration. Legacy sha256 reference syntax
keeps its original meaning; fresh hosts use v2 and existing owners drain under
their original revisions. There is no conversion or replay. See 085.

ScientificControl is the only optional operational capability visible to an
adapter. It exposes a stop flag and bounded progress reporting, not Jobs authority,
resource allocation, process control, credentials or a service client. Numerical
functions need not receive it; the dummy keeps it in the binding adapter.

Shared execution
----------------
provider_core.hosting defines resource grants, backend capabilities, exact
allocation/reservation/operation/state/result references, identified invocations,
typed definite non-admission, observations, result custody, analysis-scoped
control and pool-owned allocation retirement.

An Operation returned by submit is already owned. NotAdmitted means this
invocation caused no dispatch or orphaned acquisition. Re-observation never
resubmits work or renews its budget. Analysis code cannot retire a shared
instance; pool administration owns that capability.

observe_completion(operation) waits on an existing operation and returns its
terminal Observation without interpreting scientific outcome or result
availability. observe_cleanup(control) waits on an existing result release,
analysis cleanup or instance retirement, returns its settled observation and
propagates reported original failures (grouping independent causes only when
needed). These shared helpers do not submit, stop, release, close or retire
anything. Cancelling a wait leaves the original request owned; the caller owns
the observation timeout. An expired allowance alone does not prove settlement.

ResultConsumption owns one exact result's receiver attempt and subsequent
release. start() retains the task before reading bytes or invoking the receiver;
wait_for_acceptance() joins that same task without authorizing release. consume()
observes acceptance, requests release only after the receiver returns successfully,
and retains the original ResultRelease for later observation. Successful receiver
return remains known even if the release request raises synchronously. Exact
release requests return their original control after settlement as well.

Cancelling a consumption waiter leaves its original receiver attempt running.
The caller retains the owner and joins acceptance before closing any resources
the reader or receiver may use. Receiver failure is retained without an automatic
resend; a lost acknowledgement stays uncertain under the receiver's own contract.
Only the receiver establishes durability or publication. Scientific sequencing,
admission/refusal decisions and cleanup order remain with the caller. This owner
has no Job/Attempt authority or persistent recovery record.

The operation, exact result and receiver are fixed when the consumption owner is
created. settle() is the shutdown join for an already-started owner: it finishes
one consume observation through acceptance and release before propagating waiter
cancellation, preserving independent failure causes. It may wait indefinitely;
an untouched owner returns None without starting a receiver. Callers needing a
bounded wait use consume() and retain the owner and its dependent resources.

The bounded embedded backend exercises the contract with fixed local allocations.
It refuses unsupported isolation, process-global serialization and missing grants
before scientific construction. Resource-grant refusal is tested with a synthetic
requirement. The dummy itself does not claim a made-up resident quantity for its
small coefficient tuple. The backend cannot forcibly interrupt Python, persist
work across a process crash, enforce operating-system resource limits or execute
remotely. Those are backend capabilities, not restrictions on contributions.

Standalone dummy-provider example
---------------------------------
examples/dummy-provider is its own Python project with pyproject.toml,
src/dummy_provider and tests. Its installed package contains only science.py,
binding.py, resources.toml and its package marker. The ordinary tests have distinct purposes:

- test_science.py checks direct calculations, rejection and correction.
- test_binding.py checks the scientific binding's types and installed boundary.
- test_execution.py performs one prepare/calculate sequence using the public
  EmbeddedHost, Invocation and result-custody interfaces.

The stateful implementation demonstrates configured model and analysis
lifetimes, preparation, worker-local prepared state, consumption and progress.
A stateless sum binding demonstrates the same contribution interface without
a model or analysis lifetime. Provider-core's native tests already cover the
generic permission, ownership, allocation and cleanup rules with a private
fixture under tests/fakes.

Provider-owned integration tests
--------------------------------
ProviderFixture, CallFixture, AnalysisFixture and the test-only scenario runner
were removed. They duplicated normal unittest test methods and recreated
operation sequencing outside providers' production code. The installed
integration lane still independently builds both wheels, installs them outside
their source trees and runs the dummy provider's ordinary tests.

Real providers should extend their existing scientific and native-worker tests
to exercise production binding factories through the actual execution backend.
A local embedded-host test checks that a contribution can use the public API;
it does not qualify a native protocol or a deployed service.

Current evidence and limits
---------------------------
The revision following cfa39f7 was reviewed against numpde/hello-world
notes/000_portable_engineering_practices.txt at main@8e7eb12. The detailed review
passes and focused evidence are recorded in note 068. Subsequent simplification
removed detached call declarations, generic hashing from the provider adapter,
catch-and-rethrow rejection translation, global adapter callables, repeated exact
class checks, provider-specific empty marker records, unchecked lifecycle-hook
annotations, forced five-argument adapters and an unmeasurable dummy
resident-resource declaration.

The previous focused harness compiled the revised modules and ran 26 typed,
declaration and boundary tests. The installed integration lane was later reported
passing before removal of the scenario runner. The replacement ordinary test
suite still requires an actual contained run against this revision.

SECS, NMRNet, NMRPeak and Magnet still need their real scientific and guarded
execution paths connected to this installed contract. Existing AnalysisSession
permission checks remain until the host-managed path is equivalent and qualified.
Jobs integration, durable operation/result records, remote execution and
phase-specific scheduling remain later shared work under notes 065-066.
