Provider contribution and execution interface v1
================================================
9 November 2026 | Implemented shared contract; real-provider adoption remains open

Purpose
-------
This note records the concrete provider-facing interface implemented in
provider-core. Notes 064-066 retain the architecture, safety rules and rollout
plan. This note owns the implemented v1 names and distinctions.

The dummy contribution is intentionally science-only. It implements the
contribution interface but none of the shared service, scheduling, hosting,
permission, recovery, delivery or deployment machinery.

Provider-owned scientific types
-------------------------------
A contribution defines ordinary provider-owned types for its scientific facts.
The dummy uses separate immutable dataclasses for:

- WeightedSumSettings and CoefficientSet;
- PreparationInput and SumInput;
- PreparationResult, PredictionResult and SumResult.

Equal wire shapes do not collapse distinct meanings. PreparationInput and
SumInput both contain values, but they are different types with different format
identities and different scientific functions. The science module receives no
JSON dictionaries, transport lists, anonymous tuples or execution controllers.

Live scientific state is separate from portable payloads. The dummy has a loaded
WeightedSumModel, one WeightedSumAnalysis and worker-local PreparedValues.
CalculationState is the typed view of retained state required by calculate. Calls
with no portable fields use shared NoInput and the shared
provider-core.no-input.v1 wire format; calls with no retained scientific state use
shared NoState. Contributions do not define empty records or provider-specific
empty formats merely to satisfy the host interface.

Shared structural admission
---------------------------
JsonDataclassCodec[T] owns UTF-8 JSON parsing, duplicate-field rejection, exact
field admission, finite-number checks and construction of T. Portable records
must be frozen and slotted. Mutable list and dict annotations are refused; use a
tuple or a named nested dataclass. PayloadRejected identifies structural refusal
before science runs.

DataclassStateBinding[T] checks the declared state names and live value types, then
constructs T immediately before the scientific call. The provider does not receive
Mapping[str, object].

CallBinding[InputT, StateT, OutputT] preserves provider types through the
host-local call:

    bytes
      -> PayloadCodec[InputT]
      -> InputT
      -> StateBinding[StateT]
      -> scientific call(InputT, StateT)
      -> ScientificReturn[OutputT]
      -> PayloadCodec[OutputT]
      -> bytes

CallBinding.from_json_dataclasses(...) is the normal constructor for this path. It
reads the provider input, live-state and output types from the scientific
callable's annotations; constructs the codecs and state binding; and creates the
CallDescription from the same statement. A provider does not maintain separate
codec constants, state-binding constants and call descriptions for one call.

A scientific adapter declares required keyword-only parameters selected from
`instance`, `analysis`, `scientific_input`, `state` and `control`, in that order.
It omits values it does not use. Omitting `scientific_input` selects shared
NoInput; omitting `state` selects shared NoState. `control` is permitted exactly
when the call declares progress or cooperative interruption.

The binding checks that codec formats agree with CallDescription and that each
present parameter and ScientificReturn[OutputT] has an exact concrete annotation.
Any requested instance or analysis type must match the implementation's lifecycle
hooks. Positional, optional, misordered, unknown and operationally unjustified
parameters are rejected before scientific resources are acquired. Simple returns
need only `ScientificReturn(value=...)`; empty state and absent value disposal are
shared defaults. Type erasure exists only inside shared heterogeneous dispatch.

Scientific and structural refusal remain distinct. ScientificInputRejected derives
directly from ScientificRejection and supplies the stable code and explanation
expected by shared execution. The lightweight contract lives in
provider_core.contribution_errors, so direct scientific use does not import the
host interface or require the contained runtime launcher. contribution.py and
payload.py re-export the same rejection classes for their existing callers.
Unexpected defects remain failures rather than becoming invalid input.

Scheduler description and host-local binding
--------------------------------------------
The scheduler-readable ImplementationDescription contains only immutable data:

- binding identity and sha256 revision;
- optional configuration format and digest;
- named assets with media type, size and digest;
- resident and per-call resource requirements;
- minimum process isolation and call concurrency;
- named calls, formats and state borrow/consume rules;
- cooperative interruption and progress capabilities.

It contains no factories, provider objects, paths, credentials, framework devices
or cleanup owners. The host-local ImplementationBinding contains the configured
factories, lifecycle hooks, codecs and scientific callables inside the authorized
scientific environment. ImplementationBinding.from_calls(...) derives the
scheduler call inventory from the bound calls, so the same calls are not listed a
second time.

provider_core.contribution_declaration owns canonical JSON encoding for
configuration and asset descriptions, their sha256 digests and configured binding
revision construction. A contribution supplies provider-owned values, format and
media identities, and one implementation revision identity. An implementation
with no configuration uses None; absence remains distinct from an explicit empty
configuration document. The contribution does not duplicate generic encoding,
byte counting, hashing or length-prefixing helpers.

ScientificControl is the only optional operational capability visible to an
adapter. It exposes a stop flag and bounded progress reporting, not Jobs authority,
resource allocation, process control, credentials or a service client. Numerical
functions need not receive it; the dummy keeps it in the binding adapter.

Shared execution
----------------
provider_core.hosting defines resource grants, backend capabilities, exact
allocation/reservation/operation/state/result references, identified invocations,
typed definite non-admission, observations, result custody, analysis-scoped
control and pool-owned allocation retirement.

An Operation returned by submit is already owned. NotAdmitted means this
invocation caused no dispatch or orphaned acquisition. Re-observation never
resubmits work or renews its budget. Analysis code cannot retire a shared
instance; pool administration owns that capability.

The bounded embedded backend exercises the contract with fixed local allocations.
It refuses unsupported isolation, process-global serialization and missing grants
before scientific construction. Resource-grant refusal is tested with a synthetic
requirement. The dummy itself does not claim a made-up resident quantity for its
small coefficient tuple. The backend cannot forcibly interrupt Python, persist
work across a process crash, enforce operating-system resource limits or execute
remotely. Those are backend capabilities, not restrictions on contributions.

Dummy contribution boundary
---------------------------
provider_core.examples.dummy_provider contains science.py, binding.py and its
package marker. science.py imports only the lightweight scientific rejection
contract. binding.py imports the contribution and contribution-declaration
modules. The package contains no provider-local operational machinery.

The stateful implementation demonstrates immutable configuration/assets, loaded
instance and per-analysis lifetimes, rejected and corrected preparation,
worker-local prepared state, consuming calculation, progress and cleanup. The
stateless sum uses the same typed contribution interface without inventing
configuration, model or analysis lifetimes.

Current evidence and limits
---------------------------
The revision following cfa39f7 was reviewed against numpde/hello-world
notes/000_portable_engineering_practices.txt at main@8e7eb12. The detailed review
passes and focused evidence are recorded in note 068. Subsequent simplification
removed detached call declarations, generic hashing from the provider adapter,
catch-and-rethrow rejection translation, global adapter callables, repeated exact
class checks, provider-specific empty marker records, unchecked lifecycle-hook annotations,
forced five-argument adapters and an unmeasurable dummy resident-resource
declaration.

The latest focused harness compiled the revised modules and ran 26 typed,
declaration and boundary tests. These cover the minimal keyword-only call shapes,
control-capability agreement and implementation lifetime mismatches. The revised
embedded-host module compiled but was not run against the complete installed
package. Canonical installed-wheel and Docker qualification remain required.

SECS, NMRNet, NMRPeak and Magnet still need their real scientific and guarded
execution paths connected to this installed contract. Existing AnalysisSession
permission checks remain until the host-managed path is equivalent and qualified.
Jobs integration, durable operation/result records, remote execution and
phase-specific scheduling remain later shared work under notes 065-066.
