Provider contribution and execution interface v1
================================================
2026-11-09 | Implemented shared contract; real-provider adoption remains open

Purpose
-------
This note records the first concrete interface shared by scientific contributions
and execution backends. It refines the sketches in note 066. Notes 064-066 retain
the architecture, safety rules and rollout plan; this note owns the exact v1 names
and distinctions implemented in provider-core.

The dummy contribution is intentionally science-only. It implements the
contribution interface but none of the shared service, scheduling, hosting,
permission, recovery, delivery or deployment machinery.

Provider-owned types, shared payload admission
----------------------------------------------
A contribution defines ordinary provider-owned dataclasses for every portable
input and result. For example, the dummy defines ValuesInput, EmptyInput,
PreparationResult, PredictionResult and SumResult. Scientific functions accept and
return those types directly. Anonymous dictionaries, transport lists and tuples
are not the provider interface.

`provider_core.payload.JsonDataclassCodec[T]` owns UTF-8 JSON parsing, duplicate
field detection, exact field admission, finite-number checks and construction of
T. It supports immutable portable shapes: scalars, tuples, enums, optional values
and nested frozen dataclasses. Mutable list/dict annotations are refused; use a
tuple or a named nested dataclass. Structural failures are PayloadRejected before
science runs.

Live scientific state is separate from portable payloads. A contribution defines
a provider-owned state dataclass, such as CalculationState(prepared=...).
`DataclassStateBinding[T]` checks exact names and live value types and constructs T
immediately before the scientific call. The provider does not receive a
Mapping[str, object].

`CallBinding[InstanceT, AnalysisT, InputT, StateT, OutputT]` keeps these types
through the complete host-local call:

    bytes
      -> PayloadCodec[InputT]
      -> InputT
      -> StateBinding[StateT]
      -> provider scientific call(InputT, StateT)
      -> ScientificReturn[OutputT]
      -> PayloadCodec[OutputT]
      -> bytes

The binding validates that codec formats agree with CallDescription and that the
scientific callable is annotated with the exact InputT, StateT and
ScientificReturn[OutputT]. The heterogeneous implementation registry erases types
only inside shared dynamic dispatch; provider adapter functions remain typed.

What the scheduler can see
--------------------------
`provider_core.contribution` separates an immutable data description from the
host-local Python binding. The data description contains:

- immutable binding identity and sha256 revision;
- configuration format and sha256 digest;
- named assets with media type, byte size and sha256 digest;
- resident resource requirements;
- minimum process-isolation boundary;
- named scientific calls;
- input and result format identities;
- named state inputs and outputs, including borrow or consume semantics;
- per-call resource requirements;
- instance-, process- or no scientific serialization requirements;
- cooperative interruption and progress capabilities.

`description_document()` produces the JSON-compatible scheduler view. It contains
no factories, provider dataclasses, model objects, paths, credentials, framework
devices or cleanup owners.

What the scientific host can load
---------------------------------
The host-local `ImplementationBinding` contains the provider callbacks that
interpret configuration and assets inside the authorized scientific environment.
Optional `InstanceHooks` own a loaded model/index/runtime. Optional
`AnalysisHooks` own mutable state for one analysis before preparation has
necessarily succeeded.

A scientific call receives its typed instance, typed analysis, typed portable
input, typed retained-state struct and an optional narrow `ScientificControl`.
`ScientificControl` exposes only a stop flag and bounded ProgressEvent reporting.
It exposes no Jobs authority, resource allocator, process control, credentials or
service client. Numerical functions need not receive it; an adapter may translate
it into a narrower provider-specific interface.

What shared execution supplies
------------------------------
`provider_core.hosting` defines:

- resource grants assigned by deployment;
- backend capability declarations;
- exact allocation, reservation, operation, state and result references;
- identified invocations with original limits;
- typed definite non-admission;
- observations separating acceptance, dispatch, scientific outcome, result state,
  progress, stop request, allowance expiry and resource occupancy;
- analysis-scoped submit, observe, stop and close;
- exact result read/release;
- pool administration and exact allocation retirement.

An operation returned by submit is already owned. NotAdmitted means that this
invocation caused no dispatch or orphaned acquisition. Re-observation never
resubmits or renews the original budget. Analysis code cannot retire a shared
instance; that authority belongs to pool administration.

First backend
-------------
`provider_core.embedded_host` is a bounded fixed-local backend used by shared
tests. It is not provider code and is not the final service. It supports contract
version 1, shared-process implementations, fixed local allocations, bounded
progress, explicit grants, state affinity and consumption, result retention and
exact allocation retirement.

It refuses unsupported isolation, process-global serialization and missing grants
before scientific construction. It cannot forcibly interrupt Python, persist
operations across a process crash, enforce OS memory/device limits or execute
remotely. Those are backend capabilities, not restrictions on contributions.

Dummy contribution
------------------
`provider_core.examples.dummy_provider` contains only science.py, binding.py and
its package marker. science.py imports no provider-core module. binding.py imports
only provider_core.contribution, which is the provider-facing API. The package has
no CLI, Jobs client, interpreter, scheduler, host, pool, allocator, permission
owner, recovery, delivery, drain or deployment code.

Current evidence and limits
---------------------------
The typed payload and adapter checks cover strict JSON admission, duplicate and
unexpected fields, boolean-versus-number distinction, non-finite values,
provider-owned input/result types, typed state construction, scientific rejection
after structural admission, codec/description agreement and exact callable
annotations. Changed Python files compile under Python 3.13, compatible with the
package's Python 3.12+ requirement.

The previous c994fcd local-backend evidence does not by itself qualify this typed
revision. Canonical installed-wheel/Docker qualification remains required. SECS,
NMRNet, NMRPeak and Magnet still need their real scientific and guarded execution
paths connected to this installed contract. Existing AnalysisSession permission
checks remain until the host-managed path is equivalent and qualified. Jobs
service integration, durable operation/result records, remote execution and
phase-specific scheduling remain later shared work under notes 065-066.
